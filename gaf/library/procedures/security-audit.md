저장 파일 · 통신 · 입력 · 노출 · 변조 · 외부 부품에서 흔한 결함을 위협과 대상별 질문으로 점검하고 심각도를 매긴다. 법규나 표준의 보증이 아니고 모의침투도 아니다. 본 범위에서 열린 치명 · 높음이 없다는 말일 뿐이다. 못 본 범위는 반드시 밝힌다.

## 언제 꺼내나
- 공개 출시 전, 온라인 · 멀티플레이 기능을 켜기 전.
- 디스크나 통신에서 읽는 시스템을 새로 만든 뒤, 보안 관련 버그가 보고됐을 때.
- 치명 · 높음 지적을 고친 뒤 확인(빠른 재점검).
- 아직 코드가 거의 없으면 꺼내도 결과는 「못 봄」이다.

## 필요한 역할
- 보안 엔지니어(`security-engineer`) — 점검을 하고 지적마다 심각도와 근거를 보고한다. 점검은 이 역할의 일이다. 총괄이 점검 내용을 대신 돌리지 않는다(없으면 리드 프로그래머가 겸한다 — 겸했다고 보고서의 「점검한 역할」에 적는다).
- 네트워크 프로그래머(`network-programmer`) — 통신 · 서버 권한 쪽 질문에 답하고 고친다(온라인이 있을 때만).
- 리드 프로그래머(`lead-programmer`) — 저장 · 입력 쪽 수정 범위와 담당을 권한다. 총괄이 구현 역할에게 맡긴다. 릴리스 매니저(`release-manager`)가 출시 점검과 잇는다.

## 순서
1. 범위와 입력 확인(총괄). 범위: 전체(출시 전 권장) · 네트워크 · 저장 · 입력 · 빠른(높은 심각도만, 반복 확인용). 확인할 입력: 엔진 이름과 판 · 언어 · 대상 플랫폼 · 온라인/멀티플레이 여부 · 코드 뿌리 · 함께 볼 데이터와 설정 파일. 모르는 것은 「모름」으로 적고 추정하지 않는다.
2. 온라인 여부를 가른다. 기획에서 온라인 · 멀티플레이 기능이 없다고 확인되면 네트워크 분류는 「해당 없음 — 온라인 기능 없음」이다. 그 이유를 요약에 적는다. 정해지지 않았거나 기록이 없는 것은 해당 없음이 아니다. 기록이 없다는 것을 「온라인 없음」으로 읽지 말고 총괄이 기획을 확인한다. 확인하지 못하면 네트워크 분류를 돌리되 「못 봄 — 온라인 범위 미확인」으로 표시하고 심각도는 멀티플레이 기준으로 매긴다. 온라인이 없는 게임에 서버 점검을 강제하지 않지만 확인 없이 건너뛰지도 않는다.
3. 점검 의뢰를 쓴다. 보안 엔지니어에게 주는 사실만 적는다: 범위 · 엔진과 판 · 온라인 여부와 그 근거 · 코드 뿌리 · 함께 볼 파일 · 돌릴 분류와 그 분류의 확인 질문 · 검색에 쓸 이름 · 건너뛴 분류와 이유 · 받을 모양 · 심각도 표. 게임의 종류를 두고 한 의견 · 기대하는 심각도 · 특정 지적을 두고 한 평가를 쓰지 않는다. 쓰는 순간 미리 매긴 심각도가 들어간다.
4. 검색 이름은 엔진마다 다르고 판마다 바뀐다. 프로젝트의 엔진 판 자료에서 확인한 이름만 쓴다. 이전 판에 있던 이름이 지금 판에는 없으면 검색은 0건이고 보고는 깨끗해 보인다. 확인하지 못한 이름이 필요한 분류는 「못 봄 — 이 엔진 판의 이름을 확인하지 못함」이다. 다른 엔진의 이름 목록으로 대신하지 않고 기억에서 쓰지 않는다. 확인한 이름은 하한일 뿐이니 자료가 더 말하는 이름이 있으면 더한다.
5. 분류별로 질문한다. 보안 엔지니어가 분류마다 코드와 파일을 읽어 답한다. 질문의 틀은 아래와 같다. 위협 모델에 맞게 중요도를 정하고 해당하는 질문만 돌린다.
   - 저장 · 직렬화: 불러오기 전에 파일을 검증하는가(맹목적 해석 없음) · 저장 경로가 사용자 입력에서 만들어지는가(경로 이탈) · 변조를 알아챌 서명이나 확인값이 있는가 · 저장 파일의 수치를 범위 확인 없이 믿는가 · 불러오는 근처에 코드를 실행하는 호출이 있는가.
   - 네트워크 · 멀티플레이(온라인이 있을 때): 게임 상태가 서버 기준인가 클라이언트가 결과를 정하는가 · 들어오는 패킷의 크기 · 종류 · 값 범위를 검증하는가 · 위치 · 상태 변화를 서버에서 검증하는가 · 호출 횟수 제한이 있는가 · 인증 토큰이 평문으로 가지 않는가 · 출시 빌드에 디버그 통로가 열려 있는가.
   - 입력 검증: 플레이어가 넣은 문자열이 파일 경로에 쓰이는가 · 정리 없이 로그에 남는가 · 수량 · 능력치 같은 수치를 쓰기 전에 범위를 확인하는가 · 업적 · 통계 값을 바깥에 쓰기 전에 확인하는가.
   - 데이터 노출: API 키 · 인증 정보 · 비밀이 코드나 에셋에 박혀 있는가 · 디버그 심볼이나 자세한 오류 문구가 출시 빌드에 있는가 · 민감한 플레이어 데이터를 로그에 남기는가 · 내부 경로나 시스템 정보가 보이는가.
   - 변조 · 치트: 중요한 값이 쉽게 고칠 파일에만 있는가 · 진행 · 결제 같은 핵심 상태를 서버에서 확인하는가 · 순위 · 점수 제출을 받기 전에 검증하는가 · 멀티플레이라면 메모리 편집 도구에 대비가 있는가. 클라이언트 쪽 변조 방지는 대부분 지킬 수 없다. 경쟁이나 수익이 걸리면 서버 검증에 집중한다.
   - 외부 부품: 쓰는 외부 플러그인 · 라이브러리를 나열한다 · 쓰는 판에 알려진 취약점이 있는가 · 받은 곳이 믿을 만한가(공식 상점 · 검토된 저장소). 이 환경에서 최신 취약점 목록을 확인하지 못했으면 이 칸은 「못 봄 — 확인할 것」이다.
6. 출시 전 데이터 · 권리 질문(출시할 때). 점검 범위가 작아도 통째로 빼지 않는다. 확인할 질문: 개인 정보나 기기 식별 정보를 모으거나 보내는가(분석 · 광고 · 크래시 보고 부품 포함) · 그렇다면 개인정보 안내와 동의 방법이 있는가 · 쓰는 부품과 에셋의 사용 허락 조건과 표기 의무를 지켰는가 · 판매할 상점 · 플랫폼이 요구하는 인증 · 연령 등급 · SDK 조건이 무엇인지 확인했는가(요구 내용은 그 상점의 최신 문서에서 확인한다). 해당하지 않는 항목은 「해당 없음 — 이유」로 적고, 아직 정하지 않은 항목은 「못 봄」이다.
7. 지적을 분류한다. 지적마다 번호 · 분류 · 파일:줄 · 설명 · 공격 시나리오 · 고칠 방법 · 노력(낮음/보통/높음)을 적는다. 상태는 열림 · 받아들인 위험 · 범위 밖이다.
8. 보고서에는 비밀 값을 쓰지 않는다. 비밀을 찾았으면 종류 · 파일:줄 · 노출 방식만 쓰고 값은 가린다. 보고서를 읽는 것만으로 비밀이 새지 않아야 한다.
9. 총괄이 지적을 다시 확인한다. 치명 · 높음 지적과 검색 이름은 원본(코드 · 엔진 판 자료)으로 직접 확인한다. 확인하지 못한 지적은 「미확인」으로 남긴다.
10. 고친 뒤 빠른 재점검을 한다. 보고서 이름에 범위를 넣어(전체 · 빠른 …) 같은 날 빠른 점검이 전체 점검 보고서를 덮어쓰지 않게 한다.

## 맡길 때 적을 것
- 총괄은 필요한 틀 · 규칙 · 엔진 참조를 `gaf library take <칸>/<id>…`로 꺼내 맡기는 글에 경로를 적는다.
- 결과물 경로는 `--expect "<경로,…>"`로 약속한다(존재 · 비지 않음 · 이번 일의 변경만 확인하며 내용은 안 봄). 검사 수단을 만들면 총괄이 `gaf check add "<이름>" "<명령>" [--when "<글롭,…>"] --why "<막을 실수>"`로 청해 사람의 화면 승인을 받는다. 이후 바뀐 파일에 맞는 기본 검사는 지휘자가 돌린다.
- 결과의 `[지휘자 확인]`에서 실패는 고치고 못 봄은 통과로 적지 않는다.
- 범위 · 엔진과 판 · 온라인 여부와 근거 · 코드 뿌리 · 함께 볼 데이터와 설정 · 심각도 표를 점검 의뢰에 쓴다. 의견 · 기대 심각도는 쓰지 않는다.
- 결과물: 보안 점검 보고 한 개(프로젝트가 정한 곳, 이름에 날짜와 범위). 점검 역할은 코드를 고치지 않고 읽고 보고한다.
- 끝 기준: 돌린 분류와 못 본 분류가 모두 적혀 있고, 못 본 분류마다 이유와 필요한 입력이 있다.
- 고침 일: 지적마다 파일:줄 · 끝 기준 · `--check`로 줄 수 있는 시험이나 검색 명령.

## 사람이 정할 것
- 지적을 「받아들인 위험」으로 두는 결정(보안 동의). 멀티플레이나 온라인 기능이 있는지가 아직 기획에 없을 때 그 방향(게임 내용).
- 외부 전문가의 모의침투 의뢰나 보안 도구를 사는 일(돈). 경쟁 · 수익이 걸린 멀티플레이를 출시하기 전에는 사람 전문가의 모의침투를 권한다.
- 나머지는 총괄이 정하고 결과만 알린다.

## 판정과 남길 것
- 보안 위험을 버그로 등록할 때 QA 리드가 공격으로 생기는 게임 · 데이터 피해를 `bug-lifecycle` 절차의 S1~S4 정의에 대조한다. 아래 보안 위험 이름을 S등급으로 바로 치환하지 않는다. 영향 근거가 없으면 못 봄, S1에 맞으면 테스터는 S1 후보로 적는다. 고칠 때는 P1~P4로 정하며 열린 S2의 출시 차단은 프로젝트가 정한다.
- 심각도: 치명(원격 코드 실행 · 데이터 유출 · 멀티플레이 무결성을 깨는 쉬운 치트) · 높음(진행을 우회하는 저장 변조 · 인증 정보 노출 · 서버 권한 우회) · 보통(클라이언트 쪽 치트를 돕는 것 · 정보 노출 · 영향이 작은 입력 검증 빈틈) · 낮음(공격 면을 줄이는 보강, 직접 공격 방법은 없음). 게임이 한 사람용이라고 낮추지 않고 같은 표로 매긴다. 멀티플레이이거나 범위를 확인하지 못했으면 높음을 치명으로 센다(그렇게 매겼다고 적는다).
- 분류별 판정: 통과(질문에 답하고 열린 치명 · 높음이 없다) · 실패(열린 치명 · 높음이 있다) · 못 봄 · 해당 없음. 못 봄: 엔진 모름 · 코드 뿌리 못 찾음 · 점검할 구현이 거의 없음 · 검색 이름을 확인하지 못함 · 온라인 범위 미확인 · 의존 취약점 목록을 못 봄. 못 본 분류를 「다른 방법으로 봤다」고 쓰지 않는다.
- 출시 권고(전체 판정 — 앞에서부터 처음 맞는 것): 실패 · 출시 불가(열린 치명. 멀티플레이면 열린 높음도) > 실패 · 출시 전 수정(열린 높음) > 못 봄(위의 못 본 분류가 있음) > 통과 · 본 범위에서 열린 치명 · 높음 없음(보통 · 낮음은 남아도 된다). 열린 치명이나 높음이 있고 못 본 분류도 있으면 실패이고 못 본 분류를 옆에 적는다. 소스가 두 파일뿐인 코드의 0건은 깨끗하다는 뜻이 아니다. 이 통과는 안전의 보증이 아니다.
- 남길 기록: 보고서 머리(날짜 · 범위 · 엔진과 판 · 점검한 역할 · 훑은 파일 수) · 요약 표(심각도별 건수) · 출시 권고 · 지적(치명 → 낮음) · 받아들인 위험과 이유 · 의존 목록(이름 · 판 · 출처 · 알려진 취약점과 확인한 날) · 고칠 순서 · 다시 점검할 때. 단계 점검(gate-check)은 가장 최근 전체 범위 보고와 이후의 빠른 재점검을 읽는다. 범위가 좁은 보고는 자기가 안 본 분류를 지우지 않는다.

## 하지 않는 것
- 점검 의뢰에 게임의 종류 · 기대 심각도 · 지적을 두고 한 의견을 쓰지 않는다.
- 엔진 판에서 확인하지 못한 검색 이름이나 다른 엔진의 목록으로 0건을 만들어 깨끗하다고 하지 않는다.
- 온라인이 없다고 확인된 게임에 서버 점검을 강제하지 않는다. 확인 없이 해당 없음으로 두지도 않는다.
- 출시 때 데이터 · 권리 점검을 작은 프로젝트라는 이유로 통째로 빼지 않는다.
- 비밀 값을 보고서 · 대화에 쓰지 않는다. 안전 보증이나 법규 준수 확인으로 쓰지 않는다.
- 총괄이 점검을 직접 돌리지 않는다. 다른 역할이 겸했으면 그 사실을 보고서에 적는다.
