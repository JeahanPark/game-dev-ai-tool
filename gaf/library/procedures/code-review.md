쓴 사람이 아닌 눈으로 코드를 검토하게 하고, 그 결과를 근거와 함께 받아 판정하며, 지금 고치지 않는 것은 기술 빚으로 남겨 후속 일로 잇는다. 판정 넷과 지적 목록이 필요한 코드 검토는 검토 역할에게 보통 `gaf assign`으로 맡기고 검토 보고 파일을 `--expect`로 받는다.

## 언제 꺼내나
- 구현 역할이 코드를 내놓았고, 끝났다고 부르기 전에 다른 눈이 필요할 때.
- 기획 문서나 구조 결정 기록(ADR)이 있는 일의 구현이 그 결정을 따르는지 볼 때.
- 코드를 훑다가 급히 넘긴 곳 · 임시 처리 · 반복된 중복이 보일 때(기술 빚 기록).
- 마일스톤 앞에서 쌓인 빚의 추세를 볼 때.
- 검토할 코드가 아직 없으면 꺼내지 않는다. 있는 척 채운 보고가 가장 나쁘다.

## 필요한 역할
- 리드 프로그래머(`lead-programmer`) — 검토 역할. 규칙 · 구조 · 시험 가능성을 본다. 기술 빚 등록부의 유일한 기록자다.
- 엔진 전문가(프로젝트의 엔진 것) — 엔진이 정해져 있으면 한 명만 검토에 덧붙인다. 파일 종류(코드 · 셰이더 · UI · 엔진 구조)에 맞는 관점을 맡는다. 엔진이 정해지지 않았으면 부르지 않고 「엔진 검증: 못 봄 — 엔진이 정해지지 않았다」를 보고에 적는다.
- QA 테스터(`qa-tester`) — 시험 근거(수용 기준에 맞는 시험 사례 · 증거)를 만들거나 확인한 역할. 검토에는 근거만 넘기고 검토를 맡기지는 않는다.
- 구현 역할(게임플레이 프로그래머 등) — 지적을 받아 고친다. 검토자와 같은 세션이 아니어야 한다.
- 테크니컬 디렉터(`technical-director`) — 구조 결정과 어긋난 지적, 큰 빚의 우선순위를 판단한다(없으면 리드 프로그래머가 겸한다 — 겸했다고 보고에 적는다).

## 순서
### 코드 검토
1. 총괄이 입력을 확인한다. 받는 사람: 총괄. 내놓을 것: 입력별 「있음 / 없음」 표(바뀐 범위 · 기획 문서 · 구조 결정 · 수용 기준 · 시험 결과 · 프로젝트 코딩 기준). 끝 기준: 검토 입력을 못 받은 절은 「못 봄 — 자료 없음」으로 적는다. 약속했거나 규칙이 만들라고 한 산출물이 없으면 실패다. 추정으로 채우지 않는다. 입력이 전부 없으면 검토를 시작하지 않고 무엇이 없는지와 누가 만드는지만 보고한다.
2. 총괄이 검토 의뢰를 써 검토 역할에게 보통 `gaf assign`으로 맡긴다(아래 「맡길 때 적을 것」). 의뢰는 사실만 적는다. 바라는 결론 · 예상 심각도 · 「문제없어 보인다」 같은 말을 쓰지 않는다. 끝 기준: 의뢰에 검토자의 결론을 유도하는 문장이 없다.
3. 검토 역할이 파일을 끝까지 읽고 점검한다. 파일마다 내놓을 것: 지적 목록. 지적 하나는 「파일:줄 · 인용한 코드 또는 문제가 일어나는 입력 · 왜 문제인가 · 확신도 · 재현 조건」을 갖춘다. 겉보기만 이상한 곳(의도한 패턴 · 이미 막은 경우)은 입력을 하나씩 따져 본 뒤에 결함이라 부른다.
4. 구조 결정 따르기를 본다. 결정 참조는 맡긴 일 카드 · 파일 머리 주석 · 그 파일의 커밋 메시지 순으로 찾는다. 결정 기록 가운데 「결정」과 「결과」 부분만 읽는다. 어긋남은 세 가지로 가른다.
   - 구조 위반(막힘): 결정이 명시적으로 버린 방식을 썼다.
   - 결정 이탈(경고): 금지된 방식은 아니나 고른 방향에서 크게 벗어났다.
   - 사소한 차이(참고): 구조에 영향이 없는 작은 차이.
   참조한 결정 기록이 없으면 「참조 없음 — 이 점검 건너뜀」이고, 있는데 못 읽으면 「못 봄 — 읽지 못함」이다. 둘은 다른 결과다. 참조 없음은 통과를 막지 않는다.
5. 규칙 · 구조 점검표를 돈다. 점검 항목:
   - 규칙: 공개 함수 · 클래스에 설명 주석, 함수가 너무 길거나 복잡하지 않은가(시작 값의 예: 한 함수 40줄 · 분기 복잡도 10 — 프로젝트가 정하면 그 값), 게임 상태에 정적 단일 객체를 쓰지 않았는가, 설정값을 데이터 파일에서 읽는가, 시스템이 구체 클래스가 아닌 인터페이스를 내놓는가.
   - 구조: 의존 방향(엔진 ← 게임플레이, 반대 아님), 모듈 순환 없음, 층 분리(UI가 게임 상태를 갖지 않는다), 여러 시스템 사이는 이벤트로, 이미 있는 패턴과 일관.
   - 설계 원칙(단일 책임 · 확장 가능 · 치환 가능 · 얇은 인터페이스 · 추상에 의존)은 위반이 눈에 띄는 곳만 적는다. 점검표를 채우려고 지적을 만들지 않는다.
   - 게임 특유: 프레임 시간에 독립(델타 시간 사용), 매 프레임 도는 곳의 새 할당 없음, 빈 값 · 널 처리, 필요한 곳의 스레드 안전, 자원 정리.
6. 엔진 검토(엔진이 있을 때). 파일 종류별로 본다. 숫자나 이름이 엔진 판에 묶인 주장은 「프로젝트의 엔진 판에서 확인」한 것만 단정하고 확인하지 못한 API 이름은 「미확인」으로 표시한다.
   - 코드: 움직임 · 타이머 · 속도에 델타 시간, 업데이트 안의 할당과 노드 찾기 · 컴포넌트 찾기(준비 시점에 보관), 해제될 수 있는 객체를 오래 들고 있을 때의 유효성 검사, 신호 · 콜백 연결을 한 번만 하고 수신자가 먼저 사라지면 끊는가, 신호처럼 꾸민 동기 호출 사슬이 없는가.
   - 셰이더: 렌더러와 셰이더 종류가 프로젝트에 맞는가, 픽셀마다 드는 비용(분기 · 가변 반복 · 불투명면의 버림 · 투명면의 덧그림), 0으로 나누기 · 음수 거듭제곱 · 영벡터 정규화, 시간 기반 효과는 엔진의 시간 값을 쓰는가.
   - UI: 게임 상태는 읽기만 하고 쓰지 않는다, 글은 문자열 표에서 가져오고 번역이 길어질 자리가 있다, 마우스 없이 초점이 움직인다, 일시정지 · 모달이 바꾼 것을 되돌린다, 매 프레임 목록을 다시 만들지 않는다.
   - 엔진 구조: 장면 · 노드의 소유가 분명하고 위로 거슬러 올라가 참조하지 않는다, 준비 시점 함수를 제 쓰임대로 쓰고 형제 순서에 기대지 않는다, 전역 객체가 다른 시스템이 쓰는 상태를 갖지 않는다, 에디터가 쓰는 파일(장면 · 자원 · 메타)이 그것을 쓰는 스크립트와 맞는다.
7. 시험 가능성은 총괄이 고른 검토 역할이 직접 본다(시험 담당을 새로 부르지 않는다). 로직 · 통합 일에서: 시험이 닿아야 할 함수가 숨겨져 있지 않은가(숨은 위치와 필요한 함수 이름을 적는다), 시험 사례마다 닿을 코드 경로가 있는가, 값이 코드에 박혀 있거나 주입할 틈이 없어 시험할 수 없는 수용 기준이 있는가, 시험 사례가 덮지 않는 예외 상황이 새로 생기지 않았는가, 시험이 없는 눈에 띄는 부수 효과가 있는가. 시험이 닿을 길이 없어 시험 사례를 못 돌리면 그 길을 내는 것이 필수 수정이다. 보기와 느낌 · UI 일에서는 손으로 확인할 단계마다 그 상태에 닿을 수 있는지와 어떻게 닿는지를 적는다.
8. 총괄이 지적을 원본으로 다시 확인한다(아래 「판정과 남길 것」). 끝 기준: 심각한 지적과 API 주장 하나하나에 「확인함」 또는 「못 확인 — 검토자 주장」이 붙어 있다.
9. 판정과 필수 수정을 정한다. 필수 수정은 구현 역할에게 일 맡기기(assign)로 돌려보내고 검사 명령이 있으면 `--check`를 건다. 구조 위반이 기존 결정과 어긋나면 구현을 고친다. 설계가 정당하게 바뀐 것이면 결정 기록을 고쳐 쓰게 하고 경쟁하는 새 기록을 만들지 않는다. 결정 기록이 아예 없는 방식을 위반으로 짚었다면 먼저 올바른 방식을 결정 기록으로 남기게 한다.

### 기술 빚 기록
1. 탐색. 구현 역할이 아닌 리드 프로그래머가 코드 뿌리에서 빚의 흔적을 찾는다: 미룬 일 표시(TODO), 고칠 것 표시(FIXME — 결함이 빚으로 위장한 것이다), 임시 처리 표시(HACK), 폐기 예정 표시, 비슷한 코드 덩이의 중복, 너무 큰 파일 · 함수(참고값의 예: 500줄 파일 · 50줄 함수 — 프로젝트가 정하면 그 값). 이 숫자는 후보를 찾는 보조일 뿐 결함 판정이 아니다.
2. 분모를 먼저 밝힌다. 실제로 훑은 소스 파일 수를 센다. 코드 뿌리를 못 정했으면 「못 봄 — 코드 뿌리 미정」, 0개면 「못 봄 — 검사할 소스가 없다」로 끝내고 등록부를 쓰지 않는다. 400개를 훑어 0건이면 깨끗한 코드이고, 0개를 훑어 0건이면 아무 정보도 아니다. 건수를 보고할 때는 항상 훑은 수를 같이 적는다.
3. 분류. 구조 · 코드 품질 · 시험 · 문서 · 의존 · 성능 여섯 가지 중 하나.
4. 등록. 항목마다 열 칸을 채운다: 번호 · 분류 · 설명(무엇이고 왜 떠안았나) · 파일 · 규모(S · M · L · XL) · 영향(낮음 · 보통 · 높음 · 치명) · 우선순위 · 상태 · 추가한 날 · 고칠 일정 또는 「나중」. 상태는 열림 · 해결(날짜) · 받아들임(이유). 모르는 칸은 「—」로 두고 추측으로 채우지 않는다. 리드 프로그래머가 이 열 칸의 등록부에서 번호를 발급하는 유일한 기록자다. 버린 번호도 남기고 다시 쓰지 않는다. 등록부는 덮어쓰지 않고 고쳐 쓴다.
5. 합치기. 이미 열려 있는 항목과 같은 것인지는 파일과 분류가 같다는 것만으로 정하지 않는다. 같은 위치 · 같은 원인임이 보이면 그 항목을 갱신하고, 코드에서 패턴이 사라진 열린 항목은 「해결」 후보로 올린다.
6. 우선순위. 시작 값의 예: 영향 점수(낮음 1 · 보통 2 · 높음 3 · 치명 4)를 규모 점수(S 1 · M 2 · L 3 · XL 4)로 나눠 소수 한 자리로 적고 점수가 높은 것부터, 같으면 오래된 것부터 놓는다. 영향이나 규모를 아직 못 정한 항목은 점수 없이 「점수 안 매김 — 칸 판단 전」으로 뒤에 둔다. 점수는 정렬 보조이고 중요도를 대신하지 않는다.
7. 후속 일로 잇는다. 높은 항목은 근거(파일 · 줄) · 영향 · 고칠 범위 · 끝 기준을 갖춘 일로 만들어 구현 역할에게 맡기거나 다음 계획의 일감으로 올린다. 일정이 정해지지 않고 오래 남은 항목(시작 값의 예: 계획 단위 셋 이상)은 고치거나 이유를 달아 받아들인다.
8. 보고서만 필요할 때는 등록부를 읽기만 한다(등록부가 없으면 우선순위 · 보고 모두 「못 봄 — 등록부 없음」): 분류별 열린 항목 수와 규모 합, 기간 안에 늘어난 것과 해결한 것, 늘어나는지 · 비슷한지 · 줄어드는지, 오래 방치된 항목.

## 맡길 때 적을 것
- 총괄은 필요한 틀 · 규칙 · 엔진 참조를 `gaf library take <칸>/<id>…`로 꺼내 맡기는 글에 경로를 적는다.
- 결과물 경로는 `--expect "<경로,…>"`로 약속한다(존재 · 비지 않음 · 이번 일의 변경만 확인하며 내용은 안 봄). 검사 수단을 만들면 총괄이 `gaf check add "<이름>" "<명령>" [--when "<글롭,…>"] --why "<막을 실수>"`로 청해 사람의 화면 승인을 받는다. 이후 바뀐 파일에 맞는 기본 검사는 지휘자가 돌린다.
- 결과의 `[지휘자 확인]`에서 실패는 고치고 못 봄은 통과로 적지 않는다.
- 검토 의뢰(검토 역할에게):
  - 읽을 파일: 바뀐 범위의 파일 전부(파일마다 종류 — 코드 · 셰이더 · UI · 엔진 구조), 관련 기획 문서 · 구조 결정 기록 · 수용 기준 · 시험 결과(건수 · 통과/실패 · 어느 실행의 것인지).
  - 맡기는 일의 처음 기준(바뀐 범위가 무엇이었나)을 적는다. 작업 트리 전체의 변경이 아니라 이 일이 건드린 파일만 범위다.
  - 엔진 이름과 판(있을 때), 엔진 판에 묶인 주장은 「프로젝트의 엔진 판에서 확인」하라는 말.
  - 받을 모양: 지적마다 파일:줄 · 인용 · 이유 · 확신도(확인함 · 미확인) · 재현 조건, 그리고 판정과 필수 수정 · 제안 · 좋은 점.
  - 쓰지 않는다: 바라는 결론 · 예상 심각도 · 지적 개수의 기대.
  - 검토 역할은 대상 코드를 고치지 않고 검토 보고 파일만 쓴다.
- 구현 역할에게 돌려보낼 때: 필수 수정마다 파일:줄과 끝 기준, `--check`로 줄 수 있는 검사 명령(시험 · 빌드).
- `--review <검토 역할,…>`는 사람에게 보일 결과물 · 눈으로 봐야 하는 것의 채택 고리다. 검토 역할은 먼저 `gaf role new`로 만들고 만든 역할 자신은 넣지 않는다. 후보마다 새 검토 세션이 첫 줄 「통과」 또는 「막힘: <요약>」으로 답한다(판단 못 하면 「막힘: 못 봄 — <무엇을 왜 못 봤는지>」). 막힘의 지적은 만든 역할에게 돌아가 다음 후보를 낸다. 모두 통과하고 지금까지 가장 나은 것보다 낫다고 고를 때만 채택한다. 총괄은 회차 줄(채택 · 막힘 몇 곳)과 채택이 하나도 없을 때의 마지막 회차 지적만 받는다. 회차마다 새 세션이라 사용량이 많이 든다. 검토 보고를 받는 길로 쓰지 않는다.
- 기술 빚 일: 코드 뿌리 · 훑을 범위 · 기존 등록부 위치 · 쓰는 역할 한 명.

## 사람이 정할 것
- 없다. 코드 검토 · 빚 기록은 총괄이 정하고 결과만 알린다. 단 빚을 고치는 데 돈이 들거나 되돌리기 어렵거나(데이터 이동 등) 게임의 규칙 · 보이는 모습이 바뀔 때만 「내가 정할 것」에 올린다(보기 1~2개, 권하는 쪽 먼저).

## 판정과 남길 것
- 판정 순서(앞에서부터 처음 맞는 것): 실패 > 못 봄 > 통과(제안 있음) > 통과.
  - 실패: 필수 수정이 하나라도 있다. 구조 위반은 항상 필수 수정이다.
  - 못 봄: 검토할 코드를 받지 못했다, 엔진 검토가 돌지 않았거나 결과가 비었거나 형식이 깨졌다, 읽지 못한 결정 기록이 있다, 구조 · 설계 원칙 절이 못 봄이다. 엔진 검토를 건너뛴 검토는 코드를 통과시킨 것이 아니다. 단 알려진 결함이 있으면 실패가 먼저다.
  - 통과(제안 있음): 필수 수정이 없고 제안만 있다.
  - 통과: 필수 수정도 제안도 없다. 결정 기록 참조가 없다는 것만으로는 막지 않는다.
  - 해당 없음: 시험 가능성은 설정과 데이터 일에는 해당 없음이다.
- 검토자 주장 재확인: 검토자는 코드를 새로 만들 때는 믿을 만하지만 이미 있는 코드를 진단할 때는 틀릴 수 있다. 짧은 함수를 두고 한 틀린 주장도 매끄러워서 훑어 넘기기 쉽고, 입력을 하나씩 따져 보면 무너지는 결함 주장도 있다. 그래서 총괄은 API 이름 · 판에 묶인 주장과 심각한 지적을 원본(코드 · 엔진 판의 자료)으로 직접 다시 확인한다. 확인하면 「확인함」, 못 하면 「미확인 — 검토자 주장」으로 적어 보고에 그대로 남기거나 뺀다. 말투가 확신에 차 있다는 이유로 결함으로 올리지 않는다.
- 남길 기록: 검토 보고 한 건 — 대상 · 입력 있음/없음 표 · 엔진 검증 결과(또는 못 봄 이유) · 시험 가능성 · 구조 결정 따르기(없음/못 읽음/준수/이탈/위반) · 규칙 점검 통과 수 · 구조 · 게임 특유 문제 · 좋은 점 · 필수 수정 · 제안 · 판정. 좋은 점은 항상 적는다. 기술 빚 등록부의 열 칸 표.
- 이 글의 「통과」는 검토 역할의 판정이지 사람의 승인을 대신하지 않는다.

## 하지 않는 것
- 쓴 역할이 자기 코드를 스스로 검토해 통과시키지 않는다.
- 검토 의뢰에 바라는 결론 · 예상 심각도를 쓰지 않는다.
- 검토자가 한 말을 원본 확인 없이 결함으로 올리지 않는다. 판에 묶인 API 이름을 기억에서 단정하지 않는다.
- 검토 보고서가 자료 없음을 「문제 없음」으로 바꾸지 않는다. 0건을 훑은 것을 깨끗함으로 적지 않는다.
- 점검표의 숫자(줄 수 · 복잡도 · 파일 크기)를 결함의 증거로 쓰지 않는다. 후보를 찾는 값일 뿐이다.
- 빚을 몰래 쌓지 않는다. 임시 처리는 이유와 함께 등록하고, 같은 파일 · 같은 분류만 보고 서로 다른 빚을 하나로 합치지 않는다.
- 검토하는 역할이 코드를 고치지 않는다. 고침은 구현 역할이 한다.
