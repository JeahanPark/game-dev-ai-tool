시험이 실제로 돌았고 그 결과가 이번 빌드의 것임을 확인하는 절차다. 약속한 시험 파일 누락은 실패, 실행 수단 없음 · 0건 실행은 못 봄이다. 작은 일도 일괄 면제하지 않는다.

## 언제 꺼내나
- 구현 전에 일마다 어떤 시험과 증거가 필요한지 정할 때, 구현 뒤 QA에 넘기기 전에 빌드 상태를 볼 때, 단계 점검(gate-check) 앞에서 시험 근거를 모을 때.
- 버그를 고쳤는데 재발 방지 시험이 있는지 볼 때, 시험이 간헐적으로 실패할 때, 오래 켜 둔 플레이의 누수 · 피로를 볼 때, 시험 환경이 아예 없을 때.

## 필요한 역할
- QA 리드(`qa-lead`) — 계획 · 증거 기준 · 판정을 보고한다.
- QA 테스터(`qa-tester`) — 시험을 돌리고 결과를 읽어 기록한다(없으면 QA 리드가 겸한다 — 겸했다고 보고에 적는다).
- 게임플레이 프로그래머(`gameplay-programmer`) · 도구 프로그래머(`tools-programmer`) — 시험 코드와 보조 코드를 쓴다.
- 데브옵스 엔지니어(`devops-engineer`) — 자동 실행 틀(CI)을 맡는다.
- 엔진 전문가(프로젝트의 엔진 것 — `unity-specialist` · `unreal-specialist` · `godot-specialist`) — 엔진 시험기의 결과 읽는 법을 확인한다.

## 순서
공통: 입력(일 · 시험 · 결과 · 기획)을 센다. 약속했거나 규칙이 요구한 산출물 없음은 실패, 검토 입력을 못 받았으면 못 봄이다. 빠진 입력과 만들 곳을 적고 빈 표를 완료로 내지 않는다.

### 시험 계획(구현 전)
맡김: QA 리드가 범위의 일 목록 · 수용 기준 · 기획 문서를 받아 시험 계획을 내놓는다. 끝: 일마다 종류 · 자동 시험 · 손 확인 칸이 찼다(빈 칸은 「지적」이나 「면제 — 이유」).
1. 일마다 종류 · 수용 기준 · 관련 기획 문서의 수식 · 예외 상황 · 구조 결정의 금지 방식을 모은다. 수용 기준이 없는 일은 그 자체가 지적 사항이다. 기획 문서를 가리키지 않는 일은 간극으로 적되 계획을 막지 않는다.
2. 종류를 정한다: 로직 · 통합 · 보기와 느낌 · UI · 설정과 데이터. 최소 증거는 QA 리드 글(`roles/qa-lead.md`)의 표를 따른다. 일에 종류가 적혀 있어도 수용 기준과 한 번 대조해 어긋나면 보고한다. 적혀 있지 않으면 수용 기준으로 정하고 「추론」이라 적는다. 섞인 일은 위험이 가장 큰 기준으로 주 종류를 정하고 부 종류를 적는다. 로직과 통합 사이에서 애매하면 통합으로 잡는다(두 시험이 다 필요하다).
3. 계획을 쓴다. 요약 표(일 · 종류 · 자동 시험 · 손 확인), 자동 시험(위치 · 볼 수식과 규칙 · 상태 전환 · 부수 효과 · 경계값: 0 · 최소 · 최대 · 잘못된 입력 · 기획 문서의 예외 상황), 손 확인(확인 방법 · 확인할 역할 · 남길 증거 · 수용 기준마다 관찰할 수 있고 틀렸음을 보일 수 있는 항목), 스모크 범위, 플레이 시험 요건(일 · 답할 질문 · 최소 횟수 · 대상 플레이어 — 권고이고 결정은 사람), 끝 정의. 시험 사례 · 수식을 지어내지 않는다 — 문서에 없으면 지적한다. 「느낌」 같은 주관 표현은 기준이나 플레이 시험 규약을 덧붙인다.
4. 끝 정의: 수용 기준마다 QA 리드 표의 최소 증거와 수준을 그대로 적용한다. 스모크 통과 · 회귀 없음 · 코드 검토도 확인한다.
5. 면제 · 최소 스모크로 줄인 이유를 적는다. 보기와 느낌 · UI의 화면 증거는 면제하지 않는다. UI의 입력 · 상태 전환 · 표시 데이터도 시험 대상이므로 통째로 면제하지 않는다.

### 시험 준비와 보조 코드
맡김: 도구 프로그래머(자동 실행 틀은 데브옵스 엔지니어)가 엔진과 그 판 · 있는 시험 폴더를 받아 시험 폴더 · 안내 글 · 핵심 경로 점검표 · 자동 실행 설정을 내놓는다. 끝: 아래 3의 네 칸을 따로 적은 보고.
1. 엔진이 정해지지 않았으면 멈추고 총괄에게 보고한다(추측하지 않는다). 있는 시험 폴더 · 자동 실행 틀을 읽고, 없는 파일만 만든다(덮어쓰지 않는다).
2. 시험 파일은 엔진이 컴파일하거나 읽는 곳에 둔다. 그 밖에 두면 시험이 0건 돌고 통과로 보인다. 위치와 시험기 이름 · 명령은 프로젝트의 엔진 판에서 확인해 프로젝트가 정한다. 자동 실행 틀은 결과 파일을 늘 남기고, 종료 코드만이 아니라 결과의 시험 수 · 실패 수로 판정한다.
3. 만든 것 보고는 「파일 준비」 · 「시험 틀 설치」 · 「자동 실행 연결」 · 「첫 실행 통과」를 따로 적는다. 준비됐다는 말은 통과가 아니다. 설치 · 외부 도구 · 비밀값(라이선스 열쇠 등)은 별도 일이다.
4. 핵심 경로 점검표를 만든다: 시작 · 새 게임 · 메뉴 입력 · 주요 조작 · 저장/불러오기 · 성능. 성능 기준과 시간은 이 게임의 예산에 맞춘다(기본 가정 금지). 아직 없는 기능은 「해당 없음 — 구현 전」으로 두고, 핵심 시스템이 들어오면 항목을 더한다.
5. 보조 코드(게임플레이 · 도구 프로그래머)는 같은 준비를 여러 시험이 되풀이할 때만 만든다. 기존 시험(예: 다섯 개)의 패턴에 맞춘다. 단언은 시험 틀이 주는 단언 API로 한다. 맨 단언문은 첫 실패에서 실행이 멈추거나 출시 빌드에서 사라진다. 올바른 API를 확인하지 못했으면 보조 코드를 만들지 않는다. 보조 코드는 시험 묶음을 상속하지 않는 일반 클래스다. 경계 · 상수는 기획 문서의 수식에서 가져온다. 이미 있는 보조 파일은 덮어쓰지 않는다. 예제의 자리표시자는 실행되는 코드가 아니니 확인 전에 복사하지 않는다.

### 스모크(QA에 넘기기 전)
맡김: QA 테스터가 빌드 · 계획의 스모크 범위 · 일 목록을 받아 스모크 보고를 내놓는다. 실패를 고치지 않고 보고한다. 끝: 필수 항목마다 판정과 증거가 있다.
1. 빌드 환경을 찾는다: 시험 파일이 정말 있는가(폴더나 체크리스트 문서는 시험이 아니다), 실행기가 설치돼 있는가, 계획 · 점검표가 있는가. 실행기가 없으면 「못 봄 — 실행기 없음」이고 조용히 건너뛰지 않는다.
2. 자동 시험을 돌린다. 프로젝트가 정한 명령을 시간 제한과 함께. 시간 초과는 통과가 아니라 실패다. 결과는 종료 코드가 아니라 출력과 결과 파일을 읽는다: 돈 시험 수 · 통과 · 실패 · 건너뜀 · 실패 이름(열 개까지). 이번 실행의 것인지 확인한다(실행 전 옛 결과 파일 삭제 · 실행별 결과 경로 · 시각). 편집 모드와 플레이 모드가 따로 도는 엔진은 각각 돌려 각각 보고한다. 한쪽을 못 돌렸으면 「못 봄」이고 다른 쪽이 덮어 주지 않는다.
3. 일마다 증거를 찾는다: 증거 발견 · 손 확인 · 없음 · 권고 증거 없음(설정과 데이터의 기본 동작 확인 통과) · 알 수 없음. 이름이 비슷하다고 덮었다고 쓰지 않는다.
4. 손 확인: 먼저 「이번에 현재 빌드를 실제로 실행했나」를 확인한다. 안 했으면 이후 항목은 전부 「못 봄 — 실행 안 함」이다. 점검표의 출처를 보고에 쓴다(계획의 스모크 범위 · 프로젝트 점검표 · 표준 목록). 시작 · 새 게임 · 기본 조작 · 이번 변경과 회귀 · 저장/불러오기 · 프레임 끊김. 대상 기기가 정해졌으면 PC(키보드 · 마우스 · 창/전체 화면 · 해상도 바꾸기), 콘솔(게임패드 · TV 안전 영역 · 게임패드에 뜬 키보드 안내 · 저장 없는 첫 실행), 모바일(터치 · 화면 방향 · 백그라운드 전환 · 발열)을 더한다. 플랫폼 인증 요건은 확인할 질문으로 둔다. 답이 없는 항목을 통과로 치지 않는다. 항목마다 통과/실패/못 봄과 증거를 적는다.
5. 보고서에는 필수 항목 전부가 판정에 들어간다. 저장 · 성능 항목의 실패를 판정식에서 빠뜨리지 않는다. 빠른 실행은 「빠른 실행 — 범위 · 저장 · 성능 안 봄」으로 표시한다. 플랫폼별 표를 쓰면 못 본 칸도 표에 넣는다.
6. 실패나 못 봄이면 손 시험에 넘기지 않는다. 못 본 항목마다 까닭과 돌릴 길을 적는다.

### 회귀 묶음
맡김: QA 리드가 시험 목록 · 수용 기준 · 닫힌 버그를 받아 회귀 목록과 간극 표를 내놓는다. 끝: 핵심 경로마다 · 고친 버그마다 덮음 칸이 찼다.
1. 새로 고친 버그마다 그 버그 번호나 실패 장면을 가리키는 시험이 있는지 본다. 없으면 간극이다. 수식 · 상태 기계에 해당하면 높은 우선순위다.
2. 핵심 경로(수용 기준) 가운데 시험이 없는 것을 찾는다: 닿음 · 일부 · 없음 · 면제(이유 필수). 이름 일치만으로 닿음으로 쓰지 않고 실제 검증문을 읽는다.
3. 분모를 센다. 핵심 경로가 0이거나 시험 파일이 0이면 퍼센트를 내지 않고 「못 봄」이다.
4. 밀림을 본다: 끝난 일인데 시험이 없음 · 지난 갱신 뒤 생긴 시스템 · 바뀐 기획 문서 · 오래 갱신하지 않은 목록.
5. 목록에는 이미 있는 시험만 올린다. 갱신은 덧붙이기만 하고 목록에서 시험을 지우지 않는다. 격리(꺼 둠)는 삭제가 아니다.

### 장시간 플레이
맡김: QA 리드가 세션 설계 · 성능 예산 · 최근 플레이 시험을 받아 장시간 규약(체크포인트 · 기록 칸)을 내놓고, 플레이 뒤 기록을 읽어 판정한다. 끝: 체크포인트마다 칸이 찼거나 못 간 체크포인트가 적혔다.
1. 길이는 게임의 세션 설계에 맞춘다. 시작 값의 예: 30분 · 1시간 · 2시간 · 4시간. 첫 시험은 메모리 · 안정성 · 재미 피로를 모두 본다. 새로 켠 상태에서 시작하고, 쓴 계측 도구 이름과 지켜볼 알려진 문제를 적는다.
2. 체크포인트를 시간으로 정하고(예: 한 시간이면 15분마다) 시작(T+0) 값을 먼저 적는다. 도구가 보여 주는 단위 그대로 적고 변환하지 않는다. 임계는 시작 값 대비 증가율 · 단조 증가 추세다(예: 처음 15분 뒤 계속 20% 넘게 늘면 알림 — 프로젝트가 정하면 그 값). 장면을 내리면 처음 값으로 돌아와야 하는 개체 수는 절대값으로 본다.
3. 체크포인트마다: 메모리 · 개체 수 · 프레임 · 충돌/멈춤 · 소리 · HUD · 입력, 핵심 조작의 보람 · 난이도 체감 · 본 것 같은 순간 · 답답하거나 몰입한 순간과 까닭. 끝난 뒤: 메모리 추세와 누수 여부 · 충돌 수 · 최저 프레임 · 재미 곡선 · 콘텐츠가 바닥난 시점.
4. 자동 계측(메모리 · 프레임 시간 · 개체 수)은 총괄이 배경 일로 띄운다. 재미 피로 같은 느낌은 사람이 플레이해야 하니 그 칸은 사람이 하기 전까지 「못 봄」이다. 도구 이름과 칸은 엔진 판에서 확인하고(미확인이면 그렇게 적는다), 계측 도구를 못 찾았으면 못 봄이다.
5. 문제는 등급과 체크포인트를 달아 버그 신고로 넘긴다.

### 불안정한 시험
맡김: QA 테스터가 여러 번의 실행 기록과 시험 코드를 받아 불안정 보고를 내놓는다. 고침은 총괄이 시험을 쓴 프로그래머에게 따로 맡긴다. 끝: 같은 조건끼리 견준 표와 시험마다 원인 후보.
1. 실행 기록이 없으면 못 봄이다. 여러 번 돌려 결과 파일을 모으는 일을 먼저 맡긴다. 같은 코드 판 · 같은 씨앗 · 같은 환경끼리 이력을 묶어 견준다. 코드가 바뀐 이력은 같은 이력이 아니다. 건너뜀 · 결론 없음은 이력에 넣지 않는다.
2. 같은 조건에서 통과와 실패가 섞인 것이 불안정이다. 실행이 세 번 미만이면 모두 「의심」이고 격리하지 않는다. 다섯 번 미만이면 자료 한계를 적는다.
3. 원인 후보와 고칠 방향: 시간/비동기(명시적 대기) · 순서 의존(준비 · 정리로 떼기) · 난수 씨앗(씨앗을 넘김) · 자원 정리 누락 · 바깥 상태(파일 · 전역에서 떼기) · 부동소수 비교(오차 비교) · 장면 불러오기 경합(준비될 때까지 대기). 코드에서 시간 호출 · 난수 · 전역 상태 · 실수 비교를 찾는다.
4. 성공률이 낮다고 시험을 끄지 않는다. 원인 고침이 먼저다. 격리가 불가피하면 시험을 지우지 않고 건너뜀 표시 + 목록(원인 · 담당 · 고칠 기한 · 다시 넣을 조건)을 남기고 별도로 계속 돌린다. 목록의 기존 항목은 지우지 않는다. 건너뛴 시험은 CI가 초록이어도 빠진 범위로 보고한다. 엔진별 건너뛰는 방법은 확인된 것만 쓰고 모르면 사람이 아니라 엔진 전문가에게 묻는다.

### 증거 검토
맡김: QA 리드가 일 · 수용 기준 · 증거 경로를 받아 일마다 판정을 낸 증거 검토 보고를 내놓는다. 고치지 않고 보고한다. 끝: 범위의 일마다 판정과 까닭.
1. 일마다 증거를 찾는다(일에 적힌 경로 먼저). 시험이 돌아 통과했다는 것과 시험의 질은 다르다.
2. 자동 시험: 단언이 하나도 없으면 헛통과라 실패다. 단언 수는 보조 지표일 뿐 기준이 아니다. 경계값 · 수식 이름 연결 · 시험 이름이 시나리오와 기대를 말하는지 본다. 「test_1」 같은 이름은 이름 문제로 적는다.
3. 손 증거: 수용 기준마다 연결 · 남긴 화면 캡처(설명만 있으면 증거가 아니다) · 보기와 느낌은 증거 문서의 확인 칸이 모두 찼는가 · 날짜. UI 일은 증거 문서와 확인 칸 없이 바뀐 화면마다 남긴 캡처로 닫는다. 증거 뒤에 코드가 바뀌었으면 보고만 하지 않고 그 기준을 못 봄으로 돌린다.
4. 일마다 판정: 통과(증거가 있고 질 점검을 넘고 기준을 다 덮음) · 실패(증거 없음, 또는 단언 0 · 캡처 없음 · 빈 확인 칸 같은 질 부족) · 못 봄(종류를 모름 · 증거를 못 읽음 · 일 파일을 못 읽음 — 어느 것인지 적는다). 일을 막는 지적은 기준이 정말 검증되지 않은 것만이고, 나머지는 권고로 적는다.

## 맡길 때 적을 것
- `--review`는 사람에게 보일 시각 결과물의 채택 고리다(`code-review`의 답 · 반환 규칙). 검토 역할은 먼저 `gaf role new`로 만든다. 후보마다 새 세션의 첫 줄은 「통과」 또는 「막힘: …」(못 보면 「막힘: 못 봄 — <무엇을 왜>」)다. 매회 새 세션이라 사용량이 많다.
- 총괄이 `gaf library take <칸>/<id>…`로 꺼낸 틀 · 규칙 · 엔진 참조의 경로를 준다.
- `--expect`에 결과물 경로를 적는다(존재 · 비지 않음 · 이번 변경 확인, 내용은 별도). 검사 수단을 만들면 총괄이 `gaf check add`로 청해 사람이 화면 승인한다(`project-start`의 명령 꼴). `[지휘자 확인]`의 못 봄은 통과가 아니다.
- 갈래별 입력 · 결과물 경로 · 끝 기준을 준다. 이번 실행의 수와 결과를 보고한다.
- `--check`: 시험 명령(0건이면 실패). 보기와 느낌 · UI 결과물 채택에만 `--review`를 쓴다.
- 5분 넘는 시험 · 계측은 총괄의 배경 일로 돌린다.

## 사람이 정할 것
- 애매한 보기와 느낌 일에 플레이 시험을 할지, 장시간 플레이의 재미 피로 판단: 게임 내용이다.
- 시험 환경 설치에 돈이나 비밀값이 드는 일, 외부 서비스 연결.
- 나머지는 총괄이 정한다.

## 판정과 남길 것
- 순서는 실패 > 못 봄 > 통과다. 실패와 못 봄이 같이 있으면 실패다. 경고만 있으면 통과(경고 있음 — 경고는 따로 적는다)다. 필수 증거 없는 로직 일은 실패다.
- 실패는 시험 실패 · 시간 초과 · 빌드 · 구문 오류 · 결과 파일 없음 · 시작 실패 · 손 확인 실패 · 누수 확인 · 안정성 깨짐이다. 못 봄은 실행기 없음 · 0건 · 한쪽 모드를 못 돌림 · 실행 안 한 필수 항목 · 증거 알 수 없음이다.
- 면제는 「해당 없음 — 이유」다. 통과로 세지 않는다. 증거 검토의 전체 판정은 가장 나쁜 일의 판정이다.
- 남길 기록: 시험 계획 · 스모크 보고(환경 · 자동 시험 줄 · 일별 증거 표 · 손 확인과 점검표 출처 · 판정) · 회귀 목록(시험 · 덮는 기준/버그 · 추가한 날 · 간극 · 격리) · 장시간 기록(시작 값 · 체크포인트 · 문제 표: 번호 · 등급 · 체크포인트 · 설명 · 판정, 못 간 체크포인트) · 불안정 보고(시험 · 실패율 · 확신도 · 원인 · 권하는 조치) · 증거 검토(일 · 종류 · 판정 · 지적).
- 짧은 장시간은 통과할 수 없다. 닿지 못한 체크포인트를 적고 못 봄이다. 단 그 안에서 본 충돌은 실패다. 계획서만 있고 실행하지 않았으면 못 봄이다.

## 하지 않는 것
- 설치 · 외부 연결을 시험 준비 안에 몰래 넣지 않는다. 확인하지 못한 API 이름을 기억에서 쓰지 않는다.
