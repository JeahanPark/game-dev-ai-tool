「느리다」는 인상을 빌드 · 장면 · 입력 · 기기 · 반복 횟수 · 예산 · 잰 값으로 바꿔, 병목 후보를 찾고 잰 뒤 고치고 같은 조건으로 다시 재는 절차다. 재기 전에 고치지 않는다. 코드를 읽어 찾은 것은 후보이고 잰 값만 사실이다.

## 언제 꺼내나
- 프레임 끊김 · 불러오기 지연 · 메모리 증가 · 발열 같은 증상이 보고됐을 때.
- 다듬기 단계에서 예산 대비 상태를 확인할 때, 단계 점검이 성능 증거를 요구할 때.
- 큰 시스템을 넣거나 바꾸기 전후로 회귀를 볼 때.
- 아직 만든 것이 없으면 꺼내지 않는다. 측정할 대상이 없다.

## 필요한 역할
- 성능 분석가(`performance-analyst`) — 조사를 이끌고 실측과 정적 추정을 따로 적는다.
- 엔진 프로그래머(`engine-programmer`) — 시스템 쪽 병목을 고친다.
- 테크니컬 아티스트(`technical-artist`) — 렌더링 · 셰이더 · 에셋 비용을 본다(렌더링이 없으면 부르지 않는다).
- 리드 프로그래머(`lead-programmer`) — 큰 구조 변경이 필요한 후보를 판단한다. QA 테스터(`qa-tester`)가 재현 절차를 같이 확인한다.

## 순서
1. 입력 확인. 총괄이 예산 · 측정 도구 · 재현 절차를 확인한다. 예산 항목: 목표 프레임률 또는 프레임 시간 · 그리기 호출 한도 · 메모리 한도 · 불러오기 시간 · (온라인이 있으면) 네트워크 한도. 프로젝트가 정한 값을 쓴다. 정한 값이 없는 항목은 「못 봄 — 예산 없음」이다. 틀에 미리 적힌 값(예: 60프레임)으로 재서 「여유 99%」 같은 말을 만들지 않는다. 예산이 없으면 통과도 없다. 측정 자료가 하나도 없으면 코드 읽기로 후보만 찾고 그 사실을 보고 맨 위에 적는다.
2. 조건을 고정한다. 한 번의 측정에는 빌드(판 · 설정) · 장면 · 입력(재현 절차) · 기기(목표 기기 우선, 개발 PC만으로 끝내지 않는다) · 반복 횟수 · 예산 · 잰 값 · 도구를 적는다. 한 번만 잰 값은 「한 번」이라고 적는다. 처음 값(기준선)을 이 조건으로 남긴다.
3. 후보를 찾는다(성능 분석가). 코드를 읽어 분야별로 훑는다.
   - 계산: 매 프레임 도는 함수 목록과 비용 짐작, 큰 모음 위의 중첩 반복, 뜨거운 길의 문자열 작업 · 새 할당, 정렬되지 않은 검색 · 정렬, 매 프레임 하는 무거운 물리 질의.
   - 메모리: 큰 자료 구조의 증가 방식, 질감 · 에셋 크기, 재사용 풀 대 만들고 지우기, 해제되지 않는 참조(누수), 캐시 크기와 비우기.
   - 렌더링(해당할 때): 그리기 호출 수, 투명물이 겹쳐 그려지는 정도, 셰이더 복잡도, 입자, 멀리 있는 것의 단순화 · 안 보이는 것 거르기가 빠졌는가.
   - 입출력: 저장/불러오기, 에셋 불러오기가 동기인가 비동기인가, 네트워크 메시지의 빈도 · 크기.
   각 후보에 위치(파일:줄)와 의심하는 이유를 적는다. 이것은 추정이다. 「현재 추정 값」을 예산 통과의 근거로 쓰지 않는다.
4. 잰다. 후보를 대상으로 실제 실행에서 측정한다. 5분을 넘기는 측정은 총괄이 배경 일로 띄우고, 끝나면 결과 파일 위치와 조건을 받는다. 잰 값이 후보를 뒷받침하지 못하면 그 후보는 접는다. 보고에는 잰 것(실측) 칸과 추정(정적) 칸을 따로 둔다.
5. 고칠 것을 정한다. 항목마다: 위치 · 기대 효과(추정이면 추정이라고 적는다) · 위험(낮음 · 보통 · 높음) · 방법 · 규모(작음 / 보통 / 큼). 작은 개선(시작 값의 예: 하나에 한 시간 안쪽)은 따로 모은다. 실제 측정이 더 필요한 곳은 「조사 필요」 칸에 둔다. 「더 빠르게」처럼 영향을 못 말하는 권고는 쓰지 않는다.
6. 규모가 보통 이상인 항목은 선택지를 둔다: 최적화를 구현한다 · 기능 범위를 줄인다 · 성능 손해를 받아들이고 다듬기 단계로 미룬다(알려진 문제로 기록) · 구조를 바꿔야 해서 구조 결정으로 올린다. 총괄이 정하되, 기능이나 규칙이 바뀌는 선택(범위 축소)은 게임 내용이라 사람이 정한다. 미룬 항목은 따로 모은다.
7. 고친다. 구현 역할에게 일 맡기기로 넘기고 범위와 끝 기준을 쓴다. 성능 분석가는 고치지 않는다.
8. 같은 조건으로 다시 잰다. 빌드를 빼고 모든 조건(장면 · 입력 · 기기 · 반복 횟수)이 처음과 같아야 한다. 전 · 후 값을 나란히 적는다. 고치고 나서 다른 항목이 나빠졌는지도 같은 방식으로 본다.
9. 보고서를 파일로 남긴다. 대화에만 두면 세션이 끝나면 사라지고 다음 조사와 견줄 수 없다. 못 봄으로 남은 칸은 파일에서도 지우지 않는다. 틈을 지운 성능 보고는 나중에 완전한 측정처럼 읽힌다.

## 맡길 때 적을 것
- 총괄은 필요한 틀 · 규칙 · 엔진 참조를 `gaf library take <칸>/<id>…`로 꺼내 맡기는 글에 경로를 적는다.
- 결과물 경로는 `--expect "<경로,…>"`로 약속한다(존재 · 비지 않음 · 이번 일의 변경만 확인하며 내용은 안 봄). 검사 수단을 만들면 총괄이 `gaf check add "<이름>" "<명령>" [--when "<글롭,…>"] --why "<막을 실수>"`로 청해 사람의 화면 승인을 받는다. 이후 바뀐 파일에 맞는 기본 검사는 지휘자가 돌린다.
- 결과의 `[지휘자 확인]`에서 실패는 고치고 못 봄은 통과로 적지 않는다.
- 증상 또는 점검 목적, 범위(시스템 하나 · 전체), 대상 장면과 입력, 목표 기기, 예산(값과 출처), 측정 도구, 이미 한 측정과 그 결과.
- 읽을 파일: 관련 코드 · 이전 성능 보고 · 예산이 적힌 문서. 결과물과 둘 곳: 성능 보고 파일 하나(프로젝트가 정한 곳).
- 끝 기준: 잰 값이 조건과 함께 적혀 있고, 고침이 있으면 전 · 후 값이 같은 조건이다.
- `--check`로 줄 수 있는 것: 측정 스크립트가 통과/실패(예산 초과)를 종료 코드로 내면 그 명령.
- 5분을 넘는 측정은 배경 일로 띄우도록 총괄이 따로 적는다.

## 사람이 정할 것
- 성능을 위해 기능 · 규칙 · 보이는 모습을 줄이는 결정(게임 내용).
- 목표 기기나 장비를 사거나 빌리는 일, 외부 서비스 비용.
- 나머지는 총괄이 정하고 결과만 알린다.

## 판정과 남길 것
- 예산 항목마다 판정: 통과(잰 값이 예산 안) · 실패(잰 값이 예산을 넘음) · 못 봄(예산 없음, 측정 없음, 목표 기기에서 못 잼) · 해당 없음(그 항목이 이 게임에 없음. 예: 온라인이 없는 게임의 네트워크 한도). 전체는 실패 > 못 봄 > 통과.
- 강제 수준은 프로젝트가 정한다: 경고(초과는 발견 사항이고 막지 않는다. 기본) · 막음(초과는 출시를 막는 막힘) · 끔(예산은 참고, 잰 값은 적되 초과를 지적하지 않는다). 알 수 없는 값이면 경고로 두고 알린다. 막음이면 보고에 그렇게 적는다.
- 남길 기록: 조건 표(빌드 · 장면 · 입력 · 기기 · 반복 횟수 · 도구) · 예산 대비 표(예산 · 실측 · 정적 추정 · 판정) · 병목 후보 표(위치 · 문제 · 영향 · 규모) · 우선순위 목록 · 작은 개선 · 조사 필요 · 미룬 항목 · 전 · 후 값. 요약에는 상위 세 병목과 예산별 여유를 쓴다. 예산이 없는 항목은 「예산 없음 — 여유를 못 봄」으로 쓴다.
- 코드 읽기(정적 분석)는 후보를 찾고, 실행 측정이 확인한다. 정적 추정만 있으면 판정은 못 봄이다.

## 하지 않는 것
- 재기 전에 고치지 않는다. 느낌과 직감으로 병목을 단정하지 않는다.
- 개발 PC에서 잰 값을 목표 기기의 통과로 쓰지 않는다.
- 예산이 없는데 틀에 있는 값으로 통과를 만들지 않는다.
- 다른 조건에서 잰 값으로 개선을 주장하지 않는다. 고친 뒤 재측정을 건너뛰지 않는다.
- 추정을 실측처럼 보고하지 않고, 보고서에서 못 봄 칸을 지우지 않는다.
