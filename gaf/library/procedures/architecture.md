코드를 쓰기 전에 구조의 뼈대와 기술 결정을 글로 남기고, 기획의 요구가 빠짐없이 결정 · 맡긴 일 · 검사 증거로 이어지는지 본다. 결정이 안 정해진 채 일이 풀려 나가는 것과, 엔진 판을 모르고 짠 구조가 뒤에서 무너지는 것을 막는다.

## 언제 꺼내나
- 구현을 맡기기 전에 구조 문서가 없거나 낡았을 때(구조 설계).
- 기술 결정 하나를 정해야 할 때, 또는 있는 결정 글에 빠진 절이 있을 때(결정 기록).
- 결정이 쌓였거나 기획이 바뀐 뒤 빠진 요구 · 충돌 · 순환을 찾을 때(구조 검토).
- 구현을 맡기기 직전, 채택된 결정에서 그 일에 필요한 규칙만 뽑아 붙일 때(규칙 추리기).
- 작은 프로젝트는 계층 지도 · 꼭 필요한 결정 목록만 만들어도 된다. 깊이는 총괄이 고른다.

## 필요한 역할
- 리드 프로그래머(`lead-programmer`) — 구조 문서와 결정 글 작성. 검토는 별도 프로그래머.
- 테크니컬 디렉터(`technical-director`) — 구조 전체의 일관성을 검토하고 판정과 근거를 보고한다. 사람의 승인을 대신하지 않는다.
- 엔진 전문가(프로젝트의 엔진 것) — 결정이 엔진 판에 맞는지 본다. 없으면 리드 프로그래머가 겸한다(겸했다고 보고에 적는다).
- 게임 디자이너(`game-designer`) — 구조 때문에 기획을 고쳐야 할 때 기획 문서를 맞춘다.
- QA 리드(`qa-lead`) — 검토에서 요구가 검사 증거로 이어지는지 본다(선택).

## 순서
### 가. 구조 설계
1. 입력 점검(총괄). 엔진 이름 · 판 · 지식 기준일 · 위험 등급, 판 사이 바뀐 것, 쓰지 말 API, 모범 방식을 읽는다. 모듈 자료는 이 게임이 쓰는 분야만 읽되, 분야가 애매하면 읽는다. 엔진이 안 정해졌거나 한 장 기획 · 시스템 목록이 없거나 빈 틀이면 멈추고 그 입력부터 맡긴다. 일부만 읽고 나중에 적지 않는다.
2. 요구 기준선(리드 프로그래머). 기획 문서를 센다(N). 규칙 · 수식 · 의존 · 조절값 · 수용 기준 절에서 자료 구조 · 성능 · 엔진 기능 · 시스템 간 통신 · 저장할 상태 · 스레드와 시점 요구를 뽑는다. 절이 하나도 안 잡힌 기획은 틀 이전 글이다 — 통째로 읽고, 요구가 없다고 넘기지 않는다. 요구마다 번호를 붙인다. 이미 쓰는 번호는 그대로 두고, 새 요구는 폐기된 번호까지 포함해 다음 빈 번호를 쓴다. 확정 전 번호는 「임시」로 표시한다. 결과물: 요구 표(번호 · 기획 · 시스템 · 요구 · 분야).
3. 엔진 지식 공백 목록. 분야별 위험(높음 · 중간 · 낮음)과 그 분야를 쓰는 시스템을 표로 정리한다. 높음 분야의 권고는 엔진 참조와 맞춰 보기 전에 결정하지 않는다.
4. 계층 · 소유 · 흐름 · 경계. 시스템을 계층(표현 · 기능 · 핵심 · 기반)에 놓는다. 이 네 겹은 시작 값의 예다. 플랫폼은 엔진 · OS라 코드가 아니다 — 플랫폼을 감싸는 시스템은 기반에 둔다. 모듈마다 소유(혼자 맡는 자료 · 상태) · 공개 · 소비 · 직접 부르는 엔진 API(판 · 위험 · 확인 근거)를 쓴다. 한 상태의 주인은 하나다. 데이터 흐름은 프레임 · 이벤트 · 저장과 불러오기 · 시작 순서를 쓰고, 흐름마다 자료 이름 · 보내는 쪽 · 받는 쪽 · 직접 호출 / 이벤트 / 공유 상태 · 스레드 경계를 적는다. API 경계는 진입점 · 호출자가 지킬 것 · 모듈이 보장할 것을 프로젝트의 언어로 쓴다. 엔진 타입이 나오면 그 판에 있고 바뀌지 않았는지 확인한다.
5. 기존 결정 점검. 결정 글의 요약 · 상태 · 분야를 훑는다. 결정마다 엔진 호환 칸 · 판 · 후속 판 API 표시 · 기획 요구 연결이 있는지, 이번 구조와 부딪히는지, 지금 판에서 유효한지 본다. 요구마다 덮는 결정을 짝짓는다. **채택된 결정만 「덮임」이다.** 제안 상태에만 덮이면 「덮임(제안)」이고 통과가 아니다.
6. 필요한 새 결정 목록. 구조에서 정했는데 결정 글이 없는 것과 덮이지 않은 요구를 모은다. 우선순위는 실제 의존과 위험으로 고른다. 코드 전에 필요한 것 · 해당 시스템을 만들기 전에 필요한 것 · 구현 중에 미뤄도 되는 것으로 가른다.
7. 구조 문서 쓰기. 상태(판 · 날짜 · 엔진 · 다룬 기획 · 참조한 결정 · 두 검토 판정) · 엔진 지식 공백 요약 · 계층 지도 · 모듈 소유 · 데이터 흐름 · API 경계 · 결정 점검 · 필요한 결정 · 구조 원칙 3~5개(시작 값의 예) · 열린 질문. 구조 문서가 이미 있으면 덮어쓰지 않는다 — 고칠 절만 바꾸고 판을 올린다. 총괄이 정한다.
8. 두 검토. 총괄이 보통 `gaf assign`으로 테크니컬 디렉터에게 일관성 · 요구 기준선을, 쓴 역할이 아닌 프로그래머에게 구현 가능성을 맡긴다. 다른 프로그래머가 없으면 총괄이 작성 역할을 `gaf role reset <이름>`한 뒤 맡긴다. 각자 판정 · 근거를 보고한다. 실패는 수정, 못 봄은 입력을 채워 재검토하고 모두 통과해야 인계한다.
9. 인계. 구조 문서 경로 · 두 판정 · 남은 결정(맨 위 셋) · 막힌 것 · 열린 질문.

### 나. 결정 기록(ADR)
1. 엔진부터. 결정의 분야를 잡고 엔진 판 · 해당 분야 모듈 · 바뀐 것 · 쓰지 말 API를 읽는다. 위험이 중간 이상이면 「엔진 지식 공백 경고」(판 · 분야 · 확인된 변화)를 맡기는 글에 적는다. 훈련 기억만 믿지 않는다.
2. 번호. 결정 글 폴더를 모두 훑는다(하위 폴더 · 이름이 틀린 파일까지 — 놓치면 번호가 겹친다). 번호는 총괄이 한 곳에서 발급해 맡기는 글에 적는다. 역할 둘이 같은 번호를 잡지 않게 한다.
3. 기존 입장 먼저. 결정 등록부(상태 소유 · 인터페이스 계약 · 금지 패턴 · 성능 예산)를 먼저 읽고, 등록부 요약이 낡았다 싶으면 원 결정 글까지 따라간다. 새 결정이 기존 입장과 부딪히면 초안 전에 푼다 — 기존 입장에 맞춘다 / 명시적으로 대체한다 / 예외 사유를 쓴다.
4. 가정 확인(총괄). 문제 · 대안 2~3개 · 의존 · 기획 연결 · 상태를 먼저 적는다. 상태는 늘 「제안」이다. 의존을 못 가렸으면 「없음」이 아니라 「모름」으로 적고 확인될 때까지 푼다. 「모름」은 파일에 쓰지 않는다.
5. 초안. 칸: 상태 · 날짜 · 마지막 확인일 · 결정한 이 · 요약(2문장) · 엔진 호환 표(엔진 · 분야 · 계층 · 지식 위험 · 참조한 자료 · 후속 API · 확인할 것) · 의존 표(먼저 채택돼야 할 것 · 열어 주는 것 · 막는 것 · 순서 메모) · 맥락(문제 · 제약 · 요구) · 결정(그림 · 핵심 인터페이스 · 구현 지침을 「해야 한다 / 하면 안 된다」로) · 대안(설명 · 장점 · 단점 · 탈락 이유) · 결과 · 위험 · 기획 요구 대응 표 · 성능 영향 · 이행 계획 · 검증 방법 · 관련. 계층 칸은 구조 문서의 지도에서 잡는다. 지도에 없으면 총괄이 정한다. 일을 맡은 묶음에서 따오지 않고 분야 값을 재활용하지 않는다. 쓰지 말 API는 결정과 인터페이스에 넣지 않는다.
6. 검증. 엔진 전문가: 이 판에서 관용적인가 · 바뀐 API · 빠뜨린 위험. 막는 문제면 결정을 고치고, 작은 지적은 위험 절에 넣는다. 테크니컬 디렉터: 구조 전체와 어울리는가(판정과 근거 — 실패면 결정 · 대안 절을 고친다). 엔진 미정이면 「엔진 검증: 못 봄 — 엔진 안 정함」을 결과에 적는다. 조용히 건너뛰지 않는다.
7. 기획 이름 맞춤. 결정이 기획의 신호 · 메서드 · 자료형 이름을 바꿨는지 센다. 세 결과 중 하나를 적는다 — 있음(옛 이름 → 새 이름 경고 블록) · 없음(「기획 N개 확인, 이름 불일치 없음」 한 줄) · 못 봄(기획 연결 절이 없거나 기획이 없다). 기획 문서를 고치는 일은 게임 디자이너에게 따로 맡긴다.
8. 등록부 갱신. 새 상태 소유 · 계약 · 예산 · 명시한 API 선택 · 금지 패턴 후보를 뽑는다. 기존 항목은 고치지 않고 「대체됨」을 표시하고 새 항목을 더한다. 갱신 뒤 형식 · 중복 · 상태를 확인하는 명령이 있으면 돌리고, 없으면 「검사 못 돌림」을 적는다.
9. **제안 상태에서는 막힌 일을 풀지 않는다.** 이 결정을 기다리는 일 목록을 보고에 적는다.

### 다. 결정 채택과 보강
- 채택(총괄 + 테크니컬 디렉터 검토). 파일이 하나로 특정되고 상태 절이 있는지 본다. 이미 채택됐거나 폐기 · 대체된 것은 되살리지 않는다 — 새 결정으로 쓴다. **의존 절이 없거나 비었거나 「모름」이면 채택하지 않는다**(빈 칸이 「없음」으로 읽히는 헛통과다). 의존이 채택되지 않았으면 그것부터. 채택하면 상태만 바꾸고 날짜는 건드리지 않는다(다시 쓰면 이 결정을 따라 쓴 일이 모두 낡아 보인다). 그다음 이 결정 번호가 막힌 까닭으로 적힌 일만 준비로 옮긴다.
- 보강. 빠진 절(상태 · 의존 · 엔진 호환 · 기획 연결 · 날짜)만 더한다. 칸이 있어도 비어 있으면 빠진 것으로 본다. 기존 본문은 고치지 않는다. 날짜를 새로 더하면 보강일이지 결정일이 아니라고 적는다. 「이미 채택」이라는 답도 「제안」으로 쓰고 채택 절차를 거친다.

### 라. 구조 검토(처음 보는 세션)
1. 이전 보고 재사용. 입력(결정 · 기획 · 요구 목록 · 구조 문서 · 엔진 참조 · 설정)이 하나라도 바뀌었거나 못 읽었거나 범위(전체 · 한 기획)가 다르면 재사용하지 않는다. 한 종류 문서가 통째로 없으면 그 종류를 안 본 것이다. 보고서에 입력 목록과 읽은 날을 적는다.
2. 분모. 기획 N · 결정 M을 센다. 절은 끝까지 읽는다. 결정 M > 0인데 읽을 절이 하나도 안 잡히면 구조가 없는 것이 아니라 형식 불량이다 — 각 결정에 보강을 맡긴다.
3. 요구 번호. 같은 뜻이면 번호를 지키고 문구만 갱신한다(고친 날 표시). 임시 번호는 확정한다. 폐기된 요구는 건너뛴다. 애매하면 총괄이 게임 디자이너에게 같은 요구인지 묻는다.
4. 추적표. 요구마다 상태: 덮임(채택) · 덮임(제안) · 일부 · 빈틈 · 못 봄(결정을 못 읽음 · 상태 없음). 필요하면 요구 → 결정 → 맡긴 일 → 시험으로 늘리고 시험 칸은 있음 / 실행함 / 통과를 따로 적는다. 시험 파일이 있다는 것은 통과가 아니다.
5. 충돌. 결정을 서로 견준다 — 자료 소유 · 인터페이스 가정 · 성능 예산 합(프레임 예산 초과) · 초기화 순서 순환 · 소통 방식(이벤트 대 직접 호출) · 상태 권한. 충돌마다 종류 · 양쪽 주장 · 깨지는 것 · 풀 방법 둘을 쓴다.
6. 의존 순서. 「먼저 채택돼야 할 것」 목록으로 순서와 고리를 찾는다. 눈으로 따라가기 어려우면 목록을 계산하는 확인 명령을 맡긴다. 의존 칸이 없거나 안 채워진 결정은 「없음」이 아니라 「모름」이다. 아직 제안이거나 없는 결정에 기대는 결정은 표시한다. 순환과 순환을 기다리는 결정은 따로 적는다.
7. 엔진 교차. 판이 서로 맞는지 · 같은 후속 API를 모순되게 가정하는지 · 쓰지 말 API를 쓰는지 · 엔진 호환 절이 빠졌는지(눈먼 점). 엔진 전문가 눈으로 한 번 더 본다 — 잘못된 노드 · 매 프레임 일 · 이름으로 찾기 · 풀링 없음 같은 반례를 점검 질문으로 쓰되 의무로 박지 않고 규모와 실측으로 고른다. API 주장은 엔진 참조에서만 하고, 참조에 없으면 「확인 못 함」으로 표시한다.
8. 기획 되먹임. 높은 위험의 엔진 발견이 기획의 가정과 부딪히면 표로 적는다(기획 · 가정 · 실제와 출처 · 할 일). 기획 상태 변경은 게임 디자이너에게 맡긴다.
9. 구조 문서 범위. 모든 시스템이 계층에 있는지 · 데이터 흐름이 기획의 시스템 간 통신을 덮는지 · 경계가 통합 요구를 받치는지 · 기획 없는 구조가 있는지. 문서가 없으면 「못 봄」이다(필요 없는 문서면 「해당 없음」).
10. 보고서(칸은 아래). 쓸 때는 다른 시스템의 행과 요구 번호를 남기고 지우거나 다시 매기지 않는다. 쓰기 직전 최신 파일을 다시 읽는다. 부분 검토에서는 읽지 않은 시스템의 요구를 폐기 제안하지 않는다.

### 마. 규칙 추리기
1. 분모. 결정 수 · 채택 수 · 제안 · 폐기 · 대체 · 상태 없음을 센다. 채택이 0이면 빈 목록을 조용히 쓰지 않고 멈춰 보고한다. 모두 상태 없음이면 형식 불량이다. 규칙집에 빠진 결정은 상태와 함께 적는다.
2. 읽을 절은 결정 · 대안 · 성능 영향 · 엔진 호환이다(맥락 · 결과 · 검증은 이유라 규칙이 아니다).
3. 뽑기. 해야 하는 방식(「해야 한다 · 반드시 · 항상」과 구현 지침 전부) · 하면 안 되는 방식(명시된 금지 · 이름 붙은 안티패턴 — 탈락한 대안 전부를 영구 금지로 만들지 않는다. 이 결정 범위에서만 탈락한 것은 구분한다) · 성능 한도 · 엔진 API 제약. 규칙은 그 시스템의 계층에 놓고, 계층에 걸치면 각각에 놓는다. 이름 짓기 · 성능 예산 · 쓰지 말 API(이 프로젝트가 만드는 것에 해당하는 것만 — 3D 전용 행을 2D에 베끼지 않고, 모르면 조건을 붙이거나 「미정」에 둔다) · 쓰도록 정한 라이브러리 · 모범 방식의 필수 패턴 · 기술 선호의 금지 패턴(적힌 그대로)은 전체 규칙이다.
4. 모든 규칙에 출처(결정 번호 · 설정 이름 · 엔진 참조 파일)를 단다. 뜻을 바꾸는 풀어쓰기와 지어낸 규칙은 없다. 규칙 묶음의 버전은 날짜만 쓰지 않고, 반영한 결정 번호와 각 결정의 채택일 · 마지막 확인일을 함께 적는다.
5. 테크니컬 디렉터 검토. 필수 패턴이 빠짐없고 정확한지 · 금지가 출처에 맞는지 · 출처 없는 규칙이 없는지 · 한도가 결정과 맞는지. 실패면 쓰지 않고 고쳐 다시 보인다.
6. 붙이기(총괄). 일을 맡기기 직전, 그 일이 건드리는 시스템과 계층의 규칙만 맡기는 글에 붙인다. 규칙이 바뀌면 이미 일하는 역할에게 새 금지 규칙부터 알린다.

## 맡길 때 적을 것
- 총괄이 `gaf library take <칸>/<id>…`로 꺼낸 틀 · 규칙 · 엔진 참조의 경로를 준다.
- `--expect`에 결과물 경로를 적는다(존재 · 비지 않음 · 이번 변경 확인, 내용은 별도). 검사 수단을 만들면 총괄이 `gaf check add`로 청해 사람이 화면 승인한다(`project-start`의 명령 꼴). `[지휘자 확인]`의 못 봄은 통과가 아니다.
- 갈래별 입력과 필요한 대목 · 결과물 경로 · 아래 판정 기준을 준다. 못 본 범위와 엔진 검증 여부를 보고한다.
- `--check`: 결정의 필수 절 · 의존 순환 · 등록부 형식.
- 구조 · 결정 검토는 보통 `gaf assign`으로 판정 넷 · 지적 보고 파일을 받는다.

## 사람이 정할 것
- 큰 비용이거나 되돌리기 어려운 기술 결정(엔진 · 유료 도구와 서비스 · 나중에 못 바꾸는 저장 형식)만 올린다. 보기 1~2개, 권하는 쪽을 먼저.
- 엔진 한계로 기획의 규칙 · 그림 · 이야기를 바꿔야 할 때(게임 내용).
- 그 밖의 기술 결정과 결정 채택은 총괄이 정하고 결과로 알린다.

## 판정과 남길 것
- 구조 검토 판정은 통과 · 실패 · 못 봄 중 하나다. 통과: 모든 요구가 채택된 결정에 덮이고 충돌 · 엔진 불일치가 없고 못 본 범위가 없다. 실패(막음): 기반 · 핵심 요구가 안 덮임 · 막는 충돌 · 순환. 실패(막지 않음): 일부 덮임 · 제안 상태에만 덮임 · 기획 수정 필요. 못 봄: 결정이 없거나 못 읽음 · 요구의 출처 없음 · 결정에 상태 없음 · 구조 문서 없음 · 엔진 안 정함(전체 검토에서 이 항목 하나라도 있으면 통과가 아니다). 약속한 파일이 없으면 실패다.
- 남길 것: 보고서(날짜 · 범위 · 엔진 · 기획 수 · 결정 수 · 입력 목록) · 추적표(요구 번호 · 기획 · 시스템 · 요구 · 결정 · 상태) · 충돌 목록 · 엔진 감사 · 기획 수정 필요 표 · 필요한 결정(기반 먼저) · 의존 순서. 충돌만 교훈 기록에 더하고 빈틈은 더하지 않는다.
- 결정 글의 상태: 제안 · 채택 · 폐기 · 대체됨(번호).

## 하지 않는 것
- 제안 상태의 결정으로 규칙집을 만들거나 막힌 일을 풀지 않는다.
- 엔진을 모르는 채 구조를 짜거나, 요구 번호를 다시 매기거나 폐기 번호를 재사용하지 않는다.
- 규칙을 지어내거나 탈락 대안을 전부 금지로 옮기지 않는다.
- 기술 역할이 기획 문서를 직접 고치지 않는다.
