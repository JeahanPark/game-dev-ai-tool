처음 맡은 프로젝트를 새 프로젝트처럼 다루다가 있는 것을 덮어쓰거나, 검사 수단 없이 역할만 늘려 서로의 땜질을 베끼게 되는 일을 막는다. 총괄이 현황을 눈으로 확인하고, 필요한 역할만 꺼내 첫 일을 작게 나눠 맡기는 순서다.

## 언제 꺼내나
- 프로젝트를 처음 맡았을 때, 또는 다른 사람 · 다른 세션이 하던 일을 넘겨받았을 때.
- 사람이 「어디서부터 하지」 · 「다음에 뭘 하지」 라고 하거나, 일이 막혀 방향을 잃었을 때.
- 기획 문서가 없다는 이유로 새 프로젝트로 판단하기 전에. 문서가 없는 것과 만든 게 없는 것은 다르다.

## 필요한 역할
- 프로듀서(`producer`) — 있는 문서 · 남은 일 · 사람의 목표를 모아 현황표로 정리한다. (없으면 현황표를 쓸 역할을 총괄이 따로 만든다)
- 리드 프로그래머(`lead-programmer`) — 코드 · 빌드 · 시험의 상태를 읽는다.
- QA 리드(`qa-lead`) — 검사 수단이 있는지 보고, 없으면 만드는 일을 맡는다.
- 엔진 전문가(프로젝트의 엔진 것만 — 예: `unity-specialist`) — 엔진과 설치된 판을 확인하고 엔진 쪽 규칙을 알려 준다.
- 게임 디자이너(`game-designer`) — 기존 기획 문서가 있을 때 읽고 요약한다.
- 그 밖의 역할은 첫 일이 정해진 뒤 필요한 것만 꺼낸다(`role new --from <id>`).

## 순서
### 1. 있는 것을 먼저 본다
읽기만 하는 일이다. 프로듀서와 리드 프로그래머에게 나눠 맡기고, 아래 표를 채워 오게 한다. 칸마다 「찾은 값(근거 파일)」 · 「못 봄(이유)」 · 「해당 없음」 중 하나를 쓴다. 추측은 칸에 쓰지 않는다.

| 항목 | 볼 곳 | 못 보면 |
|---|---|---|
| 엔진과 설치된 판 | 프로젝트 파일(엔진이 남기는 설정) · 엔진 실행 파일의 판 | 「설치된 판 확인 못 함」. 「설치 안 됨」이라고 쓰지 않는다 |
| 언어 · 장르 · 대상 기기 | 설정 · 기획 문서 · 코드 | 못 봄 |
| 기존 기획 문서 · 구조 결정 기록 | 문서 폴더 | 「없음」은 찾아본 곳과 같이 적는다 |
| 코드 | 코드 뿌리(엔진마다 다르다) | 뿌리를 못 찾았으면 「못 봄 — 코드 뿌리 못 찾음」. 「소스 0개」라고 쓰지 않는다 |
| 시험 · 빌드 · 검증 스크립트 | 시험 폴더 · 빌드 설정 · 스크립트 | 못 봄 |
| 시제품 · 실험 | 시제품 폴더 | 폴더마다 설명 글이 있는지 · 쓰는 중인지 버린 것인지를 적는다 |
| 남은 일 · 일 추적 | 작업 기록 · 인계 글 · 다른 도구에서 관리 중인지 | 다른 곳에서 관리할 수 있다. 「없음」으로 단정하지 않는다 |
| 사람의 목표 | 사람이 한 말 그대로 | 말에 없으면 「정해지지 않음」 |

판정 규칙:
- 문서가 없다고 새 프로젝트로 보지 않는다. 코드는 있는데 기획 문서가 없으면 「코드 먼저 만든 프로젝트」다.
- 단계 이름은 `gate-check` 절차를 따른다(개념 · 기획 · 기술 준비 · 사전 제작 · 제작 · 다듬기 · 출시). 단계는 개념 문서 · 시스템 목록 · 엔진 설정 · 구조 결정 기록 같은 실물로 가른다. 다듬기 · 출시는 단계 점검을 넘겨 기록된 때만 쓴다. 파일 개수로 단계를 추측하지 않는다. 개수는 현황값일 뿐 완성도나 시험 범위의 근거가 아니다. 퍼센트를 쓰려면 분모와 재는 방법을 같이 적는다.
- 단계가 이미 기록돼 있어도 실물을 따로 보고 둘 다 적는다. 기록을 읽어 되풀이하는 것은 판정이 아니다. 둘이 어긋나면 어긋난다고 쓴다. 기록이 낡았거나 일이 다른 곳에 있을 수 있다.
- 단계 판정의 차례(먼저 걸리는 것): 막는 빈 곳이 있거나, 기록과 실물이 어긋나거나, 신호가 두 단계에 걸치면 실패(이유) → 단계를 가르는 확인이 하나라도 못 돌았으면 못 봄(무엇이 안 돌았나) → 아니면 통과. 못 봄 뒤에 알려진 문제를 숨기지 않는다.
- 빈 곳 목록은 까닭을 말해 주지 않는다. 빈 곳마다 생각할 수 있는 까닭(먼저 만들고 문서를 안 썼다 · 다른 곳에서 관리한다)을 같이 적는다.
- 무엇을 빈 곳으로 볼지는 프로젝트 규모와 사람의 목표에 맞춘다. 한 장 기획과 엔진만 있는 작은 프로젝트에서 시스템 기획서 · 구조 결정 기록 · 일 계획이 없는 것은 빈 곳이 아니다. 다음 일은 코드다.
- 사람의 목표는 사람 말에서만 가져온다. 말에서 읽은 것은 「추측」 표시를 붙인다(예: 「기간이 정해진 대회」 · 「배우려고」 · 「포트폴리오」 · 「판매」 · 「얼리 액세스」 · 「퍼블리셔 제안」 · 「모바일」 · 「취미」). 둘이 맞으면 판매 쪽을 앞세우고, 얼리 액세스 · 퍼블리셔 제안은 판매보다 앞세운다.

### 2. 검사 수단이 있는지 본다 (이 틀에서 더한 단계)
시험 · 빌드 · 검증 스크립트가 종료 코드로 통과/실패를 내는지 본다. 역할 여럿이 검사 없이 일하면 서로의 땜질을 베낀다.
- 있다: 어떤 명령이 무엇을 보는지 한 줄씩 적는다. 실제로 한 번 돌려 보고 결과를 적는다. 돌려 보지 못하면 「못 봄」이다.
- 없다 · 돌지 않는다: 역할을 늘리기 전에 그것을 만드는 일을 QA 리드에게 첫 일로 맡긴다. 끝 기준은 「명령 하나가 종료 코드 0이면 통과, 아니면 실패」다.
- 검사 수단이 준비되면 총괄이 아래 `gaf check add`로 기본 검사를 청한다. 사람이 화면에서 승인하면 이후 모든 일에서 바뀐 파일에 맞춰 지휘자가 돌린다. 일별 `--check`가 실패하면 출력 끝을 역할에게 돌려보내 고치게 한다(기본 3번).
- 시험 파일이 있다는 것과 시험이 통과했다는 것은 다른 증거다. 둘을 따로 적는다.

### 3. 필요한 역할만 꺼낸다
- 현황표와 검사 수단을 보고, 첫 일에 필요한 역할만 꺼낸다. 이름이 있는 역할을 다 늘리지 않는다.
- 엔진 전문가는 그 프로젝트의 엔진 것만 꺼낸다.
- 새 역할이 읽을 안내 글(역할 안내)을 맡기는 글에 넣거나 파일로 둔다. 역할은 서로의 대화를 못 본다. 안내 글 칸: 프로젝트 요약(2~3문장) · 이 역할이 할 일 · 이 역할에 걸리는 구조 · 주요 폴더와 파일(목적 · 읽을 차례) · 따를 규칙 · 지금 상태(찾은 것을 파일 이름으로, 없으면 「없음」) · 지금 진행 중인 일 · 함께 일하는 역할과 시스템 · 자주 걸리는 곳 · 첫 일 · 총괄에게 확인할 것.
- 약속했거나 규칙이 만들라고 한 산출물이 없다 = 실패. 검토하는 쪽이 판정에 필요한 입력을 받지 못했다 = 못 봄. 지어 채우지 않는다. 입력을 전부 못 받았으면 안내 글 대신 「못 봄」을 보고한다.

### 4. 엔진이 정해지지 않았거나 판이 문제일 때
엔진은 이미 있는 것을 쓴다. 프로젝트에 엔진 파일이 있거나 사람이 엔진을 말했으면 그 엔진이다. 다른 엔진을 권하지 않는다.
- 엔진이 없고 사람이 말도 안 했으면, 먼저 사람이 게임을 만들어 본 엔진을 본다. 하나가 있으면 그것을 권한다. 써 본 경험은 다른 무엇보다 앞선다. 없거나 여럿이면 대상 기기 → 만들 게임의 종류(2D · 3D) → 주 입력 → 팀 규모와 경험 → 쓰고 싶은 언어 → 라이선스 예산 순으로 확인한다. 경험 다음에는 대상 기기가 가장 먼저 후보를 거른다. 점수표로 엔진을 탈락시키지 않는다. 사람의 조건을 줄로 둔 비교표를 만들고, 1~2개를 장단과 함께 권한다(첫째 권장 · 그 대신 고를 때). 엔진 고르기는 사람이 정한다(아래 「사람이 정할 것」).
- 엔진 가격 · 라이선스 · 수수료는 지금 값을 확인한 뒤에만 쓴다. 확인 못 하면 「지금 값 못 확인」이라고 쓴다. 「라이선스가 열려 있으니 만든 것 전부가 내 것」 같은 말은 쓰지 않는다.
- 판을 고를 때 목표 판 · 설치된 판 · 프로젝트가 이행된 상태를 따로 적는다. 고른 판과 설치된 판이 다르면 둘 다 적고 말없이 하나를 고르지 않는다. 설정과 참조 글만 바꿨다고 「엔진 준비 끝」이라고 하지 않는다.
- 고른 판이 모델이 아는 범위보다 새로울 수 있다. 그때 엔진 참조 글은 공식 문서에서 읽은 것만 근거로 쓰고 쪽 주소를 적는다. 공식 문서에 없는 것은 「근거 못 찾음 — 무엇」이라고 적는다. 훈련 기억으로 채우지 않는다. 문서를 읽을 수 없으면 「못 봄」이다.
- 판을 올리는 일은 먼저 읽기만 한다. 공식 이행 안내에서 이름이 바뀐 · 없어진 API와 바뀐 기본값 · 동작을 뽑고, 코드에서 그것을 쓰는 곳을 파일 · 줄 · 찾은 API · 품으로 표를 만든다. 옮기는 차례는 의존이 적은 것부터다. 없으면 「쓰는 곳 못 찾음」이지 안전하다는 뜻이 아니다. 그 API · 엔진 기능에 기대는 구조 결정 기록은 다시 검토할 목록에 넣는다. 실제 올리기는 사람이 정한다.
- 엔진 · 도구를 설치하거나 내려받는 일은 이 절차에서 하지 않는다. 사람의 동의가 필요하다. 필요하면 무엇을 왜 설치해야 하는지 사람에게 알린다.

### 5. 이미 있는 문서가 쓸 수 있는 꼴인지 본다
문서가 「있다」와 「쓸 수 있다」는 다르다. 서랍의 문서 틀과 꼴이 다르면 역할이 읽을 때 조용히 틀린 결과를 낼 수 있다. 이 점검은 차이를 목록으로 만들 뿐이다. 꼴만 다른 문서를 「없음」으로 적지 않는다. 있는 문서를 다시 만들게 된다.
- 기존 문서의 내용은 고치지 않는다. 진행 중인 일은 다시 만들지 않는다.
- 차이를 심각도로 나눈다: 막는 것(역할이 틀린 결과를 조용히 내는 것) · 높음(안전 점검이 빠져 일을 맡기기 위험한 것) · 중간(품질이 떨어지지만 돌아가는 것) · 낮음(있으면 좋은 것).
- 고치는 차례: 막는 것 → 높음(틀 · 설정 같은 바탕을 문서 내용보다 먼저) → 중간(기획 문서 → 구조 결정 기록 → 일 문서. 일 문서가 앞의 둘을 바탕으로 쓰인다) → 낮음.
- 차이마다 한 문장 설명(전문 용어 없이) · 고치는 방법 · 확인 칸을 둔다. 보고에는 막는 것을 하나씩 적고, 나머지는 심각도별 개수로 적는다.
- 문서가 엉뚱한 곳에 있으면 찾기만 한다. 옮기는 것은 사람의 문서를 건드리는 일이니 목록으로 보고한다.
- 막는 것과 높음이 0개면 「쓸 수 있다」, 나머지는 선택 사항으로 보고한다. 점검을 못 돌린 문서는 「못 봄」이다. 통과가 아니다.

### 6. 첫 일을 작게 나눠 맡긴다
- 다음 일은 한 가지만 정한다. 사람에게 여섯 가지를 던지지 않는다.
- 순서의 기준: 검사 수단이 없으면 그것부터. 그다음 검토 대기(일은 끝났고 닫기만 남은 것) → 진행 중 → 아직 안 한 일 순이다. 「진행 중」은 끝난 것이 아니다. 사람이나 기록이 구현이 끝났다고 할 때만 마무리 검토로 보낸다.
- 막힌 일은 막힌 이유와 함께 이름을 적되 다음 일로 고르지 않는다. 검토 대기 · 진행 중 · 안 한 일이 하나도 없고 막힌 일 · 상태가 없는 일만 남았으면 「끝났다」가 아니다. 그 가운데 첫째의 막힌 이유를 푸는 것(상태가 없으면 상태를 적는 것)이 다음 일이다.
- 확인할 수 없는 단계는 「못 봄(무엇을 못 봤나)」이다. 끝났다고도 안 끝났다고도 쓰지 않는다. 여러 번 하는 일(시스템마다 기획서 등)은 하나가 있다고 끝난 것이 아니다. 사람이 「끝냈다」고 했으면 그 말대로 넘어가되 근거를 적는다.
- 기획 문서만 있고 해 볼 것이 없으면 첫 일은 「가장 작게 만들어 사람이 해 보기」다(`prototype` 절차). 기획 문서가 원본으로 남고, 시제품에 쓰는 요약은 요약일 뿐이다. 아이디어가 없거나 흐릿하면 `concept-brief`, 코드가 이미 게임을 담고 있는데 문서가 없으면 `reverse-document` 절차를 꺼낸다.
- 사람이 막히거나 당황한 말을 하면 차분하게 한 가지 행동만 말한다. 일하는 방식이 프로젝트에 비해 무거우면 문서를 줄이는 쪽을, 시스템이 많아져 한 장 기획을 넘었으면 늘리는 쪽을 권한다.

## 맡길 때 적을 것
- 총괄은 필요한 틀 · 규칙 · 엔진 참조를 `gaf library take <칸>/<id>…`로 꺼내 맡기는 글에 경로를 적는다.
- 결과물 경로는 `--expect "<경로,…>"`로 약속한다(존재 · 비지 않음 · 이번 일의 변경만 확인하며 내용은 안 봄). 검사 수단을 만들면 총괄이 `gaf check add "<이름>" "<명령>" [--when "<글롭,…>"] --why "<막을 실수>"`로 청해 사람의 화면 승인을 받는다. 이후 바뀐 파일에 맞는 기본 검사는 지휘자가 돌린다.
- 결과의 `[지휘자 확인]`에서 실패는 고치고 못 봄은 통과로 적지 않는다.
- 읽을 파일: 프로젝트 설정 · 기획 문서 폴더 · 코드 뿌리 · 시험 폴더 · 인계 글. 찾는 곳이 정해져 있으면 경로, 아니면 찾아볼 곳 목록을 준다. 엔진 전문가에게는 `gaf library take engines/<엔진>/<글>`로 꺼낸 경로를 맡기는 글에 적는다. 코드를 권하기 전에 없어진 API · 바뀐 점을 거기서 보게 한다.
- 결과물과 둘 곳: 현황표(위 표 그대로) · 검사 수단 목록 · 차이 목록. 표에 칸이 비면 「못 봄」이나 「해당 없음」을 쓰게 한다.
- 끝 기준: 칸마다 근거 파일 또는 못 본 이유가 있다. 단계 판정에는 근거와 못 돈 확인이 같이 있다.
- `--check`로 줄 수 있는 것: 검사 수단을 만드는 일의 「이 명령이 0이면 통과」. 현황표의 판정 · 지적 보고가 필요하면 별도 검토 역할에게 보통 `gaf assign`으로 맡긴다. `--review`는 사람에게 보일 결과물 · 눈으로 봐야 하는 것에만 쓰고, 검토 역할은 먼저 `gaf role new`로 만든다(채택 고리의 답과 반환 범위는 `code-review` 절차 참고).
- 쓸 곳: 현황표 파일. 맡기는 글의 쓸 곳은 안내다. 막는 범위는 역할을 만들 때 `gaf role new <이름> --write <글롭>`으로 정한다. `gaf assign`에는 쓰기 범위 칸이 없으므로 더 좁혀야 하면 그 범위의 역할을 따로 만든다.

## 사람이 정할 것
- 사람의 목표가 말에 없고 그 값이 일의 범위를 갈라놓을 때(보기 1~2개, 권하는 쪽 먼저).
- 엔진 · 대상 기기 · 게임의 방향을 사람이 말한 적 없을 때(게임 내용, 되돌리기 어려운 일).
- 엔진 판을 올리거나 갈아타는 일, 설치 · 내려받기가 필요한 일(되돌리기 어렵거나 사람의 동의가 필요한 일).
- 이미 정해진 값(기록된 엔진 · 사람이 말한 목표)은 다시 묻지 않고 그대로 쓴다.
- 그 밖에 현황을 읽고 알게 된 것의 해석 · 역할 구성 · 첫 일의 순서는 총괄이 정하고 결과로 알린다.

## 판정과 남길 것
- 현황표 칸은 찾은 값 · 못 봄(이유) · 해당 없음이다. 판정이 붙는 것(검사 수단 · 문서 꼴 · 단계)은 통과(근거 있음) · 실패 · 못 봄(이유) · 해당 없음으로 적는다. 실패와 못 봄이 같이 있으면 실패다.
- 파일이 있다 · 시험이 통과했다 · 사람이 해 보고 확인했다는 서로 다른 증거다. 현황표에 따로 적는다.
- 남길 기록: 현황표(항목 · 판정 · 근거) · 기록된 단계와 실물의 어긋남 · 검사 수단 목록과 한 번 돌린 결과 · 차이 목록(심각도 · 한 줄 설명 · 고치는 방법) · 첫 일 목록.
- 「있는 것을 못 봄」을 숨기지 않는다. 못 본 칸이 많으면 그것이 이 절차의 결과다.

## 하지 않는 것
- 문서가 없다고 새 프로젝트처럼 처음부터 만들지 않는다. 진행 중인 일을 다시 만들지 않는다.
- 파일 개수로 단계나 완성도를 추측하지 않는다.
- 못 본 것을 「없음」 · 「0개」 · 「통과」로 쓰지 않는다.
- 검사 수단이 없는 채로 역할을 늘리지 않는다.
- 엔진 · 도구를 설치하거나 내려받지 않는다. 엔진을 사람 대신 고르지 않는다.
- 사람의 목표를 추측으로 확정하지 않는다.
