코드나 만들어 둔 게임에 문서가 없을 때, 읽은 것을 문서로 옮기는 절차다. 코드는 무엇이 만들어졌는지만 말하고 왜 만들었는지는 말하지 않는다. 그 틈을 지어내 채우면 지어낸 공식이 요구가 되고 일이 되고 코드가 된다.

## 언제 꺼내나
- 기획서 없이 기능을 만들었거나, 문서가 없는 코드를 넘겨받았을 때.
- 시제품에서 나온 규칙을 정식 문서로 옮겨야 할 때.
- 「왜 이렇게 만들었나」를 문서로 남기고 싶을 때.
- 문서를 쓰기에 읽을 구현이 너무 적으면 이 절차가 아니라 사람에게서 듣고 쓰는 `system-design` 절차로 간다(순서 3).

## 필요한 역할
- 게임플레이 프로그래머(`gameplay-programmer`) 또는 리드 프로그래머(`lead-programmer`) — 대상 코드를 읽고 관찰을 파일 · 줄로 적는다.
- 게임 디자이너(`game-designer`) — 관찰을 기획 문서의 칸으로 옮긴다. 의도를 지어내지 않는다.
- 테크니컬 디렉터(`technical-director`) — 구조 결정 기록(ADR)을 쓸 때 검토하고 판정과 근거를 보고한다. (없으면 쓴 역할이 아닌 프로그래머가 겸한다. 다른 프로그래머도 없으면 총괄이 작성 역할을 `gaf role reset <이름>`한 뒤 맡긴다 — 겸했다고 보고에 적는다)
- QA 테스터(`qa-tester`) — 읽은 동작을 실제로 돌려 보고 확인한다. 읽기만 한 것과 돌려 본 것을 가른다.

## 순서
### 1. 무엇을 문서로 만들지 정한다
총괄이 정한다. 종류와 대상 경로를 맡기는 글에 적는다.

| 종류 | 만드는 것 | 대상의 예 |
|---|---|---|
| 기획 문서 | 한 시스템의 규칙 · 공식 · 값 · 예외 상황 | 게임플레이 · UI 코드 |
| 구조 결정 기록 | 패턴 · 선택의 이유와 대가 | 핵심 구조 · AI · 네트워크 코드 |
| 개념 문서 | 시제품에서 알아낸 것 | 시제품 폴더 |
| 한 장 기획(이미 만든 게임 전체) | 이미 만들어진 게임의 한 장 기획. 만든 기능을 「만듦」으로 표시 | 한 파일 또는 한 폴더로 된 게임 |

문서의 크기는 프로젝트 규모에 맞춘다(시작 값의 예): 작은 프로젝트는 한 장 기획, 중간은 5칸(개요 · 자세한 규칙 · 예외 상황 · 의존 관계 · 수용 기준 — 수치 규칙이 있으면 공식 추가), 큰 프로젝트는 8칸(플레이어 환상 · 조절값 포함). 작은 프로젝트에서 시스템 하나만 읽었으면 게임 전체가 아니라 그 시스템의 한 장 기획을 쓴다. 프로젝트가 정한 규모가 있으면 그것을 따른다. 규모를 짐작으로 정하지 않는다. 확인하지 못했으면 가장 작은 쪽으로 쓰고 그렇게 했다고 말한다.

### 2. 읽는다 (관찰만 적는다)
프로그래머가 대상을 읽고 「관찰 목록」을 만든다. 결과물: 항목마다 한 줄 + 근거(`파일:줄`). 끝 기준: 모든 항목에 근거가 있다.
- 기획 문서용: 규칙 · 공식 · 게임플레이 값(피해 · 대기 시간 · 범위) · 상태 기계 · 능력 · 성장 · 코드가 처리하는 예외 상황 · 서로 영향을 주는 시스템.
- 구조 결정용: 패턴 · 스레드 · 저장 방식 · 의존과 결합 · 성능 특성 · 제약과 대가.
- 개념용: 핵심 메커니즘 · 뜻밖에 생긴 플레이 · 잘 된 것과 안 된 것 · 기술적 실현성 · 환상과 느낌(환상과 느낌은 코드에서 읽을 수 없으니 칸만 만들고 사람에게 남긴다).
- 이미 만든 게임을 읽을 때: 먼저 읽을 목록을 만든다 — 제목 · 반복 고리 · 입력 처리(키 이름) · 상태나 장면 이름과 이동 · 이기고 지는 조건 · 이름 붙은 수치와 설정 · 소리 · 저장 · 네트워크 호출. 긴 파일은 구역별로 읽고 읽은 줄 범위와 읽지 않은 줄 범위를 적는다. 몇 줄만 찾아 읽은 것은 끝까지 읽은 것이 아니다. 같은 폴더의 설명 글(README)도 자료이고 이름을 밝혀 쓴다(통째로 붙이지 않는다).
- 어떤 항목은 반드시 하나씩 적는다: 「못 읽은 것」. 압축된 코드 · 네트워크로 받는 파일 · 없는 파일 · 서버 쪽 · 작업자(worker)나 내장 페이지는 읽지 못한 것으로 이름 붙여 적는다. 반복 고리가 없는 페이지는 「게임 고리를 찾지 못함」이고, 그 경우 한 장 기획의 기능 칸은 비어 있고 이유를 쓴다. 모든 스크립트가 압축돼 있으면 규칙은 못 읽은 것이고, 기능은 화면에서만 뽑아 전부 「추측」이다.

### 3. 충분한지 본다 (여기서 멈출 수 있다)
읽은 것을 센다: 이름 붙은 동작과 눈에 보이는 규칙(빈 틀이나 빈 클래스는 제외) · 값을 계산하는 식 · 쓰는 곳이 있는 조절값.
- 셋이 모두 0이거나, 대상에 상투 코드 밖의 줄이 20줄 안쪽이면(시작 값의 예) 멈춘다. 「이 경로에는 문서로 만들 만한 구현이 없다. 찾은 것: 동작 N · 식 N · 값 N. 읽을 동작이 없으니 쓰면 지어낸 글이 된다」라고 보고하고, 설계가 사람 머릿속에 있으면 사람에게서 듣고 쓰는 `system-design` 절차로 간다.
- 일부만 있으면 있는 만큼만 쓴다. 칸이 비면 「소스에서 찾지 못함」이라고 쓴다. 칸을 지우지 않고(지우면 「안 찾아봄」으로 읽힌다) 그 시스템이 보통 가진 것으로도 채우지 않는다. 대괄호 예시는 모양이지 채울 개수가 아니다.

### 4. 세 칸으로 가른다
게임 디자이너가 관찰 목록을 아래 세 칸으로 옮긴다. 칸이 섞이면 실패다.

| 칸 | 넣는 것 | 근거 |
|---|---|---|
| 관찰한 동작 | 코드가 실제로 하는 일. 파일:줄. 돌려 본 것이면 「돌려 봄」, 읽기만 했으면 「읽음」 | 필수 |
| 추론 | 관찰에서 추측한 이유 · 역할. 「추측」 표시와 무엇에서 추측했는지 | 추측한 근거 |
| 개선 제안 | 빠진 예외 상황 · 균형 의심 · 후속 일 | 제안일 뿐 요구가 아니다 |

세 칸 밖에 「사람에게 확인할 것」 칸을 따로 둔다: 원래 의도 · 재미 · 유지할 것 · 핵심 기둥인지 보조인지 · 값이 그렇게 커지는 것이 의도인지 · 구조를 그렇게 고른 이유(검증 가능성 · 분리 · 물려받은 것 · 성능). 코드에서 읽을 수 없는 것은 지어내지 않고 여기에 남긴다.
- 게임 내용에 닿는 의도 질문(원래 의도 · 재미 · 유지할 것 · 핵심인지 · 값이 커지는 것이 의도인지)은 총괄이 모아 사람에게 한 번에 올린다(질문마다 후보 이유를 보기로). 구조를 고른 이유는 사람에게 묻는 다섯에 들지 않으니 올리지 않고 문서의 열린 질문으로 남긴다. 코드를 읽어서 아는 것은 묻지 않는다. 답을 받으면 해당 항목에 「사람이 확인」을 표시한다.
- 답이 안 오면 해결한 척 쓰지 않는다. 항목은 「의도 미확인 — 구현에서 추측, 확인 안 됨」으로 문서에 열린 질문으로 남는다. 추론한 의도를 확정한 의도처럼 쓰는 것이 이 절차의 가장 흔한 실패다.
- 한 장 기획의 칸 채우기: 사람의 말 칸에는 사람이 쓴 말만(설명 글은 출처로 이름만). 소개 · 장르 · 조작 · 모습 · 처음 1분 · 도전(지는 조건이 처음 걸리는 때 — 질 방법이 없으면 비우고 이유)은 코드와 화면에서 「추측」 또는 「강한 추론」으로 표시. 기능 칸은 근거(파일:줄과 해당 화면)가 있을 때만 「만듦」 표시, 「안 만듦」은 사람의 말이나 코드의 해야 할 일 표시에서만. 질문 · 지킬 것 · 피할 것 · 범위 밖은 비운다(사람의 말에서만 채운다). 만드는 순서의 1단계는 「들어온 그대로의 게임」이고 모든 기능이 만듦이다. 센 수(무작위 함수 · 시간 함수를 부르는 곳의 개수)는 판단 없이 숫자만 적는다.

### 5. 출처를 문서 맨 위에 박는다
이 문서는 사람이 쓴 기획서와 같은 꼴과 곳에 놓이지만, 사람이 쓴 것은 「의도」를 말하고 이것은 「관찰한 동작과 추론」을 말한다. 읽는 쪽이 구분하지 못하면 안 된다. 제목 바로 아래에 적는다.
- 「코드에서 거꾸로 만든 문서. 대상 경로 · 날짜 · 읽은 판(커밋 번호나 날짜). 이 글은 코드가 **하는 일**을 적었다. 『의도 미확인』은 추측이지 확인된 것이 아니다. 문서와 코드가 어긋나면 문서가 요구라고 가정하지 않는다.」
- 머리 정보: 상태(코드에서 거꾸로 만듦) · 출처 경로 · 날짜 · 확인한 사람.
- 고칠 때도 이 표시를 지우지 않는다. 사람이 의도를 확인하고 기획서로 채택할 때 지우는 것은 그 사람의 일이다.

### 6. 문서를 쓰고 후속 일을 적는다
- 게임 디자이너(구조 결정 기록은 프로그래머)가 쓴다. 쓰는 곳: 기획 문서 · 구조 결정 · 개념 문서의 정해진 자리. 이미 있는 문서를 덮어쓰지 않고 차이를 보여 준다.
- 보고에 코드에 없던 것을 더한 곳(덧붙인 예외 상황 · 균형 의심)을 따로 적는다.
- 모자란 곳(구현이 부분만 되어 있음 · 다른 시스템과의 상호작용이 아직 없음)은 「미완성」으로 표시한다.
- 후속 일을 제안으로만 적는다: 수치가 급격히 커지는 공식의 균형 점검 · 구조 결정 기록 · 빠진 예외 상황 구현 · 이 시스템을 핵심 기둥으로 올릴지. 자동으로 시작하지 않는다. 총괄이 우선순위를 정해 맡긴다.
- 단계마다 사람에게 쓰기를 묻지 않는다. 의도 칸은 질문으로 올라간다.

## 맡길 때 적을 것
- 총괄은 필요한 틀 · 규칙 · 엔진 참조를 `gaf library take <칸>/<id>…`로 꺼내 맡기는 글에 경로를 적는다.
- 결과물 경로는 `--expect "<경로,…>"`로 약속한다(존재 · 비지 않음 · 이번 일의 변경만 확인하며 내용은 안 봄). 검사 수단을 만들면 총괄이 `gaf check add "<이름>" "<명령>" [--when "<글롭,…>"] --why "<막을 실수>"`로 청해 사람의 화면 승인을 받는다. 이후 바뀐 파일에 맞는 기본 검사는 지휘자가 돌린다.
- 결과의 `[지휘자 확인]`에서 실패는 고치고 못 봄은 통과로 적지 않는다.
- 종류와 대상 경로 · 규모(5칸/8칸/한 장) · 읽을 파일. 읽지 않을 곳(압축 파일 · 외부 라이브러리 · 만든 결과물).
- 결과물과 둘 곳: 관찰 목록(근거 줄 포함) · 세 칸으로 나눈 문서 · 사람에게 확인할 것 목록.
- 끝 기준: 관찰 항목마다 `파일:줄`이 있다 · 의도 칸 안의 모든 말은 「사람이 확인」 또는 「의도 미확인」이다 · 읽은 줄 범위와 못 읽은 곳 목록이 있다 · 빈 칸은 「소스에서 찾지 못함」이다.
- `--check`: 문서의 근거 줄이 실제로 그 파일에 있는지 보는 명령, 문서 맨 위에 출처 표시가 있는지 보는 명령(0이면 통과). 의도가 지어졌는지는 검사 명령으로 못 가른다. 별도 검토 역할에게 보통 `gaf assign`으로 「추론이 관찰이나 확정된 의도로 쓰인 곳」의 판정 · 지적 보고를 맡긴다(`--expect`에 보고 경로).
- 쓸 곳: 대상 문서 한 개. 코드는 고치지 않는다. 맡기는 글의 쓸 곳은 안내다. 막는 범위는 역할을 만들 때 `gaf role new <이름> --write <글롭>`으로 정한다. `gaf assign`에는 쓰기 범위 칸이 없으므로 더 좁혀야 하면 그 범위의 역할을 따로 만든다.

## 사람이 정할 것
- 원래 의도 · 재미 · 지켜야 할 것(게임 내용). 보기 1~2개와 권하는 이유 먼저.
- 완성된 문서를 사람이 쓴 기획서로 채택할지(채택하면 출처 표시를 지운다).
- 의도가 코드와 다를 때 코드를 고칠지 문서를 고칠지(게임 내용).
- 구조 선택의 이유는 올리지 않는다. 「의도 미확인」인 열린 질문으로 두고 일을 막지 않는다.
- 그 밖의 읽을 범위 · 규모 · 후속 일의 순서는 총괄이 정하고 결과로 알린다.

## 판정과 남길 것
- 항목별: 통과(근거가 있고 칸이 맞다) · 실패(근거 없는 관찰 · 추론이 관찰 칸에 있음 · 의도가 확정된 것처럼 쓰임) · 못 봄(읽지 못한 곳 · 돌려 보지 못함) · 해당 없음. 실패와 못 봄이 같이 있으면 실패다.
- 증거를 가른다: 코드를 읽었다 · 돌려 봤다 · 사람이 확인했다는 서로 다른 증거다.
- 남길 기록: 관찰한 동작 · 추론 · 개선 제안 · 사람에게 확인할 것의 네 칸 · 읽은 범위와 못 읽은 곳 · 발견한 조절값(이름 · 값 · `파일:줄`) · 출처 표시 · 후속 일 제안.
- 이미 만든 게임의 한 장 기획에는 위에 더해 「읽은 것에서」 기록 칸: 읽은 파일과 줄 · 기능마다 있는 곳과 보여 주는 화면 · 못 읽은 목록.

## 하지 않는 것
- 의도를 추측해 확정으로 쓰지 않는다. 재미 · 느낌을 코드에서 읽었다고 쓰지 않는다. 지킬 것에 사람이 말하지 않은 줄을 넣지 않는다.
- 비어 있는 칸을 그 시스템이 보통 가진 것으로 채우지 않는다. 칸을 지우지 않는다.
- 읽지 못한 곳을 읽은 것처럼 쓰지 않는다. 몇 줄만 찾아 읽고 다 읽었다고 하지 않는다.
- 출처 표시 없이 사람이 쓴 기획서와 같은 곳에 놓지 않는다.
- 코드를 고치지 않는다. 문서 쓰기 전에 후속 일을 자동으로 시작하지 않는다.
- 구현이 거의 없는 곳에서 서식만 채워 문서를 만들지 않는다.
