화면은 정상일 때만 설계하면 빈 화면 · 오류 · 불러오는 중에 무너지고, 한 입력 장치만 생각하면 다른 장치에서 못 쓴다. 이 절차는 화면 · HUD · 공통 상호작용 · 접근성 목표를 명세로 쓰고, 빠진 곳을 검토로 찾는다.

## 언제 꺼내나
- 화면 · 흐름 · HUD를 구현하기 전(기획서에 화면 요구가 있을 때).
- 같은 동작이 화면마다 다르게 되어 공통 패턴 목록이 필요할 때.
- 접근성 목표(어디까지 맞출지)를 프로젝트 차원에서 정할 때.
- 화면 명세를 UI 구현이나 시각 설계로 넘기기 전 검토할 때.

## 필요한 역할
- UX 디자이너(`ux-designer`) — 명세 작성의 중심.
- 아트 디렉터(`art-director`) — 영역의 모양 · 색 · 느낌(UX는 영역을 정하고 아트는 어떻게 보일지 정한다).
- UI 프로그래머(`ui-programmer`) — 부품 목록을 정하기 전 구현 가능성 · 데이터 연결 확인.
- 게임 디자이너(`game-designer`) — 데이터의 주인이 불분명할 때.
- 내러티브 디렉터(`narrative-director`) — 화면에 보이는 설정 글 · 품목 이름이 있을 때.
- 접근성 전문가(`accessibility-specialist`) — 접근성 기준을 정의하고 점검한다(없으면 UX 디자이너가 겸한다 — 겸했다고 보고에 적는다).
- QA 리드(`qa-lead`) — 수용 기준이 시험 가능한지 본다.

## 순서
1. **모드를 정한다**(총괄): 화면/흐름 하나 · HUD · 공통 상호작용 패턴 목록 · 프로젝트 전체 접근성 요구. 필요한 화면의 범위는 프로젝트가 정한다(핵심 화면만 · 화면마다).
2. **맥락을 모은다**(맡기는 글에 적는다). 한 장 기획 · 플레이어 여정(있으면 이 화면이 어느 단계인지 · 도착할 때의 감정 · 채울 필요). 여정 문서가 없으면 「없다」고 쓰고 열린 질문에 올린다 — 이 절차는 그 문서를 만들지 않는다. 기획서의 **화면 요구**(이 화면 이름이나 분류를 가리키는 것 — HUD는 모든 시스템 것이 모인다) · 기존 화면 명세(들고 나는 길 맞추기) · 공통 패턴 목록(이름과 한 줄만) · 아트 방향 · 접근성 목표 · **입력 장치**(주 입력 · 게임 패드 · 터치 · 목표 플랫폼). 입력 장치를 못 정했으면 한 번만 정하고 화면마다 다시 묻지 않는다. 기획서 수를 세고 화면 요구 절이 없는 기획서는 **「화면이 없다」가 아니라 「절이 없다」**로 보아 정말 화면이 필요 없는지 확인한 뒤 뺀다(HUD에서 시스템 하나의 표시를 조용히 빼면 안 된다). 절은 제목 뒤 몇 줄만 보지 않고 다음 같은 급 제목까지 읽는다. 기존 명세가 있으면 내용이 있다는 이유만으로 끝난 절로 보지 않고 빈 절만 채운다.
3. **화면 명세 쓰기**(화면/흐름). 절 순서:
   - 목적과 플레이어 필요: 「플레이어는 ___하려고 이 화면에 온다」. 개발자 관점이 아니라 플레이어 관점.
   - 도착할 때의 맥락: 언제 처음 만나나 · 직전에 뭘 했나 · 어떤 마음 상태(차분 · 급함 · 궁금)를 전제하나 · 스스로 오나 게임이 보내나.
   - 내비게이션 위치: 「뿌리 → 위 화면 → 이 화면」과 다른 진입 경로.
   - 들고 나는 길 표 둘: (들어오는 곳 · 계기 · 가져오는 맥락) (나가는 곳 · 계기 · 되돌릴 수 없는 상태 변화).
   - 배치: 정보를 나열하고 **가장 먼저 봐야 할 것 순서**를 정한 뒤에 영역(머리 · 내용 · 동작줄 …) 후보 2~3개와 이유 → 부품 목록(종류 · 보이는 내용 · 눌리나 · 공통 패턴 이름 또는 새 패턴 표시) → 필요하면 글자로 그린 배치도.
   - **상태와 변형 표**(상태 · 계기 · 바뀌는 것): 정상 · **빈 상태**(처음이라 자료가 없을 때) · **오류 상태**(실패 · 없는 자원) · **불러오는 중**(비동기로 가져올 때) · 성장에 따라 바뀌는 상태(잠김 · 튜토리얼 덧씌움) · 플랫폼 변형. 시간이 걸리거나 자동으로 닫히는 상태는 시간을 적는다.
   - **상호작용 표**: 부품마다 동작(탭 · 클릭 · 누르기 · 길게 · 끌기) · 입력 장치별 입력(마우스 · 패드 버튼 · 키) · 즉시 피드백(시각 · 소리 · 진동) · 결과(이동 · 상태 변화 · 데이터 쓰기). 다른 화면으로 가면 그 명세가 있는지 확인하거나 「명세 의존」으로 적는다. 마우스처럼 정밀한 조작을 패드에 요구하지 않는다.
   - 발생 사건: 동작마다 게임이 알려야 할 사건(분석 · 상태 변화) 또는 「사건 없음」(의도). 저장 상태 · 진행 · 경제를 바꾸는 동작은 구조 쪽에 알린다. **분석 사건을 어디에 보낼지는 별도 데이터/동의 결정이다** — 이 명세가 정하지 않는다.
   - 전환과 애니메이션: 들어옴 · 나감 · 상태가 바뀔 때. 멀미를 일으킬 움직임에 줄이기 옵션이 있나.
   - 데이터 요구 표(데이터 · 주인 시스템 · 읽기/쓰기 · 비고): 값이 어디서 오나 · 실시간인가(무엇이 갱신을 일으키나) · **값이 없을 때 뭘 보이나**. 게임 상태(진행 · 인벤토리 · 경제)는 UI가 주인이 아니다. 단 UI 안의 선택 · 초점 · 열린 탭 같은 **화면 지역 상태는 UI가 갖는다** — 둘을 가른다.
   - **입력 장치별 점검(장치마다 블록 하나)**: 닿을 수 있나 · 탭/방향키 순서 · **초점이 보이나** · 모달에 초점 가두기 · 취소/뒤로가기 동작 · 눌리는 영역 크기 · 패드 연결이 끊길 때. 게임이 지원하지 않는 장치는 블록을 빼고 그렇다고 적는다. 명세가 정한 것만 체크하고, 정하지 않은 것은 체크하지 말고 열린 질문에 올린다.
   - 접근성: 접근성 요구 문서가 있으면 정한 목표에 맞춘다. 키보드만으로 끝까지 · 패드 순서 · 글자 대비와 최소 글자 크기 · **색만으로 정보를 전하지 않기** · 비문자 요소의 보조기기 안내 · 움직임 줄이기. 목표가 없으면 열린 질문에 「접근성 목표 미정」을 적고 멈추지 않는다.
   - 현지화: 가장 긴 글과 배치에 들어가는 최대 글자 수 · 한 줄이어야 하는 글(버튼 이름) · 숫자 · 날짜 · 통화 형식. 번역 길이 여유 +30%는 **시작 값의 예일 뿐이다** — 이 게임의 목표 언어로 실제 길이를 재서 배치가 깨지는 곳을 표시한다.
   - 수용 기준: 시험자가 다른 문서를 안 읽고 확인하는 것. 적어도 열리는 시간 하나 · 이동(들고 나는 길) 하나 · 오류/빈 상태 하나 · 접근성 하나 · 이 화면의 목적 하나를 덮는다(그 밖의 예: 값의 최소/최대 표시 · 키보드/패드로 모든 부품에 닿나).
4. **HUD 명세**(화면과 순서가 다르다): 정보 구조를 끝내기 전에 배치를 건드리지 않는다.
   - 철학: 화면 정보와 게임의 관계를 1~2문장(거의 없음 · 필요한 것만 · 정보 가득 · 상황에 따라 변함). 이후 모든 선택의 제약이다.
   - **정보 전체 목록**: 모든 기획서의 화면 요구에서 모은다(위 맥락 모으기의 수를 센다). 분류: 항상 보임 · 상황에 따라 보임 · 요청하면 보임 · 화면에 글로 안 보이고 세계/소리로 전함. HUD에서 가장 무거운 결정이라 한꺼번에 정하지 않고 몇 개씩 묶어 차례로 정한다. 「항상 보임」이 늘어 철학과 부딪히면 줄이거나 철학을 고치거나 상황별로 나누는 보기를 올린다.
   - 영역 → 부품 명세(이름 · 분류 · 내용 · 모양(막대 · 숫자 · 아이콘) · 갱신 방식 · 나타나는 계기 · 애니메이션).
   - **상황별 상태**: 탐험 · 전투 · 대화/컷신 · 일시정지를 모두 다룬다(게임에 없는 상황은 「해당 없음」과 이유). 저자원 · 빈 값 같은 변형은 표로.
   - **정보 우선순위**: 부품마다 반드시 유지 · 유지 권장 · 숨겨도 됨 · 항상 숨김, 숨겼을 때 무엇이 대신 전하나(소리 · 세계 속 단서 · 없음).
   - **시각 예산**: 동시에 보일 수 있는 최대 부품 수와 화면에서 차지할 최대 비율, 넘으면 무엇부터 뺄지. 숫자는 이 게임이 정한다.
   - **알림**: 알림 종류마다 계기 · 위치 · 지속 · 동시 최대 수 · 우선순위 · **동시에 둘이 오면 어떻게 하나 · 전투 중 보류하는 것 · 대기열에 안 넣는 것**.
   - 플랫폼 적응(눌리는 크기 · 안전 영역) · 사용자 조절값(크기 · 투명도 · 부품별 보이기 · 자막 크기 — 범위와 기본값) · 수용 기준(적어도 안전 영역 · 상황별 부품 · 시각 예산 · 접근성 · 알림 대기를 덮는다).
5. **상호작용 패턴 목록**: 기존 화면 명세에서 이미 쓰는 패턴을 뽑아 이름 · 분류 · 쓰는 화면 · 설명 · 규격(동작 · 입력 · 피드백 · 접근성) · 쓸 때 · **쓰지 말 때**를 적는다. 안 쓰이지만 필요한 패턴과 서로 어긋나는 패턴(합칠 것)은 「빈 곳」에 올린다. 새 패턴이 필요하면 총괄에 알린다.
6. **프로젝트 접근성 요구**: 어디까지 맞출지(목표 단계)를 정하고 시각 · 운동 · 인지 · 청각 · 플랫폼 보조 기능 · 기능별 표 · 시험 계획 · 일부러 안 하는 것(이유)을 적는다. **목표 단계는 사람이 정한다** — 이 문서가 다른 화면 명세의 기준이다. 목표가 비어 있으면 다른 점검이 「못 봄」이 된다.
7. **교차 점검**(명세를 쓴 뒤): 기획서 화면 요구가 모두 들어갔나(N/M) · 패턴 이름을 썼나, 새 패턴은 목록에 올렸나 · 들고 나는 길이 이웃 명세와 맞나 · 접근성 목표를 다뤘나 · 데이터가 있는 부품마다 빈 상태가 있나. 결과 칸: `요구 N/M · 새 패턴 · 길 불일치 · 접근성 빈 곳 · 빈 상태 없는 곳`.
8. 총괄이 쓴 역할과 다른 검토 역할에게 보통 `gaf assign`으로 명세 검토를 맡겨 판정 넷 · 지적 목록을 보고 파일로 받는다. 관련 문서의 수정은 쓸 곳을 적은 새 일로 맡긴다.

### 검토(별도 역할이 하는 점검표 — 읽기만 하고 고치지 않는다)
- **화면 명세**: 머리(상태 · 작성자 · 대상 플랫폼) · 모든 절이 채워짐 · 목적이 플레이어 관점 · 도착 맥락이 구체적(「인벤토리를 열었다」만이 아님) · 오류 · 빈 · 불러오는 상태 · 입력 장치별 완전성(장치마다 초점 순서 · 패드 방향 순서 · 정밀 조작 없음 — 어느 장치를 볼지는 명세 머리가 아니라 프로젝트의 플랫폼 · 입력 설정이 기준이고, 설정이 없을 때만 머리를 쓴다) · 데이터 주인에 UI 없음(게임 상태 기준) · 갱신 계기 · 값 없음 처리 · 접근성 목표 충족(낮은 단계라도 색만으로 전하지 않기 · 그 위 단계는 초점 순서와 글자 대비 · 더 위는 주요 상태 변화의 화면 낭독 안내) · 기획서 요구 대응 · 근거 없는 화면 요소 없음 · 공통 패턴 일관(목록에 있는 동작을 처음부터 다시 정하지 않음) · 글이 긴 곳 표시 · 수용 기준이 명세 없이 시험 가능 · 열기 시간 · 해상도.
- **HUD**: 철학 · 정보 구조가 모든 시스템 화면 요구를 덮음 · 안전 영역 · 부품 명세 · 상황별 4상태 · 우선순위 · 시각 예산 · 플랫폼 · 조절값 · 수용 기준. 중앙 플레이 영역을 가리는 부품에는 숨김 규칙 · 색 구분에 색약 대안 · 알림 대기 규칙 · 예산 준수.
- **패턴 목록**: 목록 색인이 실제와 맞음 · 흔한 조작 패턴 가운데 이 게임이 쓰는 것(버튼 변형 · 토글 · 슬라이더 · 드롭다운 · 목록 · 격자 · 모달 · 대화 상자 · 토스트 · 툴팁 · 진행 막대 · 입력칸 · 탭 · 스크롤) · 지금 명세들이 쓰는 게임 전용 패턴 · 패턴마다 쓸 때/쓰지 말 때/상태/접근성/구현 메모 · 서로 충돌 없음(뒤로가기 일관). 작성 틀에 없는 항목(애니메이션 표준 · 소리 표준)은 실제로 쓰는 것만 요구하고 해당 없는 장르 · 부품을 강제하지 않는다.
- 어느 점검표를 썼는지(머리의 문서 종류 또는 파일 이름으로 추정)를 보고에 적는다. 여러 파일이면 먼저 요약 표(파일 · 판정 · 주된 문제)를 둔다.
- 빠진 입력 때문에 못 봄이 나왔으면, 같은 입력으로 다시 돌려 다른 판정을 내지 않는다. 새 입력이 와야 판정이 바뀐다.

## 맡길 때 적을 것
- `--review`는 사람에게 보일 시각 결과물의 채택 고리다(`code-review`의 답 · 반환 규칙). 검토 역할은 먼저 `gaf role new`로 만든다. 후보마다 새 세션의 첫 줄은 「통과」 또는 「막힘: …」(못 보면 「막힘: 못 봄 — <무엇을 왜>」)다. 매회 새 세션이라 사용량이 많다.
- 총괄이 `gaf library take <칸>/<id>…`로 꺼낸 틀 · 규칙 · 엔진 참조의 경로를 준다.
- `--expect`에 결과물 경로를 적는다(존재 · 비지 않음 · 이번 변경 확인, 내용은 별도). 검사 수단을 만들면 총괄이 `gaf check add`로 청해 사람이 화면 승인한다(`project-start`의 명령 꼴). `[지휘자 확인]`의 못 봄은 통과가 아니다.
- 대상 · 깊이 · 입력 경로 · 수를 센 기획서 화면 요구 목록을 준다.
- 쓸 곳: UX 문서와 프로젝트가 정한 접근성 요구 자리. 쓸 곳은 안내일 뿐이다. 쓰기 제한은 `gaf role new <이름> --write <글롭>` 때 정한다. `gaf assign`으로 좁힐 수 없으니 더 좁아야 하면 역할을 따로 만든다.
- 끝 기준은 위 점검표다. `--check`: 필수 절 · 빈 자리표시. 취향은 후보와 이유만 보고한다.
- 명세 검토 보고는 보통 `gaf assign`, 화면 그림 채택은 `--review`로 맡긴다.

## 사람이 정할 것
- 배치의 취향과 시각 방향 · HUD 철학(정보를 얼마나 보일지) · 접근성 목표 단계 — 게임 내용.
- 기획서의 화면 요구와 화면 공간이 부딪힐 때 어느 쪽을 줄일지(조용히 뺀 요구가 없어야 한다).
- 분석 사건을 외부로 보낼지(별도 데이터/동의 결정 · 보안 동의가 걸린다).
- 나머지(절 순서 · 문서 깊이 · 입력 장치 정리 · 검토 붙이기)는 총괄이 정하고 결과로 알린다.

## 판정과 남길 것
- 명세 판정: **통과**(필수 절 모두 · 필수 상태 · 입력 장치별 점검 · 요구 N/M 모두 · 시험 가능한 기준) · **실패**(필수 절/상태 빠짐 · 요구가 빠짐 · 근거 없는 요소 · 서로 어긋난 길 — 빈 곳을 메우면 되는지, 목적 · 범위 · 완성도가 무너져 다시 설계해야 하는지를 같이 적는다) · **못 봄**(명세를 못 읽음 · 점검 기준이 없는 차원) · **해당 없음**(그 장치/화면이 게임에 없음 — 이유). 못 봄이 있으면 통과가 아니고, 실패와 함께 있으면 실패다.
- **접근성 차원**: 목표 문서가 없으면 「못 봄 — 확정된 목표 없음」이다. 명세 머리의 목표는 **가정으로** 이어 쓰고 가정이라고 적는다. 목표를 정하는 것이 먼저다.
- 접근성 기준(대비 비율 · 글자 크기 · 번역 길이 폭)은 이 글만으로 모든 게임의 통과 기준이 되지 않는다. **적용할 목표 · 플랫폼 · 언어 · 확인 방법을 명세에 적고**, 문서가 충족한다는 것과 기기에서 실제로 확인했다는 것을 따로 쓴다. 전투 · 탐험 · 대화가 없는 게임은 해당 상태를 「해당 없음」으로 적는다.
- 패턴 목록 차원: HUD는 해당 없음. 화면 명세인데 목록이 없으면 목록이 필요한 단계면 못 봄, 필요 없는 단계면 해당 없음.
- 남길 것: 화면 명세 · HUD 명세 · 패턴 목록 · 접근성 요구 · 검토 보고(차원별 판정 · 막힘/참고 · 필요 입력) · 열린 질문 · 교차 점검 결과.

## 하지 않는 것
- 취향이 걸린 선택을 정해 버린 채 명세를 다 된 것처럼 내밀지 않는다. 기획서 요구를 조용히 빼거나 레이아웃을 조용히 키우지 않는다. 기존 명세와 어긋나는 곳을 알리지 않고 쓰지 않는다. 결정마다 출처(기획서 요구 · 여정 · 사람의 선택)를 밝힌다.
- 정상 상태만 쓰고 끝내지 않는다. 지원하지 않는 입력 장치를 있는 것처럼 쓰지 않는다.
- 접근성 목표 없이 「접근성 통과」라고 쓰지 않는다. 수치 하나를 보편 규칙으로 쓰지 않는다.
- 같은 대화에서 쓴 명세를 검토하고 독립 검토라고 보고하지 않는다.
- 시각 방향을 역할이 정하지 않는다. 그림 자체는 이 절차의 역할이 만들지 않는다(art-direction 절차 참고).
