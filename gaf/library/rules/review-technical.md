기술 산출물(구상의 위험 목록 · 시스템 경계 · 구조 문서 · 구조 결정 기록(ADR) · 구현 규칙 목록)이 탄탄한지, 엔진 판의 사실에 기대는지를 처음 보는 검토 세션이 묻게 하는 질문 모음이다. 원문의 기술 검토 여덟이 소제목 여덟이다.

## 언제 붙이나
- 검토 역할은 총괄이 그때 고른 검토 세션이다(산출물을 쓴 세션이 아니다). 테크니컬 디렉터 역할 글을 줄 수 있으나 직함이나 위아래가 아니라 처음 보는 눈이 요점이다. 검토 역할은 판정과 근거를 보고하고, 정하는 것은 총괄이다.
- 총괄은 지금 산출물에 맞는 소제목만 골라 그 「볼 자료」와 같이 준다. 질문 글은 검토 세션이 읽는다. 구조를 건드리지 않는 작은 변경에는 붙이지 않는다.
- 쓰는 때(단계 이름과 수는 프로젝트가 정한다 — 예: 구상 → 시스템 기획 → 기술 준비 → 제작 → 마감 → 출시):
  - 구상: 기술 위험을 짚은 뒤(필요할 때).
  - 시스템 기획: 의존 지도가 정해진 뒤 기획 문서를 쓰기 전에 시스템 경계.
  - 기획 문서를 고칠 때(시스템 기획 · 제작): 영향 보고가 나온 뒤 변경 영향.
  - 기술 준비: 구조 문서 · 결정 기록마다 · 규칙 목록을 쓰기 전. 새 판 엔진 API를 건드리면 엔진 판.
  - 단계 점검: 총괄이 `rules/verdicts`의 「단계 점검의 관점」에 따라 이 관점을 골랐을 때.
- 판정은 「판정과 증거의 규칙」(`rules/verdicts`)을 따른다. 볼 자료를 못 읽은 질문은 못 봄이다. 엔진 판에 묶인 주장은 프로젝트의 엔진 참조 문서로 확인한 것만 단정한다.

## 기준
### 구상의 기술 위험이 감당할 만한가
- 볼 자료: 핵심 반복 설명 · 장르 · 대상 플랫폼 · 엔진(또는 「안 정함」) · 짚은 기술 위험 목록.
- 물을 것:
  - 이대로면 구상을 무너뜨릴 큰 위험이 있는가.
  - 엔진에 묶인 위험이라 엔진 선택에 영향을 줘야 하는 것이 있는가.
  - 혼자 · 작은 팀이 흔히 낮춰 잡는 위험이 있는가.
- 실패로 보는 것: 구상이나 범위를 고쳐야 하는 막힘. 줄이는 법을 붙일 위험은 우려로 남긴다.
- 못 봄으로 남기는 것: 핵심 반복 · 플랫폼 · 위험 목록을 받지 못했다. 엔진 「안 정함」은 빠진 입력이 아니다.

### 시스템 경계가 구조로 버티는가
- 볼 자료: 시스템 목록(아직 없으면 의존 지도 요약) · 층 배정(프로젝트가 정한 한 벌 — 예: 바탕 · 핵심 · 기능 · 표현 · 다듬기, `templates/systems-index`) · 의존 그래프 전부 · 병목 시스템 · 찾은 순환 의존과 푸는 안.
- 물을 것:
  - 시스템마다 따로인 관심사를 맡고 겹침이 적은가.
  - 너무 많이 떠맡은 시스템(신 객체)이 있는가.
  - 의존 순서가 구현 차례를 꼬는가.
  - 경계에 숨은 공유 상태가 있어 구현하면 단단히 엉키는가.
  - 바탕 층 시스템이 기능 층에 기대는가(뒤집힌 의존).
- 실패로 보는 것: 구조 문제를 낳을 근본적 경계 문제 — 기획 문서를 쓰기 전에 다시 짠다. 기획 문서 안에서 다룰 경계 문제는 우려로 남긴다.
- 못 봄으로 남기는 것: 의존 그래프나 층 배정을 받지 못했다.

### 기획 변경의 영향 평가가 맞는가
- 볼 자료: 기획 변경 영향 보고 전부 — 변경 요약 · 영향받는 결정 기록마다 분류(그대로 유효 · 다시 볼 것 · 대체될 듯) · 권하는 조치. 결정 기록을 고치기 전에 쓴다.
- 물을 것:
  - 분류가 맞는가. 특히 변경이 가정을 깨는데 「그대로 유효」로 낮게 잡은 것이 있는가.
  - 권하는 조치가 구조로 옳은가.
  - 이미 짚은 결정에 기대는 다른 결정 · 시스템으로 번지는 영향을 놓쳤는가.
- 실패로 보는 것: 평가를 다시 해야 한다 — 무엇을 놓쳤는지 적는다. 다시 볼 결정 · 권고는 우려로 남긴다.
- 못 봄으로 남기는 것: 영향 보고가 일부만 왔다(분류가 빠진 결정 기록이 있다).

### 구조 문서가 기술 요구를 다 덮는가
- 볼 자료: 구조 문서 · 기술 요구 기준선(요구 번호와 개수) · 결정 기록 목록과 상태 · 엔진 지식 빈틈 목록. 구조 문서를 처음 쓴 뒤와 큰 구조 고침 뒤에 쓴다.
- 물을 것:
  - 기준선의 요구마다 구조 결정이 덮는가.
  - 위험이 큰 엔진 영역마다 다뤘거나 열린 질문으로 적었는가.
  - API 경계가 기술 요구를 빠짐없이 나눠 맡고, 의존 방향을 지키는가. 엔진 · 언어별 구현 가능성과 인터페이스 정의의 빈틈은 `rules/review-code`에서 본다.
  - 바탕 층의 결정 빈틈이 구현 시작 전에 풀렸는가.
- 실패로 보는 것: 코딩을 시작하기 전에 풀어야 할 막힘. 그 밖의 빈 곳은 우려로 남긴다.
- 못 봄으로 남기는 것: 기준선이나 결정 기록 목록을 받지 못했다(덮었는지를 셀 수 없다).

### 결정 기록 하나가 받아들일 만한가
- 볼 자료: 결정 기록 · 엔진 판과 그 영역의 지식 빈틈 위험 정도 · 관련 결정 기록. 「받아들임」으로 바꾸기 전에 쓴다.
- 물을 것:
  - 문제와 이유가 분명한가. 버린 대안을 진짜로 따져 봤는가.
  - 결과 절이 맞바꾼 것을 솔직히 적었는가.
  - 엔진 판이 적혀 있는가. 모델이 배운 시점 뒤에 바뀌었을 수 있는 API 위험을 짚었는가.
  - 덮는 기획 요구에 이어져 있는가.
- 실패로 보는 것: 결정이 덜 정해졌거나 기술 가정이 틀렸다. 빈 곳은 우려로 남긴다.
- 못 봄으로 남기는 것: 결정 기록이나 엔진 판 참조를 읽지 못했다.

### 엔진 API가 그 판에서 맞는가
- 볼 자료: 쓰려는 API · 기능 · 엔진 참조 문서의 판과 모델이 배운 시점 · 깨지는 변경 · 폐기 API 문서의 관련 부분. 엔진에 묶인 구현 방법을 굳히기 전에 쓴다.
- 물을 것:
  - 이 API가 그 엔진 판에 있는가.
  - 시그니처 · 동작 · 이름공간이 바뀌었는가.
  - 알려진 폐기나 새 대안이 있는가.
- 실패로 보는 것: API가 바뀌었다 — 고친 방법을 같이 낸다. 구현 전에 확인할 것은 우려로 남긴다.
- 못 봄으로 남기는 것: 참조 문서가 그 API를 다루지 않는다. 기억으로 채우지 않고 「출처 없음」으로 적는다.

### 규칙 목록이 결정 기록에서 나왔는가
- 볼 자료: 쓰기 전 미리 보기(층별 규칙 수 · 뽑은 규칙 전부) · 덮은 결정 기록 목록 · 엔진 판 · 기술 선호 문서나 엔진 참조에서 온 규칙.
- 물을 것:
  - 결정 기록의 꼭 따를 패턴이 모두 바르게 실렸는가.
  - 금지 방식이 빠짐없고, 출처 결정 기록이 바르게 붙었는가.
  - 출처 결정 기록이나 선호 문서 없이 지어낸 규칙이 있는가.
  - 성능 한도가 결정 기록이 실제로 정한 제약과 맞는가.
- 실패로 보는 것: 틀렸거나 출처 없는 규칙 — 목록을 쓰기 전에 고친다. 고칠 규칙은 우려로 남긴다.
- 못 봄으로 남기는 것: 덮은 결정 기록을 읽지 못했다.

### 단계를 넘어갈 만큼 기술 바탕이 섰는가
- 볼 자료: 들어갈 단계와 프로젝트 크기 · 요구 · 권하는 산출물 · 구조 문서(있으면) · 엔진 참조 · 결정 기록 목록.
- 물을 것(그 단계가 요구하는 만큼만 — 나중 단계가 필요로 할 것으로 판정하지 않는다):
  - 시스템 기획으로: 고른 엔진에서 구상이 되는가. 기술 준비로: 시스템 목록 · 기획 문서가 구조를 짤 만큼 있는가.
  - 제작으로: 구조가 탄탄하고 바탕 층 결정이 구현을 시작할 만큼 끝났는가. 그 뒤: 빌드에서 구조가 버티는가.
  - 위험 큰 엔진 영역을 이 단계가 요구하는 깊이로 다뤘는가. 성능 예산이 현실적이고 필요한 곳에 적혔는가.
- 실패로 보는 것: 단계를 막는 것. 요구 산출물의 부재 · 해당 없음은 `rules/verdicts`의 단계 점검 기준을 따른다.
- 못 봄으로 남기는 것: 요구 산출물 목록을 받지 못했다.

## 확인하는 법
검사로 만들 수 있는 것: 의존 그래프의 순환 · 바탕 층이 기능 층에 기대는 화살표(층 표가 있으면 스크립트) · 기준선의 요구 번호마다 결정 기록이 이어졌는가(번호 대조) · 결정 기록에 엔진 판 칸이 찼는가 · 규칙 목록의 규칙마다 출처 칸이 찼는가 · 영향 보고에서 분류가 빈 결정 기록. 결정이 옳은지 · 경계가 깔끔한지는 검토 역할이 본다.
검토 역할이 볼 것: 고른 소제목의 질문에 하나씩 답하고 근거(파일:줄)를 붙인다. API 이름 · 판에 묶인 주장은 참조 문서의 줄을 댄다.
판정 적기: 소제목마다 통과 · 실패 · 못 봄 · 해당 없음 하나와 근거 · 우려 목록(무엇 · 어디 · 누구 몫) · 못 봄이면 빠진 자료. 소제목을 여럿 썼으면 가장 엄한 것이 전체 판정이다.
