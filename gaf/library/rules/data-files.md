조절값 · 적 · 아이템 같은 게임 자료 파일이 깨지지 않고, 숫자의 뜻이 적혀 있고, 꼴이 바뀌어도 읽는 쪽이 따라올 수 있게 하는 규칙이다. 원문은 JSON을 두고 썼다. 프로젝트가 다른 글 자료 형식을 쓰면 같은 기준을 그 형식과 엔진의 자료 형식에 맞춘다.

## 언제 붙이나
- 시스템 디자이너 · 경제 디자이너 · 레벨 디자이너가 자료 파일에 값을 넣거나 항목을 더하는 일.
- 게임플레이 프로그래머 · 도구 프로그래머가 자료 파일의 꼴(키 · 칸 · 스키마)이나 읽는 코드를 바꾸는 일.
- 붙이지 않는 때: 엔진 에디터가 쓰는 장면 · 자산 파일(`rules/scene-files` 규칙).

## 기준
- **읽힌다.** 자료 파일은 그 형식으로 올바르게 읽혀야 한다(JSON이면 올바른 JSON). 깨진 파일 하나가 빌드 전체를 막는다.
- **파일 이름.** 파일 이름 규칙을 프로젝트가 하나 정한다. 원문의 예: 소문자와 밑줄만 쓰고 `[시스템]_[이름].json` 꼴(`combat_enemies.json`). 엔진의 관례가 다르면(PascalCase를 쓰는 엔진) 엔진 관례를 따른다.
- **고정 이름.** 원문의 웹 시작 틀을 쓰는 프로젝트일 때만, 게임과 조절 패널이 같은 이름으로 읽는 설정 파일은 이름을 바꾸지 않는다. 그 안의 조절값 하나가 값 · 최솟값 · 최댓값 · 걸음(value · min · max · step) 꼴이면 그 꼴을 지킨다.
- **스키마.** 자료 파일마다 적어 둔 스키마가 있다 — JSON Schema 같은 스키마 파일이거나, 맞는 기획 문서 안의 표.
- **숫자의 뜻.** 숫자 값에는 무엇을 뜻하는지 주석이나 곁 문서가 있다.
- **키 이름.** 한 프로젝트 안의 키 이름 규칙을 하나로 맞춘다. 원문은 snake_case를 권했다(파일 이름 규칙과 맞춘다는 이유). 프로젝트가 정하면 그 규칙이다.
- **옮기는 층.** 엔진의 직렬화가 필드 이름 그대로 묶는데 코드의 이름 규칙이 파일 키 규칙과 다르면, 파일 키를 바꾸지 말고 한 번 옮겨 주는 층을 둔다. 자료 형식 그대로의 전달용 구조를 따로 두고 실제 타입으로 한 번 옮기거나, 이름 규칙을 바꿔 주는 직렬화 설정을 쓴다. 그 층이 자료 형식의 경계라고 적는다. 이유: 키는 엔진을 넘는 자료의 계약이다. 옮기는 층을 피하려고 파일 키를 바꾸지 않는다.
- **고아 없음.** 쓰이지 않는 항목을 두지 않는다. 항목마다 코드나 다른 자료 파일이 가리킨다.
- **버전.** 스키마를 깨는 변경에는 자료 파일의 버전을 올린다.
- **기본값.** 선택 칸에는 말이 되는 기본값을 둔다.
- 원문의 틀린 예: 파일 이름 `EnemyData.json`, 키 `Goblin` · `hp` — 대문자 파일 이름, 대문자 키, 이름 꼴을 안 따름, 필수 칸 빠짐.
- 엔진별 쓰는 법(자료 자산 · 직렬화 도구 · 읽는 길)은 프로젝트의 엔진 참조 문서와 그 엔진 전문가 역할이 정한다.

## 확인하는 법
검사로 만들 수 있는 것: 이 규칙은 거의 다 검사 명령으로 만들 수 있다. 하나로 묶은 검증 스크립트를 `--check`에 거는 것을 먼저 한다.
- 읽힘 — 대상 폴더의 자료 파일을 모두 읽어 본다. 읽은 파일 수와 실패 목록(파일:줄)을 찍는다. 0개를 읽었으면 통과가 아니라 못 봄이다.
- 스키마 — 파일마다 스키마로 검증한다(필수 칸 · 타입 · 범위). 스키마가 없는 자료 파일은 목록으로 내고 실패.
- 이름 · 키 — 파일 이름과 모든 키를 정한 정규식에 대 본다.
- 고아 — 항목 id를 모아 코드와 다른 자료 파일에서 찾고, 못 찾은 것을 낸다. 코드가 id를 문자열로 이어 붙여 만들면 놓치므로 결과는 후보로 보고, 그런 곳은 이유 적힌 허용 목록으로 남긴다.
- 참조 — 다른 항목을 가리키는 칸(원문의 예 `loot_table`)이 실제 있는 id인지.
- 기본값 · 숫자의 뜻 — 스키마의 선택 칸마다 기본값이, 숫자 칸마다 설명이 적혀 있는지.
- 버전 — 이전 판 스키마와 비교해 깨는 변경(칸 이름 · 타입 · 필수 여부)이 있는데 버전이 그대로면 실패.
- 조절값 꼴 — 값마다 최솟값 ≤ 값 ≤ 최댓값이고 걸음 > 0인지.
- 옮기는 층 — 시험. 견본 자료 파일을 읽어 실제 타입의 값이 기대와 같은지(키가 묶이지 않아 기본값으로 조용히 채워지는 것을 잡는다).

사람이나 검토 역할이 볼 것:
- 숫자 설명이 실제 뜻과 맞는가, 기본값이 말이 되는가 — 값을 정한 기획 역할이 아닌 검토 역할.
- 값 자체(피해 · 확률 · 가격)는 게임 내용이라 사람이 정한다.

판정: 기준마다 통과 · 실패 · 못 봄 · 해당 없음과 근거(파일:줄 · 검사 출력)를 적는다. 스키마가 없어 검증하지 못한 파일은 「못 봄」이 아니라 스키마 기준의 실패다. 원문의 웹 시작 틀을 쓰지 않는 프로젝트의 고정 이름 기준은 「해당 없음」이다. 스키마가 있는지 판정할 입력을 검토하는 쪽이 받지 못했다면 「못 봄 — 스키마 입력 미수신」으로 적는다. 부재와 입력 미수신은 `rules/verdicts`를 따른다.
