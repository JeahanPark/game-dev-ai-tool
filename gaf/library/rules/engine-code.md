게임플레이가 올라서는 엔진 · 핵심 코드가 위로 기대지 않고, 매 프레임 도는 곳에서 낭비하지 않고, 바꿀 때 부르는 쪽을 깨지 않게 하는 규칙이다.

## 언제 붙이나
- 엔진 프로그래머가 핵심 시스템(갱신 고리 · 그리기 · 물리 · 자원 관리 · 공개 API)을 쓰거나 고치는 일.
- 성능 분석가 · 엔진 프로그래머가 최적화하는 일(잰 근거 기준).
- 공개 인터페이스를 바꾸는 일 — 부르는 쪽(게임플레이 프로그래머 · 도구 프로그래머)에 영향이 있을 때.
- 붙이지 않는 때: 게임플레이 코드만 바뀌는 일(`rules/gameplay-code` 규칙).

## 기준
- **의존 방향.** 엔진 코드는 게임플레이 코드에 기대지 않는다(엔진 ← 게임플레이, 반대 아님).
- **매 프레임 할당.** 매 프레임 도는 곳(갱신 고리 · 그리기 · 물리)에서는 보통 새로 할당하지 않는다 — 미리 잡아 두고, 풀에 두고, 다시 쓴다. 원문은 할당 0을 모든 곳에 요구했다. 잰 병목이 있는 곳부터 지키고, 예외는 잰 값과 이유를 적는다. 원문의 틀린 예가 짚은 것: 매 프레임 새 목록 만들기, 매 프레임 장면 전체를 뒤져 찾기. 맞는 예: 목록을 한 번 만들어 두고 매 프레임 비워서 다시 채우기.
- **스레드.** 엔진 API는 스레드에 안전하거나, 한 스레드에서만 쓴다고 적혀 있다.
- **잰 근거.** 최적화는 하기 전과 한 뒤를 모두 재고 잰 숫자를 남긴다.
- **공개 API 설명.** 공개 API의 설명 주석에는 쓰는 예를 둔다. 원문은 모든 공개 API에 요구했다 — 보통은 그렇게 하고, 예를 빼면 이유를 적는다. 주석 꼴은 그 엔진 언어의 문서 주석 관례를 따른다.
- **호환.** 공개 인터페이스를 바꿀 때는 폐기 예고 기간을 두고 옮기는 법을 적는다.
- **자원 정리.** 자원은 정해진 때에 정리되게 한다(RAII 같은 결정적 정리).
- **낮춰 돌기.** 엔진 시스템은 어떤 기능을 쓸 수 없게 돼도 멈추지 않고 줄여서 돈다.
- **엔진 API 확인.** 엔진 API 코드를 쓰기 전에 프로젝트의 엔진 참조 문서로 지금 엔진 판을 확인하고 API를 대 본다. 기억으로 쓰지 않는다.
- 엔진별 쓰는 법(미리 잡는 길 · 할당 없는 찾기 함수 · 주석 꼴)은 프로젝트의 엔진 참조 문서와 그 엔진 전문가 역할이 정한다.

## 확인하는 법
검사로 만들 수 있는 것:
- 의존 방향 — 정적 검사. 엔진 폴더의 가져오기(import · include · using)를 훑어 게임플레이 폴더 · 모듈을 가리키면 실패. 훑은 파일 수를 같이 찍는다. 가장 값싸고 확실한 검사다.
- 매 프레임 할당 — 성능 시험. 정한 장면을 정한 프레임 동안 돌리며 엔진의 할당 측정(할당 횟수 · 바이트)을 읽어, 0이나 프로젝트가 정한 예산을 넘으면 실패. 갱신 함수 안의 생성 구문을 찾는 정적 검사는 후보만 낸다.
- 공개 API 설명 · 스레드 표시 — lint나 문서 생성기. 공개 심볼마다 설명 주석과 예가 있는지, 스레드 표시(안전 · 한 스레드만)가 있는지.
- 호환 — 스크립트. 공개 API 목록을 이전 판과 비교해, 지워지거나 꼴이 바뀐 것에 폐기 표시와 옮기는 글이 있는지.
- 자원 정리 — 시험. 열기 · 닫기를 여러 번 되풀이한 뒤 핸들 수 · 메모리가 처음으로 돌아오는지.
- 낮춰 돌기 — 시험. 기능 하나를 쓸 수 없게 한 설정(없는 장치 · 끈 기능을 흉내)에서 시스템이 멈추지 않는지.
- 잰 근거 — 보고에 전후 숫자가 있는지는 꼴 검사로 본다. 숫자가 맞는지는 같은 측정을 다시 돌려 본다.
- 엔진 API — 빌드(컴파일)가 없는 API의 일부를 잡는다. 판마다 뜻이 바뀐 API는 빌드로 잡지 못한다.

사람이나 검토 역할이 볼 것:
- 스레드 표시가 실제 동작과 맞는가(표시가 있다고 안전한 것은 아니다), 줄여서 도는 모습이 받아들일 만한가, 쓰는 예가 쓸모 있는가 — 리드 프로그래머나 테크니컬 디렉터.
- 엔진 판에 묶인 API 주장 — 엔진 전문가가 엔진 참조 문서로 확인하고, 출처를 확인하지 못한 것은 「출처 없음 — 무엇이 어디에 없다」로 적고 판정은 「못 봄 — API 출처를 확인하지 못함」으로 남긴다(`rules/verdicts`).

판정: 기준마다 통과 · 실패 · 못 봄 · 해당 없음과 근거(잰 값 · 파일:줄)를 적는다. 재지 않은 최적화는 「실패 — 요구한 전후 측정 없음」이다. 측정 기록을 검토하는 쪽이 받지 못했으면 「못 봄 — 측정 입력 미수신」이다(`rules/verdicts`). 공개 인터페이스를 건드리지 않은 일의 호환 기준은 「해당 없음」이다.
