시제품은 두 가지이고 규칙이 다르다. **버릴 시제품**(엔진 판 · 종이 판 · 기술 확인 · 대표 구간)은 질문 하나에 답하고 버리는 코드다. **키울 웹 시제품**(브라우저에서 도는 작은 판 — 아래의 전용 기준은 원문의 웹 시작 틀을 쓰는 프로젝트일 때만 적용한다)은 사람이 게임의 시작으로 남길 수 있는 판이다. 둘 다 제품 코드와 섞이지 않게 하고, 무엇을 알았고 무엇이 어디서 왔는지 남기게 하는 규칙이다. 순서는 `procedures/prototype` 절차(총괄이 이 규칙과 함께 꺼내 맡기는 글에 경로를 적는다)를 따른다.

## 언제 붙이나
- 프로토타이퍼(없으면 겸하는 게임플레이 프로그래머)가 시제품을 만들거나 고치는 일.
- 시제품을 제품으로 옮기거나 키울지 볼 때 — 테크니컬 디렉터 · 리드 프로그래머의 검토.
- 붙이지 않는 때: 제품 코드의 일. 이 규칙의 느슨한 기준을 제품 코드에 쓰지 않는다.

## 기준
### 모든 시제품
- 시제품마다 프로젝트가 정한 시제품 폴더 아래 자기 폴더 하나에 둔다.
- 주석을 쓸 수 있는 파일은 머리에 「시제품 — 제품용 아님」 주석으로 시작한다.
- 제품 코드는 시제품 폴더를 참조하거나 가져오지 않는다.
- 버릴 시제품은 자기 폴더 밖의 파일을 고치지 않고, 그대로 배포 · 출시하지 않는다.
- 키울 웹 시제품은 한 장 기획도 쓰고, 사람이 붙여 넣은 그림을 참고 폴더에 둘 수 있다. 나눌 때는 작업 폴더가 아니라 따로 만든 배포용 복사본에서 나눈다.

### 키울 웹 시제품
원문의 웹 시작 틀을 쓰는 프로젝트일 때만 아래 기준을 적용한다. 다른 시작 틀은 프로젝트가 정한 설정 · 출처 · 실행 구조를 따른다.
- 조절값은 모두 설정 파일 한 곳에 두고, 값마다 값 · 최솟값 · 최댓값 · 걸음을, 그리고 난수 씨앗을 둔다. 게임은 그 값을 도는 중에 읽고 코드에 박지 않는다.
- 게임의 무작위는 씨앗을 받는 난수 함수 하나로 낸다. 언어의 기본 난수(원문은 브라우저의 기본 난수 함수)를 바로 쓰지 않는다.
- 끊긴 상태로 돈다. 라이브러리는 폴더 안에 두고, 도는 동안 네트워크에 요청하지 않는다.
- 그림 · 소리 · 가져온 라이브러리 파일마다 출처 기록에 한 줄이 있다. 임시 파일은 출처 기록에 임시 표시를 하고 확장자 앞에 `_ph`를 붙인다.
- 한 장 기획의 복사본이 설명 파일(README)을 대신한다.
- 꾸밈도 이 판의 몫이다: 제목 화면 · 게임 끝과 다시 하기, 한 장 기획이 부르면 소리와 소리 끄기.
- 계속하기로 정해지면 프로젝트 뿌리로 키울 수 있다. 키울 때는 복사해서 키우고, 원래 시제품 폴더는 고치지 않는다.

### 버릴 시제품
- 배우는 것이 목표라 기준을 일부러 느슨하게 둔다. 되는 것: 코드에 박은 값 · 설명 주석이 거의 없음 · 단순한 구조(주입 없음) · 싱글턴과 전역 상태 · 복사해 붙인 코드 · 남겨 둔 디버그 출력 · 임시 그림과 소리 · 빠르고 거친 해결.
- 그래도 필요한 것: 설명 파일 하나에 시험하는 가설 · 돌리는 법 · 지금 상태(진행 중 · 끝남) · 발견(끝날 때 채운다).
- 개념이 확인돼 기능이 제품으로 갈 때: 발견을 기획 문서에 반영하고, 시제품 폴더는 참고로 남기되 늘려 쓰지 않는다. 코드를 그대로 옮길지 다시 쓸지는 엔진 · 품질 · 검사 결과를 보고 프로젝트가 정하고, 정한 것과 이유 · 재사용 조건을 적는다. 원문은 다시 쓰기를 규칙으로 두었다. 이미 만든 시제품을 제품 기반으로 쓰는 것은 되돌리기 어려운 일이라 사람이 정한다.
- 끝난 시제품은 발견을 남긴 뒤 보관하거나 지운다(지우기는 사람이 정한다). 버릴 시제품 코드가 조금씩 「정리」되며 제품 코드로 자라게 두지 않는다.

## 확인하는 법
검사로 만들 수 있는 것:
- 가져오기 금지 — 정적 검사. 제품 코드 전체에서 시제품 폴더 경로를 가리키는 가져오기 · 참조를 찾으면 실패. 이 규칙에서 가장 중요한 검사다.
- 머리 주석 — 스크립트. 시제품 폴더의 주석 가능한 파일마다 앞 몇 줄 안에 「제품용 아님」 표시가 있는지. 본 파일 수를 같이 찍는다.
- 폴더 밖 쓰기 — 이 일에서 바뀐 파일 목록이 모두 시제품 폴더 안인지(키울 웹 시제품은 한 장 기획 · 참고 폴더까지 허용).
- 설명 파일 — 스크립트. 버릴 시제품마다 설명 파일이 있고 가설 · 돌리는 법 · 상태 · 발견 칸이 있는지. 상태가 「끝남」인데 발견이 비었으면 실패.
- 키울 웹 시제품의 설정(원문의 웹 시작 틀을 쓰는 프로젝트일 때만) — 스크립트. 조절값마다 네 칸이 있고 최솟값 ≤ 값 ≤ 최댓값, 걸음 > 0이며 씨앗 칸이 있는지.
- 난수 · 네트워크(원문의 웹 시작 틀을 쓰는 프로젝트일 때만) — 정적 검사로 기본 난수 함수와 네트워크 요청(바깥 주소 · 요청 함수)을 찾는다. 네트워크를 끊은 채 띄워 시작이 되는지 보는 시험을 같이 둔다.
- 출처(원문의 웹 시작 틀을 쓰는 프로젝트일 때만) — 스크립트. 그림 · 소리 · 라이브러리 폴더의 파일 목록과 출처 기록을 대조해 빠진 줄 · 남는 줄을 낸다. 임시 표시와 `_ph` 이름이 서로 맞는지.
- 키운 뒤 — 원래 시제품 폴더 파일들의 지문(해시)이 키우기 전과 같은지.

사람이나 검토 역할이 볼 것:
- 가설이 답을 냈는가 · 재미있는가 — 사람이 해 본다(`procedures/prototype` 절차). 판이 돌아간다는 것은 재미의 증거가 아니다.
- 옮길지 다시 쓸지의 이유와 재사용 조건 — 테크니컬 디렉터나 리드 프로그래머가 검토하고 판정과 근거를 보고한다. 정하는 것은 사람이다.

판정: 기준마다 통과 · 실패 · 못 봄 · 해당 없음과 근거(파일:줄 · 검사 출력)를 적는다. 버릴 시제품에 키울 웹 시제품의 기준은 「해당 없음」이고, 그 반대도 같다. 사람이 해 보지 않은 판의 가설 판정은 「못 봄 — 해 보지 않음」이다.
