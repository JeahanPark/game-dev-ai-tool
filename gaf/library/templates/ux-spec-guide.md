# 화면 명세 길잡이

틀의 절 번호대로 나눴다. 「왜」는 그 절이 막는 실패이고, 「예」는 채운 본보기다.

## 1. 목적과 플레이어 필요

**왜**: 화면은 플레이어 쪽에서 있을 이유가 있어야 한다. 개발자 쪽(「세이브 데이터를 보인다」)으로 만든 화면은 어지럽고, 플레이어 쪽(「패드를 내려놓기 전에 진행이 안전하다고 믿게 한다」)으로 만든 화면은 목적이 또렷하다. 배치보다 먼저 쓴다 — 뒤의 모든 선택을 거르는 체다.

**플레이어 필요**: 한 문단. 시스템 기능이 아니라 사람의 필요를 쓴다. 이 화면을 열 때 플레이어가 뭐라고 말할지, 안 되면 무엇에 짜증 날지 생각한다 — 그 짜증이 필요를 말해 준다.
- 나쁜 예: 「플레이어의 아이템과 장비를 보인다.」
- 좋은 예: 「무엇을 들고 있는지 알고, 다음 만남에 무엇을 가져갈지 게임 세계의 감각을 깨지 않고 빨리 정하게 한다. 인벤토리는 행동 사이의 계획 도구다.」

**플레이어 목표**: 한 문장, 수용 기준을 쓸 수 있을 만큼. 예: 「찾는 아이템을 버튼 세 번 안에 찾고, 다른 화면으로 가지 않고 장비한다.」

**게임 목표**: 한 문장, 시스템이 이 상호작용에서 받아야 할 것. 예: 「다음 만남을 불러오기 전에 장비 선택을 기록해 전투 시스템에 넘긴다.」 보기는 좋은데 시스템을 못 돕는 UI를 막는다.

## 2. 도착할 때의 맥락

**왜**: 전투 중에 연 인벤토리와 던전을 깬 뒤 연 인벤토리는 플레이어의 머리와 마음이 다르다. 같은 구조도 한쪽에서는 버겁고 한쪽에서는 쉽다. 무엇을 먼저 보이고 숨기고 움직이고 줄일지를 추상적인 사용자가 아니라 실제로 도착하는 플레이어에 맞춘다.

**예**:

| 질문 | 답 |
|---|---|
| 방금 무엇을 했나 | 예: 전투를 끝냈다 · 탐험 중 Esc를 눌렀다 · 이야기 컷신이 열었다 |
| 감정 상태 | 예: 아슬아슬하게 살아남아 긴장 · 목표 사이를 돌아다녀 차분 |
| 머리에 담은 것 | 예: 많음 — 적 위치를 따라가는 중 · 적음 — 위협 없음 |
| 이미 아는 것 | 예: 아이템을 막 주웠지만 능력치는 아직 못 봤다 |
| 가장 하려는 것 | 예: 새 아이템이 지금 무기보다 나은지 본다 |
| 걱정 | 예: 뭔가 놓친다 · 되돌릴 수 없는 실수 · 어디 있었는지 잊는다 |

**감정 목표**(사람이 정한다): 한 문장. 예: 「자신 있고 손에 쥔 느낌 — 정보가 다 있고, 선택의 결과가 모호하지 않다.」

## 3. 내비게이션 위치

**왜**: 계층에서 자리를 모르면 들고 나는 전환 · 뒤로 버튼 · 일시정지와의 관계를 정할 수 없다. 구조 문제도 일찍 드러난다 — 여덟 곳에서 닿는 화면이면 복잡하다는 신호이니 구현이 아니라 설계에서 푼다.

**예 — 닿는 길**:

| 진입점 | 계기 | 메모 |
|---|---|---|
| 메인 메뉴 → 플레이 | 「새 게임」을 고름 | 주 진입 |
| 일시정지 메뉴 → 계속 | 플레이 중 Start | 둘째 진입 |
| 게임 사건 | 튜토리얼이 처음 한 번 강제로 연다 | 시스템 진입 — 플레이어가 닫아도 깨지지 않아야 한다 |

## 4. 들어오는 길과 나가는 길

**왜**: 두 표가 화면과 나머지 내비게이션의 약속이다. 들어오는 길마다 나가는 길이 있어야 한다. 정하지 않은 전환은 버그가 된다 — 플레이어가 갇히거나 게임 상태가 어긋난다. 구현 전에 다 채운다. 빈 칸은 설계가 덜 끝났다는 표시다.

**예 — 들어오는 길**:

| 계기 | 출발 | 전환 | 가져오는 데이터 | 메모 |
|---|---|---|---|---|
| 인벤토리 버튼 | 플레이 · 탐험 | 겹쳐 쌓기 — 게임 멈춤 | 지금 장비 · 인벤토리 내용 | 전투가 아닌 모든 상태에서 |
| 줍기 안내를 수락 | 줍기 대화상자 | 대화상자를 인벤토리로 바꿈 | 새 아이템을 미리 강조 | 열 때 새 아이템이 눈에 띄게 |
| 퀘스트가 보냄 | 퀘스트 갱신 알림 | 겹쳐 쌓기 | 강조할 아이템 id | 그 아이템으로 바로 연결 |

**예 — 나가는 길**:

| 나가는 동작 | 도착 | 전환 | 돌려주거나 저장 | 메모 |
|---|---|---|---|---|
| 닫기(뒤로 · B · Esc) | 이전 상태 — 탐험 | 겹침 빼기 — 게임 계속 | 바뀐 장비 확정 | 전환이 시작되기 전에 확정 |
| 「장비」를 고름 | 같은 화면 | 그 자리 상태 변화 | 장비 변경 사건 | 이동 없이 새로 그림 |
| 지도 단축키 | 지도 화면 | 바꾸기 | 없음 | 돌아오면 인벤토리 상태가 남아 있다 |

## 5. 배치 명세

**왜**: UX 설계와 UI 구현 사이에 넘기는 문서다. 픽셀까지 맞을 필요는 없고 무엇이 중요한지(계층) · 무엇이 함께인지(가까움) · 무엇이 크고 작은지(비율)를 전하면 된다. 글자 배치도면 설계 도구 없이 된다. 프로그래머는 짐작 없이 구조를 만들고, 아티스트는 시선의 무게를 둘 곳을 안다. 기준 해상도 하나로 그리고(예: 1920×1080) 다른 해상도의 변화는 따로 적는다.

**예 — 배치도(5.1)**:

```
┌────────────────────────────────────────┐
│ [← 뒤로]        인벤토리        [옵션] │ ← 머리 영역
├────────────────────────────────────────┤
│ ┌──────────┐  ┌─────────────────────┐  │
│ │ 분류     │  │ 상세 판             │  │ ← 내용 영역
│ │ ● 무기   │  │ 아이템 이름         │  │
│ │   방어구 │  │ {아이콘}            │  │
│ │   소모품 │  │ 능력치 비교         │  │
│ ├──────────┤  │ 설명 ...            │  │
│ │ 격자     │  └─────────────────────┘  │
│ │ {□}{□}{□}│                           │
│ │ ...      │                           │
│ └──────────┘                           │
├────────────────────────────────────────┤
│  [장비]   [버리기]   [비교]   [닫기]   │ ← 동작줄
└────────────────────────────────────────┘
```

**예 — 영역(5.2)**:

| 영역 | 내용 | 대략 크기 | 스크롤 | 넘칠 때 |
|---|---|---|---|---|
| 머리 | 위 띠 — 이동 · 제목 · 전체 동작 | 너비 전체 · 높이 약 10% | 아니요 | 긴 제목은 말줄임 |
| 분류 | 왼쪽 — 분류 탭 | 너비 약 25% | 예 — 세로 | 목록 아래에 스크롤 표시 |
| 격자 | 가운데 — 고른 분류의 아이콘 | 너비 약 45% | 예 — 세로 | 쪽 넘김(예: 4×4) |
| 상세 | 오른쪽 — 능력치와 설명 | 너비 약 30% | 예 — 긴 설명 | 아래를 흐리고 스크롤 |
| 동작줄 | 아래 — 고른 아이템의 동작 | 너비 전체 · 높이 약 15% | 아니요 | 좁아지면 아이콘만 |

**예 — 부품 목록(5.3)**:

| 부품 | 종류 | 영역 | 목적 | 꼭 있나 | 다시 쓰나 |
|---|---|---|---|---|---|
| 뒤로 버튼 | 버튼 | 머리 | 이전 화면으로 | 예 | 예 — 공통 이동 버튼 |
| 분류 탭 | 토글 버튼 | 분류 | 격자를 분류로 거름 | 예 | 아니요 — 새로 |
| 아이템 칸 | 아이콘 + 틀 | 격자 | 칸 하나(빈 칸 · 찬 칸) | 예 | 아니요 — 새로 |
| 능력치 비교 줄 | 묶음 — 이름 + 값 + 차이 | 상세 | 지금 장비와 견줌 | 예 | 아니요 — 새로 |
| 장비 버튼 | 주 버튼 | 동작줄 | 고른 아이템을 장비 | 예 | 예 — 공통 주 버튼 |
| 빈 상태 안내 | 글 + 아이콘 | 격자 | 분류에 아이템이 없을 때 | 예 | 예 — 공통 빈 상태 |

**예 — 열 때 초점**: 격자의 첫 칸. 바로 연결해 열면 강조한 아이템. 격자가 비면 첫 분류 탭.

## 6. 상태와 변형

**왜**: 화면은 그림 한 장이 아니라 상태의 묶음이다. 정상 길만 설계하면 빈 상태가 깨지고, 불러오는 표시가 안 보이고, 데이터가 없을 때 멈춘다. 이 표가 QA의 시험표다.

**예**:

| 상태 | 계기 | 보이는 변화 | 동작 변화 | 메모 |
|---|---|---|---|---|
| 불러오는 중 | 열리는 중 · 데이터 없음 | 격자에 자리 표시 · 동작 버튼 못 씀 | 닫기만 된다 | 평소에 <프로젝트 값>ms 넘게 보이면 데이터 가져오기를 살핀다 |
| 빈 상태 | 아이템 0개인 분류로 옮김 | 격자 자리에 빈 상태 안내 | 아이템 동작을 숨김 | 설명 없는 못 쓰는 버튼은 헷갈린다 — 숨긴다 |
| 채워짐 | 아이템이 하나 이상 | 칸이 차고 첫 칸에 초점 | 모든 동작 가능 | 기본 · 가장 흔함 |
| 선택됨 | 칸으로 옮김 | 상세가 차고 동작줄이 그 아이템에 맞게 바뀜 | 종류에 따라 장비 · 버리기 · 비교 | 이미 장비한 것은 장비 대신 「장비 중」 표시 |
| 버리기 확인 대기 | 버리기를 고름 | 확인 대화상자가 덮음 | 뒤 조작 멈춤 | 버린 것은 되찾을 수 없다 — 모달로 |
| 오류 | 데이터를 못 가져옴 | 「불러오지 못했다」 + 다시 시도 | 다시 시도와 닫기만 | 오류는 기록하고 기술 내용은 보이지 않는다 |
| 새로 얻음 | 줍기에서 바로 연결해 엶 | 「새것」 표시 · 상세를 미리 채움 | 선택됨과 같다 | 그 칸을 한 번 떠날 때까지 표시 |

## 7. 상호작용 지도

**왜**: 이 화면에서 입력마다 무엇이 되는지의 원본이다. 모든 입력 장치와 모든 상태(올림 · 초점 · 누름 · 못 씀)를 생각하게 한다. 접근성 점검의 입력이기도 하다 — 마우스로만 되는 동작은 키보드 · 패드 칸에서 걸린다.

**예 — 이동 입력(7.1)**:

| 입력 | 플랫폼 | 동작 | 보이는 반응 | 소리 | 메모 |
|---|---|---|---|---|---|
| 방향키 · 방향 버튼 | 모두 | 영역 안에서 초점 옮김 | 초점 표시가 옆으로 | 가벼운 이동음 | 영역 끝에서 돌고, 방향키만으로 영역을 넘지 않는다 |
| Tab · R1 | 키보드 · 패드 | 다음 영역으로 | 다음 영역의 첫 부품으로 | 영역 바뀜 소리 | Shift+Tab · L1은 거꾸로 |
| 마우스 올림 | PC | 올림 상태 | 밝기 · 밑줄 | 없음 | 올림은 초점을 옮기지 않는다 — 클릭만 옮긴다 |
| 터치 탭 | 모바일 | 한 번에 고르고 실행 | 눌림 물결 | 가벼운 클릭 | 위험이 낮은 동작만 탭 한 번에 실행 · 되돌릴 수 없는 동작은 따로 확인 |

**예 — 동작 입력(7.2)**:

| 입력 | 초점 | 동작 | 반응 | 애니메이션 | 소리 | 메모 |
|---|---|---|---|---|---|---|
| Enter · A · 왼쪽 클릭 | 아이템 칸 | 고르고 상세를 채움 | 상세가 바뀜 | 예: 120ms 페이드 | 선택음 | 이미 골랐으면 아무 일 없음 |
| Enter · A | 장비 버튼 | 장비 | 「장비 중」 표시가 옮겨 감 | 예: 80ms | 장비 성공음 | 인벤토리 시스템에 장비 사건 |
| Y · 오른쪽 클릭 | 아이템 칸 | 문맥 메뉴 | 칸 옆에 메뉴 | 예: 80ms | 메뉴 열림음 | 장비 · 버리기 · 살펴보기 · 비교 |
| Esc · B · 뒤로 | 화면 전체 | 닫고 이전 상태로 | 나가는 전환 | 예: 200ms | 뒤로 소리 | 닫기 전에 모두 확정 — 인벤토리는 초안이 아니다 |

**예 — 상태별 제한(7.3)**: 불러오는 중 — 아이템 · 동작 입력을 모두 막는다(다룰 데이터가 없고 경합을 막는다). 확인 대화상자가 열림 — 확인과 취소만(모달이라 뒤가 잠긴다). 오류 — 다시 시도와 닫기만(옮겨 다닐 데이터가 없다).

## 8. 데이터 요구

**왜**: UI와 게임 상태의 경계가 게임 UI에서 가장 중요한 구조 경계다. UI는 데이터를 읽고 주인이 아니며, 사건을 보내고 상태를 직접 쓰지 않는다. 구현 전에 채우면 두 실패를 막는다 — UI 개발자가 건드리면 안 될 시스템을 건드리는 것, 시스템이 UI가 반쯤 만들어질 때까지 데이터를 내놓아야 하는 줄 모르는 것.

**예**:

| 데이터 | 출처 · 주인 | 갱신 | 형식 | 없을 때 |
|---|---|---|---|---|
| 아이템 목록 | 인벤토리 시스템 | 열 때 · 인벤토리 바뀜 사건 | 아이템 배열(id · 이름 · 아이콘 · 분류 · 능력치 · 장비 여부) | 빈 배열 → 빈 상태. null은 없다 — 시스템이 배열을 돌려준다 |
| 지금 장비 | 장비 시스템 | 열 때 · 장비 바뀜 사건 | 칸 → 아이템 id | 빈 칸은 null — 빈 칸 아이콘 |
| 능력치 비교 | 능력치 시스템 | 선택이 바뀔 때 | 능력치 이름 → 지금 · 새 값 · 차이 | 선택이 없으면 상세에 자리 표시 |
| 가진 돈 | 경제 시스템 | 열 때만 — 실시간 아님 | 정수 | 이 모드에 경제가 없으면 줄을 숨김 |

## 9. 보내는 사건

**왜**: UI와 시스템 경계의 다른 반쪽이다. 8절이 UI가 읽는 것이면 이 절은 UI가 게임에 돌려 말하는 것이다. 설계 때 사건을 정하면 UI 프로그래머가 게임 규칙을 짜지 않고, 게임 프로그래머가 UI의 동작에 놀라지 않는다.

**예**:

| 동작 | 사건 | 값 | 받는 시스템 | 메모 |
|---|---|---|---|---|
| 장비 | 장비 요청 | 아이템 id · 목표 칸 | 장비 시스템 | 시스템이 확인하고 성공하면 장비 바뀜 사건을 낸다 — UI는 그것을 듣고 고친다 |
| 버리기 | 버리기 요청 | 아이템 id · 개수 | 인벤토리 시스템 | 확인 대화상자를 수락한 뒤에만 |
| 비교 열기 | 비교 열림 | 아이템 둘의 id | 분석 | 게임 상태 변화 없음 — 분석 전용 |
| 화면 닫기 | 화면 닫힘 | 머문 시간 | 분석 | 이유와 상관없이 닫을 때마다 |

## 10. 전환과 애니메이션

**왜**: 전환은 꾸밈이 아니라 계층과 인과를 전한다. 오른쪽에서 들어오면 앞으로 간 것이고, 페이드는 맥락이 끊긴 것이다. 전환이 들쭉날쭉하면 맞게 동작해도 깨진 느낌이 난다. 개발자 재량에 맡기지 않고, 움직임 줄이기를 처음부터 계획한다.

**예**:

| 전환 | 방식 | 길이 | 끊을 수 있나 | 움직임 줄이기에서 |
|---|---|---|---|---|
| 화면 들어옴 | 오른쪽에서 미끄러져 | 예: 250ms · ease-out | 아니요 — 끝나야 조작된다 | 바로 나타남 |
| 화면 나감(뒤로) | 오른쪽으로 | 예: 200ms · ease-in | 아니요 | 바로 사라짐 |
| 상세 바뀜 | 내용 교차 페이드 | 예: 120ms | 예 — 빨리 옮기면 앞 것을 끊는다 | 바로 바꿈 |
| 버튼 누름 | 누를 때 작아지고 뗄 때 돌아옴 | 예: 60ms · 60ms | 예 — 일찍 떼면 돌아옴 | 그대로 둔다 — 손맛 피드백이지 꾸밈이 아니다 |
| 확인 대화상자 열림 | 뒤를 어둡게 · 대화상자가 커짐 | 예: 150ms | 아니요 | 커지지 않고 바로 |

## 11. 입력 장치별 점검

**왜**: 입력 장치를 다 덮는 것은 고를 일이 아니다. 대상 플랫폼의 인증 요구나 시장의 접근성 법규와 걸릴 수 있다 — 어느 요구가 걸리는지는 그 플랫폼 · 시장의 최신 공식 문서로 확인할 질문으로 남긴다. 「검토 통과」 전에 채우고, 실패나 못 봄이 남으면 구현을 시작하지 않는다.

## 12. 접근성

**왜**: 접근성은 설계 때 정해야 한다 — 나중에 끼우면 비싸고 구조상 안 되는 일이 많다. 이 절은 이 화면만의 요구다. 프로젝트 전체 기준은 접근성 요구 문서에 있으니 먼저 읽고 겹치거나 어긋나지 않게 한다.

**예 — 글자 대비**: 상세의 아이템 이름(어두운 판) · 안 고른 분류 탭(중간 회색) · 고른 탭(강조색) · 동작 버튼 이름(상태마다 다른 색) · 능력치 차이(초록에만 기대지 않는다). 필요 비율은 모두 접근성 요구 문서의 <프로젝트 값>이고, 잰 비율은 구현 뒤에 적는다. 그 값이 어느 외부 기준의 어느 조항인지는 확인할 질문이다.

**예 — 색약 대책**:

| 부품 | 위험 | 대책 |
|---|---|---|
| 능력치 차이(빨강 · 초록 = 나빠짐 · 좋아짐) | 적록 색약 | ↑ · ↓ 화살표와 + · − 앞붙임을 색과 함께 쓴다. 색은 보조다 |
| 희귀도 색(회색 · 초록 · 파랑 · 보라 · 주황) | 여러 색약 | 아이콘 아래에 희귀도 이름. 색은 보조다 |

**예 — 초점 순서**: 1 뒤로 → 2 옵션 → 3~6 분류 탭 → 7~ 격자 칸(왼쪽 → 오른쪽, 위 → 아래) → 장비 · 버리기 · 비교 · 닫기 → 다시 뒤로. 상세 판에는 초점이 들어가지 않는다 — 칸 초점에 따라 바뀌는 보기 판이다.

**예 — 화면 낭독기 안내**:

| 상태 변화 | 안내 글 | 언제 |
|---|---|---|
| 화면 열림 | 「인벤토리. 아이템 N개. <분류> 선택됨.」 | 초점이 자리 잡을 때 |
| 칸에 초점 | 「<이름>. <분류>. <희귀도>. <주요 능력치>. <장비 여부>.」 | 초점이 올 때 |
| 장비 | 「<이름>을 <칸>에 장비했다.」 | 장비 바뀜 사건이 확인된 뒤 |
| 빈 상태 | 「<분류>에 아이템이 없다.」 | 빈 상태가 그려질 때 |

**인지 부담 쓰는 법**: 플레이어가 이 화면을 쓰며 동시에 따라가는 정보 흐름을 센다. 예: (1) 격자 위치 (2) 상세 능력치 (3) 견줄 지금 장비 (4) 할 수 있는 동작 (5) 분류 — 다섯. 프로젝트가 정한 기준이 있으면 견주고 줄일 방법을 적는다. 예: 옮기면 상세가 저절로 바뀌어 직접 찾아볼 일이 없고, 비교를 저절로 보여 고를 일을 줄인다. 원문의 「7±2」 같은 수를 모든 게임의 한계로 쓰지 않는다 — 기준이 필요하면 프로젝트가 플레이 시험으로 정한다.

## 13. 현지화

**왜**: 현지화를 생각하지 않고 만든 UI는 첫 번역에서 깨진다. 영어보다 길어지는 언어(원문은 독일어를 예로 든다), 배치를 뒤집어야 하는 아랍어 · 히브리어, 훨씬 짧아 빈 곳이 생기는 일본어 · 중국어가 있다. 미리 계획하면 싸고, 만든 뒤 고치면 비싸다. 글마다 최대 글자 수와 넘칠 때의 계획을 둔다. 늘어나는 폭은 목표 언어로 실제로 재서 정한다.

**예**:

| 글 | 기준 길이 | 최대 | 폭 | 뒤집기 | 넘칠 때 | 위험 |
|---|---|---|---|---|---|---|
| 화면 제목 「INVENTORY」 | 9자 | 16자 | 78% | 오른쪽 또는 가운데 | 말줄임 — 핵심 내용이 아니다 | 낮음 |
| 아이템 이름 | 평균 약 15자 · 최대 약 35자 | 50자 | 43% | 오른쪽 정렬 | 말줄임 + 올림 · 초점 때 전체 이름 | 중간 — 판타지 이름은 길다 |
| 아이템 설명 | 약 80~120자 | 200자 | 67% | 오른쪽 정렬 · 줄바꿈 | 상세 판 안에서 스크롤 | 낮음 |
| 버튼 「Equip」 | 5자 | 14자 | 180% | 버튼 배치를 뒤집음 | 글자를 <프로젝트 값>까지 줄인 뒤 말줄임 | 중간 — 독일어 「Ausrüsten」은 9자 |
| 분류 탭 「Consumables」 | 11자 | 18자 | 64% | 탭 위치를 뒤집음 | 언어별 줄임말을 현지화 파일에 | 높음 |

## 14. 수용 기준

**왜**: 수용 기준은 「끝」의 약속이다. 없으면 개발자가 끝났다고 할 때 끝이고, 있으면 시험자가 목록을 다 확인할 때 끝이다. 디자이너에게 묻지 않고 확인되게, 통과나 실패로 갈리게 쓴다.

**예**(화면에 맞춘 것 · 따로 확인되는 것):
- 아이템 사이를 옮겨도 눈에 띄는 프레임 떨어짐이 없다(목표 프레임 ± <프로젝트 값>)
- 모든 상태(불러오는 중 · 빈 · 채워짐 · 오류 · 확인)가 바르게 보인다
- 모든 칸이 차도 격자가 프레임 떨어짐 없이 스크롤된다
- 닫고 다시 열어도 인벤토리 변화가 남아 있다
- 열린 동안 다른 시스템이 보낸 인벤토리 바뀜 사건에 멈추지 않는다
- 능력치 비교가 색만으로 구분하지 않는다
- 화면 낭독기가 초점 때 아이템 이름과 주요 능력치를 읽는다(플랫폼 낭독기로 확인)

## 15. 열린 질문

**예**:

| 질문 | 맡은 역할 | 언제까지 | 결론 |
|---|---|---|---|
| 비교를 늘 보일까, 비교 버튼을 누를 때만 보일까 | UX 디자이너 | 예: 격자 구현 시작 전 | 미정 — 게임 내용이라 사람에게 올린다 |
| 격자에서 패드 자유 커서를 쓰나, 방향 버튼 이동만인가 | 리드 프로그래머 + UX 디자이너 | 예: 입력 방식 구조 결정 기록(ADR) 뒤 | 미정 — 그 결정에 달림 |
| 버린 아이템은 사라지나, 세계에 떨어지나 | 시스템 디자이너 | 인벤토리 기획서를 고친 뒤 | 막힘 — 기획서 예외 상황 절이 비어 있음 |
| 인벤토리 크기에 상한이 있나, 끝없이 스크롤인가 | 경제 디자이너 | 예: 경제 모델 확정 전 | 미정 |
