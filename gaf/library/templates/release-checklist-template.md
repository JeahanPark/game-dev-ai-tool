> **쓰는 법** — 누가 채우나: 릴리스 매니저(점검과 합치기) · 열린 버그와 시험 칸은 QA 리드 · 언제: 출시 후보 빌드가 나온 뒤 · 줄여도 되는 절: 이 게임에 없는 것(서버 · 분석 · 업적 · 결제 · 지역별 가격 등)의 줄은 지우지 말고 「해당 없음(이유)」으로 둔다 · 사람이 정할 것: 대상 기기 · 상점 · 지원 언어를 아직 안 정했을 때 · 출시 · 배포 · 상점 제출 · 공지 게시(되돌리기 어려운 일) · 막는 항목을 받아들이고 내는 것.
>
> 총괄은 이 글과 함께 `templates/release-platform-requirements`와 대상 상점마다 필요한 인증 블록(`templates/certification-console` · `templates/certification-steam` · `templates/certification-itch` · `templates/certification-none`, 대상 미정이면 `templates/certification-unknown`)을 꺼낸다. `gaf library take <칸>/<id>…`로 꺼낸 프로젝트 문서 경로(기본 `docs/서랍/<칸>/<id>.md`)를 맡기는 글에 적는다.
>
> 정식 출시는 출시 준비표(`templates/launch-checklist`) · 판마다는 출시 점검표(`templates/release-checklist-template`) — 겹치는 줄은 출시 점검표의 결과를 옮긴다.
>
> 판정 칸에는 넷 가운데 하나를 쓴다: 통과 · 실패 · 못 봄 · 해당 없음. 아직 정하지 않은 조건은 「못 봄 — 아직 안 정함」으로 적는다. 근거 칸에는 증거나 사람의 답(누가 · 언제)을 적고, 해당 없음에는 이유를 적는다. 비어 있는 칸을 「해당 없음」으로 읽지 않는다.
>
> 상점 · 콘솔의 인증 · 등급 요구는 이 표가 정하지 않는다. 「최신 공식 요구를 확인했나(언제 · 어디서)」 칸으로 남기고, 이 표를 인증 기준으로 쓰지 않는다. 이 점검표의 판정은 출시 결정이 아니다. 채운 문서에서는 이 칸을 지운다.

# 출시 점검표 — <판> · <플랫폼>

만든 날: <날짜>

## 코드 상태

| 항목 | 값 |
|---|---|
| 훑은 소스 파일 | <N개 — 못 훑었으면 「못 봄 — 이유」> |
| TODO 수 | <N — 많으면 위 다섯 개> |
| FIXME 수 | <N — 모두 적는다 · 막는 항목 후보> |
| HACK 수 | <N — 모두 적는다 · 검토 필요> |

훑은 파일이 0개면 「0건」은 결과가 아니라 못 봄이다.

## 빌드 확인

| 항목 | 판정 | 근거 · 이유 |
|---|---|---|
| 모든 대상 플랫폼에서 깨끗한 빌드가 된다 | | |
| 컴파일 경고가 프로젝트의 경고 기준 안이다(<프로젝트 값 — 예: 경고 0>) | | |
| 모든 에셋이 들어 있고 바르게 불러진다 | | |
| 빌드 크기가 예산 안이다(<프로젝트 값>) | | |
| 빌드 판 번호가 맞다(<판>) | | |
| 사람이 정한 기준 지점(태그 등)에서 빌드를 다시 만들 수 있다 — 기준 지점은 확인만 한다 | | |

## 품질 관문

열린 버그: S1 <N> · S2 <N> · S3 <N> — 버그 기록이 없으면 「못 봄 — 버그 기록 없음」(0건이 아니다)

| 항목 | 판정 | 근거 · 이유 |
|---|---|---|
| 열린 S1(치명) 버그 0건 | | |
| 열린 S2(높음) 버그 — 프로젝트의 엄격함대로 <막음 · 근거에 위험으로 적음> | | |
| 열린 S3(보통) 버그 — 같은 방식 <막음 · 근거에 위험으로 적음> | | |
| 핵심 경로 기능을 모두 시험했고 QA 판정이 있다 | | |
| 성능 — 최소 사양 기기에서 목표 프레임(<프로젝트 값>) | | |
| 성능 — 메모리 사용이 예산 안(<프로젝트 값>) | | |
| 성능 — 불러오기 시간이 예산 안(<프로젝트 값>) | | |
| 성능 — 오래 플레이해도 메모리 누수 없음 | | |
| 직전 빌드 대비 회귀 없음 | | |
| 장시간 시험 통과(<프로젝트 값> 연속 플레이 — 장시간 시험 기록의 판정) | | |

> 막는 항목은 우회 방법도 받아들인 위험도 없는 실패 전부다. S2 · S3의 예외를 허용하는지는 프로젝트가 정하고, 허용한 경우 우회 방법이나 위험을 받아들인 사람(누가 · 언제)을 조건 목록에 적는다. 버그 등급 밖의 빌드 · 내용 · 상점 등도 같은 기준으로 본다.

## 기기별 항목

## 인증

<대상 상점마다 하나씩 인증 블록을 옮겨 붙인다 — 콘솔 인증 점검(`templates/certification-console`) · Steam 출시 점검(`templates/certification-steam`) · itch.io 출시 점검(`templates/certification-itch`) · 인증 해당 없음 기록(`templates/certification-none`) 가운데 대상의 것. 대상 상점 · 플랫폼을 아직 안 정했으면 인증 대상 미정 기록(`templates/certification-unknown`).>

## 출시 준비

| 항목 | 판정 | 근거 · 이유 |
|---|---|---|
| 분석 · 원격 수집이 데이터를 받는지 확인 | | |
| 충돌 보고가 설정되고 결과 화면에 들어갈 수 있다 | | |
| 첫날 패치를 준비하고 시험했다(필요할 때) | | |
| 출시 직후 당번 일정(<프로젝트 값 — 예: 첫 72시간>) | | |
| 출시 공지 초안 — 게시는 사람이 한다 | | |
| 보도 · 인플루언서용 키 배포 준비 — 배포는 사람이 정한다 | | |
| 지원 담당에게 알려진 문제와 자주 묻는 질문을 알렸다 | | |
| 출시 뒤 큰 문제가 나면 쓸 되돌릴 계획을 적었다 | | |

## 출시 판정: <통과 · 못 봄 · 실패>

먼저 맞는 것이 이긴다: 항목 · 절에 실패가 하나라도 있으면 **실패** · 실패가 없고 못 봄(「못 봄 — 아직 안 정함」 포함)이 하나라도 있으면 **못 봄**(하나하나 이름을 적는다) · 아니면 **통과**. 기록된 우회 방법을 확인했거나 사람이 위험을 받아들여 진행하기로 정한 항목은 「통과 + 조건 목록」으로 적는다. 그 밖의 실패는 실패로 남긴다. 조건 목록은 합칠 때도 남긴다. 근거 없이 빈 항목은 못 봄이다. 합치는 순서는 `rules/verdicts`를 따른다.

이 판정은 출시 결정이 아니다. 출시 · 배포 · 상점 제출은 사람이 정한다.

**근거:**
<준비 상태의 요약. 출시 전에 풀어야 할 막는 항목을 적는다. 실패면 풀어야 할 항목과 걸릴 시간 추정을 적는다. 막지 않기로 한 열린 S2 · S3는 여기에 위험으로 적는다.>

| 검토한 역할 | 본 것 | 판정(통과 · 실패 · 못 봄 · 해당 없음) | 근거 |
|---|---|---|---|
| <예: QA 리드> | 품질 관문 · 시험 | | |
| <예: 테크니컬 디렉터> | 빌드 · 기술 위험 | | |
| <예: 프로듀서> | 일정 · 전체 준비 | | |
| <예: 크리에이티브 디렉터> | 내용 · 경험 | | |

이 출시에 걸린 역할만 넣는다. 모든 직군의 서명을 받는 표가 아니다.

사람이 정한 것: <누가 · 언제 · 무엇 — 예: 출시함 · 미룸 · 막는 항목을 받아들이고 냄>
