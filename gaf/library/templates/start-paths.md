> **쓰는 법** — 누가 채우나: 총괄 · 언제: 새 프로젝트를 시작할 때, 이미 해 둔 것이 있는 프로젝트를 들일 때, 무게를 바꿀 때 · 줄여도 되는 절: 고른 길이 아닌 길의 절은 지운다(고른 길 하나만 남긴다) · 사람이 정할 것: 엔진(되돌리기 어려운 결정이다)과 돈이 드는 도구, 한 장 기획의 게임 내용. 무게 · 걸음 고르기는 총괄이 정한다. 채운 문서에서는 이 칸을 지운다.
>
> 고정된 단계 순서 · 명령 목록은 없다. 무게는 「꼭 있어야 할 문서」를 바꿀 뿐, 쓸 수 있는 틀 · 절차를 막지 않는다. 고르는 근거는 파일 개수가 아니라 일의 위험과 이미 있는 결과물(돌려 본 결과)이다.

# 시작 길 — <프로젝트 이름>

## 지금 어디인가
- 이미 있는 것: <한 장 기획 · 기획 문서 · 코드 · 시제품 — 경로와 함께, 없으면 「없음」>
- 엔진: <정함 — 이름 · 판 · 사람이 정한 날 | 안 정함>
- 고른 무게: <가볍게 | 보통 | 무겁게> — 까닭: <일의 크기 · 위험 · 이미 있는 자료로 한 줄>

## 고르는 길

### 가볍게 — 돌아가는 코드까지 네 걸음
1. 엔진 정하기 — 사람이 정한다
2. 한 장 게임 기획 쓰기
3. 기획의 기능 목록을 맡길 일 카드로 나누기(큰 묶음 · 작업 묶음 계획 없이)
4. 첫 맡길 일 — 첫 게임 코드

엔진을 아직 안 정했으면, 한 장 기획을 바로 해 볼 수 있는 시제품으로 먼저 만들고 엔진은 그 뒤에 정할 수 있다 — 해 볼 수 있는 것이 먼저, 엔진이 나중. 이 길을 고르면 2 바로 뒤에 시제품을 다음 걸음으로 적는다.

### 보통 · 무겁게
<이 프로젝트가 쓸 것만 골라 차례대로 적는다. 아래는 고를 수 있는 것의 예다 — 단계 이름과 묶음은 프로젝트가 정한다>
- 구상: 엔진 정하기 → 한 장 기획 · 구상서 → 시제품 → 아트 기준서 → 시스템 목록
- 시스템 설계: 시스템마다 기획서 → 기획서 전체 검토
- 구조: 구조 설계 → 결정마다 구조 결정 기록 → 구조 검토 → 규칙 추리기 → 접근성 요구 · 상호작용 패턴 → 시험 준비
- 제작 전: 화면 명세(HUD · 핵심 화면) → 큰 묶음 → 맡길 일 카드 → 작업 묶음 계획(쓰면)
- 제작: 맡길 일을 하나씩
- 무겁게는 더해서: 제작 전의 대표 구간 보고서 · 플레이 시험 보고, 기획서마다 기획 검토

묶음 사이에 점검을 두면, 점검이 「통과」일 때만 다음 묶음으로 간다. 「못 봄」은 통과가 아니다.

### 이미 해 둔 것이 있을 때
<기획 문서나 코드가 이미 있으면 이 길로. 해당하는 걸음만 적는다. 있는 기획 문서로 시제품을 먼저 만들 수 있으면 그것을 1 앞에 둔다>
1. 프로젝트 상태 보고 — 지금 어디인가 · 무엇이 빠졌나
2. 도입 점검 — 있는 문서가 서랍의 틀이 읽는 꼴인가
3. 엔진 정하기 — 엔진이 이미 정해졌으면 뺀다
4. 한 장 기획 — 구상이 없을 때만. 코드가 이미 게임을 담고 있으면(돌려 보고 판단한다) 한 장 게임 기획(`templates/game-brief`)을 코드에서 거꾸로 채우고, 아니면 새로 쓴다. 둘 중 하나만 적는다

보통 · 무겁게라면 1~3 뒤에: 있는 시스템마다 구현에서 뽑은 기획서 · 코드에서 뽑은 구조 기록 → 구조 검토 → 점검.
