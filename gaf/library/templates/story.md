> **쓰는 법** — 누가 채우나: 총괄이 「끝났을 때 채우는 칸」 앞까지 채워 맡기고, 맡은 역할이 끝났을 때 그 칸을 채운다. 시험 명세는 QA 역할이 맡기기 전에 쓴다 · 언제: 역할에게 일 하나를 맡길 때마다 · 줄여도 되는 절: 작은 일은 목표 · 범위 밖 · 수용 기준(증거 포함) · 검사 명령 · 끝났을 때 채우는 칸만 남긴다. 맥락 · 구현 메모 · 시험 명세는 기획 문서나 구조 결정이 없는 일이면 「해당 없음 — 까닭」 한 줄 · 사람이 정할 것: 범위에 게임 내용(규칙 · 그림 · 이야기)을 더하는 것, 역할이 스스로 정한 것 가운데 게임 내용인 것, 느낌 기준을 사람이 해 보는 것. 그 밖(쪼개는 법 · 순서 · 닫기)은 총괄이 정한다. 채운 문서에서는 이 칸을 지운다.
>
> 빈 칸은 「없음」이 아니라 「확인 안 함」이다. 없으면 「없음」, 해당하지 않으면 「해당 없음 — 까닭」이라고 적는다. 역할이 자기 일을 스스로 「끝」으로 닫지 않는다 — 닫기는 총괄이 증거를 보고 한다.

# 일 <번호>: <일 이름>

> 묶음: <이 일이 속한 큰 묶음, 없으면 「없음」>
> 상태: <준비 | 막힘 — 까닭(예: ADR-<번호>가 제안 상태) | 하는 중 | 검토 대기 | 끝>
> 계층: <프로젝트가 정한 한 벌 — 예: 바탕 · 핵심 · 기능 · 표현 · 다듬기>
> 종류: <로직 · 통합 · 보기와 느낌 · UI · 설정과 데이터> — 섞이면 구현 위험이 큰 쪽. 종류가 아래 「증거」를 정한다
> 예상 크기: <S | M | L — 제안이고 바꿀 수 있다. 시간으로 적으면 사람의 시간인지 AI가 도는 시간인지 밝힌다>
> 맡은 역할: <역할 이름>
> 붙인 규칙의 판: <이 카드에 붙인 규칙 목록의 날짜 · 반영한 결정 번호, 없으면 「해당 없음」>
> 마지막 갱신: <날짜 — 맡은 역할이 구현을 시작할 때 적는다>

## 수용 기준

<이 일 범위의 기준. 기획 문서에서 따오고 지어내지 않는다. 한 장 기획만 있으면 그 기획의 목표 · 기능 항목에서 구체적인 문장으로 만든다. 확인할 수 있는 문장으로 쓴다 — 「점프를 만든다」가 아니라 「누르고 있으면 <프로젝트 값>초 안에 <프로젝트 값> 단위까지 오른다」. 느낌 기준 말고는 「좋아 보인다」 같은 판단을 쓰지 않는다>

| 번호 | 기준 | 닫는 증거 | 증거를 둘 곳 |
|---|---|---|---|
| AC-1 | <기준 문장> | <자동 시험 / 실행해서 찍은 그림 / 사람이 해 봄 / 스모크> | <경로> |
| AC-2 | <기준 문장> | <...> | <경로> |
| AC-3 | <성능 기준이 있으면 — 기준값은 <프로젝트 값>> | <측정 명령과 결과> | <경로> |

## 구현 메모

<다스리는 결정의 구현 지침에서 따온 것. 뜻이 바뀌게 풀어쓰지 않는다. 구현 역할은 결정 글 대신 이곳을 읽는다. 결정에 없는 지침은 지어내지 않는다. 결정이 안 다룬 구조 선택은 정하지 말고 계획만 보고한다. 엔진 구현은 프로젝트의 엔진 참조 문서를 따른다>

## 범위 밖

*옆 일이 맡는다 — 여기서 구현하지 않는다:*

- <일 번호>: <그 일이 맡는 것>

## 시험 명세

<QA 역할이 맡기기 전에 쓴다. 명세가 없으면 「시험 명세 아직 없음 — 수용 기준대로 구현한다」라고 적는다. 구현 역할은 시험을 더 써도 되지만 수용 기준을 바꾸지 않는다. 시험을 통과시키려고 값을 특수 처리하지 않는다>

**로직 — 자동 단위 시험 / 통합 — 통합 시험 또는 기록된 플레이 시험 명세:**

- **AC-1**: <기준 문장>
  - 전제: <시작 조건>
  - 행동: <무엇을 하나>
  - 기대: <무엇이 맞아야 하나>
  - 경계값 · 예외 상황: <한계값 · 실패 상태>

**보기와 느낌 · UI — 눈과 손으로 보는 절차:**

- **AC-1**: <기준 문장>
  - 준비: <그 상태에 어떻게 가나 — 그 장면으로 곧장 여는 법>
  - 볼 것: <무엇을 보나>
  - 통과 조건: <누가 봐도 갈리지 않는 통과 설명>

## 증거

**종류:** <종류>
**종류가 정하는 최소 증거**(`roles/qa-lead`의 기준 — 프로젝트 기준이 따로 있으면 그쪽을 따르되 UI · 보기와 느낌의 화면 캡처는 빼지 않는다):

| 종류 | 기준을 닫는 증거 | 수준 |
|---|---|---|
| 로직 | 자동 단위 시험 | 막는 것 |
| 통합 | 통합 시험 또는 기록된 플레이 시험 | 막는 것 |
| 보기와 느낌 | 남긴 화면 캡처 + 검토 확인 기록 | 막는 것 |
| UI | 건드린 화면마다 남긴 화면 캡처 | 막는 것 |
| 설정과 데이터 | 기본 동작 확인 통과 | 권고 |

「막는 것」은 증거가 없으면 끝으로 두지 않는다. 「권고」는 없으면 보고에 적되 끝을 막지 않는다.

- 「시험 파일이 있다」는 「시험이 통과했다」가 아니다. 맡길 때 정한 검사 명령이 실제로 통과해야 덮인 것이다.
- 그림은 연 사람이 거기서 본 것만 적는다. 안 연 그림을 묘사하지 않는다. 증거를 찍은 뒤 관련 파일이 바뀌었으면 그 기준은 「못 봄 — 증거를 얻은 뒤 변경됨」으로 돌린다.
- 사람이 나중에 해 보겠다고 한 기준은 「못 봄 — 사람이 해 볼 예정」으로 적고, 확인 전에는 그 기준을 완료로 세지 않는다.

## 끝났을 때 채우는 칸

*맡은 역할이 채운다. 총괄과 검토 역할이 이것으로 닫기 점검을 한다.*

### 실제 바뀐 파일

<이 일로 실제로 만들거나 고친 파일만 — 작업 폴더 전체의 변경을 적지 않는다(다른 역할의 일이 섞인다)>

- <경로> — <무엇을 바꿨나>

### 기준별 판정

| 기준 | 판정(통과 · 실패 · 못 봄 · 해당 없음) | 증거 경로 | 메모 |
|---|---|---|---|
| AC-1 | <판정> | <경로> | <못 봄 · 해당 없음이면 까닭> |
| AC-2 | <판정> | <경로> | <...> |

- 검사 명령: <돌린 명령 · 종료 코드 · 실패한 줄> — 돌리지 못했으면 「못 봄 — 까닭」
- 실행 결과: <봄 — 본 것(그림 경로) / 못 봄 — 까닭 / 해당 없음 — 까닭> 한 줄(「로직이라서」는 해당 없음의 까닭이 못 된다)

### 역할이 스스로 정한 것

<카드와 기획이 말하지 않았는데 역할이 정한 값 · 타이밍 · 색 · 화면 글자 · 아무도 안 정한 경우. 한 줄에 하나, 어디에 있는지와 함께. 게임 내용인 것은 총괄이 사람에게 올린다. 없으면 「없음」>

- <무엇을 · 어떻게 정했나> — <파일 · 줄>

### 남은 것

- <못 한 것 · 범위 밖이라 안 고친 것(누구 몫인지 · 무엇이 필요한지) · 알게 된 위험, 없으면 「없음」>
