# 시스템 기획서 길잡이

틀은 모든 시스템 기획서가 시작하는 뼈대다. 절마다 「(아직 안 씀)」이 들어 있고, 그 표시가 남은 절은 아직 안 쓴 것으로 읽는다. 이 길잡이는 절을 쓸 때 무엇을 넣고 어떤 표와 칸을 쓰는지 말한다. 틀의 절 제목 차례대로 되어 있다.

## 머리 정보
- **상태**: `설계 중`(뼈대의 값) · `설계됨` · `검토 중` · `고칠 것 있음` · `확정`(사람이 정함) · `구현됨` 가운데 하나.
- **쓴 이**: 쓴 역할이나 사람.
- **고친 날**: 마지막으로 고친 날.
- **맞춰 본 날**: 지금 설계와 맞는지 마지막으로 확인한 날.
- **섬기는 기둥**: 이 시스템이 받치는 게임 기둥.

## 요약
2~3문장: 이 시스템이 무엇이고, 플레이어에게 무엇을 해 주고, 왜 이 게임에 있나. 다른 역할이 여러 기획서를 훑을 때 이 절을 보고 더 읽을지 정한다. 전문 용어를 쓰지 않는다.

그 아래 **한눈에** 줄을 채운다: 층 · 우선순위 · 주요 의존.

## 개요
이 프로젝트를 전혀 모르는 사람에게 설명하는 한 문단. 무엇이고, 플레이어가 무엇을 하고, 왜 있나.

## 플레이어 환상
이 메커닉을 쓸 때 플레이어가 무엇을 느껴야 하나. 어떤 감정이나 힘의 환상을 섬기나. 아래의 모든 세부 결정을 이 절이 이끈다. 게임 내용이므로 사람의 말에서 가져오고, 사람이 말하지 않았으면 「(추측)」으로 표시한다.

## 자세한 설계
### 핵심 규칙
흐리지 않은 규칙. 프로그래머가 묻지 않고 구현할 수 있어야 한다. 차례가 있는 과정은 번호 목록, 성질은 점 목록으로 쓴다.

### 상태와 바뀜
상태가 있는 시스템이면(예: 무기 상태 · 상태 이상 · 단계) 모든 상태와 가능한 모든 바뀜을 적는다.

| 상태 | 들어가는 조건 | 나가는 조건 | 하는 일 |
|---|---|---|---|

### 다른 시스템과 주고받는 것
전투 · 인벤토리 · 성장 · UI와 어떻게 주고받나. 하나마다 경계를 적는다: 무엇이 들어오고 무엇이 나가며, 무엇을 누가 맡나(그 값의 주인이 어느 시스템인가).

## 공식
이 시스템이 쓰는 모든 공식. 공식마다 아래 꼴로 쓴다.

### <공식 이름>

```
결과 = 기본값 * (1 + 보정합) * 배율
```

| 변수 | 형 | 범위 | 어디서 오나 | 설명 |
|---|---|---|---|---|
| 기본값 | 실수 | <예: 1~100> | 데이터 파일 | 보정 전 기본 양 |
| 보정합 | 실수 | <예: -0.9~5.0> | 계산 | 켜진 보정을 모두 더한 값 |
| 배율 | 실수 | <예: 0.5~2.0> | 데이터 파일 | 단계에 따른 배율 |

**나올 값의 범위**: <최소> ~ <최대>
**예외**: <예: 보정합이 -0.9보다 작으면 -0.9로 묶어 결과가 음수가 되지 않게 한다>

## 예외 상황
드문 상황에서 무엇이 일어나는지 분명히 적는다. 상황마다 분명한 결론이 있어야 한다.

| 상황 | 일어날 일 | 이유 |
|---|---|---|
| <X가 0이면?> | <이렇게 된다> | <이 이유로> |
| <두 효과가 동시에 일어나면?> | <우선 규칙> | <설계 이유> |

## 의존
이 메커닉이 기대는 시스템과 이 메커닉에 기대는 시스템을 모두 적는다.

| 시스템 | 방향 | 무엇에 기대나 |
|---|---|---|
| <예: 전투> | 이것이 전투에 기댄다 | 피해 계산 결과가 필요하다 |
| <예: 인벤토리> | 인벤토리가 이것에 기댄다 | 아이템 효과 자료를 준다 |

## 조절값
균형을 맞추려고 바꿀 수 있어야 하는 모든 값. 지금 값 · 안전한 범위 · 끝으로 가면 일어나는 일을 적는다.

| 조절값 | 지금 값 | 안전한 범위 | 올리면 | 내리면 |
|---|---|---|---|---|

|---|---|---|---|

## 조작감
> **그림 · 소리 요구와 따로 두는 이유**: 그림 · 소리 요구는 어떤 반응 사건이 있는지(사건과 자산의 표)를 적는다. 조작감은 메커닉을 다룰 때 어떻게 느껴지는지 — 반응 속도 · 무게 · 딱 떨어짐 · 몸으로 느끼는 결 — 를 적는다. 시간 · 프레임 · 손에 오는 감각의 설계 목표다. 애니메이션 예산 · 입력 처리 구조 · 판정 시간을 정하므로 설계할 때 정한다. 구현 뒤에 맞추면 비싸고, 바탕부터 다시 해야 할 때가 많다.

아래 여섯 부분으로 쓴다. 조작감의 기준은 게임 내용이므로 사람이 정한다. 숫자는 목표 기기와 프레임률에 맞춘 프로젝트 값이다.

### 느낌 참고
노리는 느낌을 담은 구체적인 메커닉이나 순간을 댄다. 게임 이름만이 아니라 정확한 메커닉을 대고, 무엇을 빌리는지 적는다. 이렇게 느껴지면 안 되는 반대 참고도 둘 수 있다.

> 예: 「무기를 휘두르면 무겁고, 한번 휘두르면 되돌릴 수 없고, 미리 보이지만, 맞았을 때 시원하다. 둥둥 뜨는 가벼운 근접 공격은 아니다.」

### 입력 반응
행동마다 입력에서 보이거나 들리는 반응까지 허용하는 가장 긴 지연.

| 행동 | 입력에서 반응까지 최대 지연(ms) | 프레임 수(목표 프레임률 <프로젝트 값> 기준) | 메모 |
|---|---|---|---|
| <주 행동> | <예: 50ms> | <예: 3프레임> | |
| <보조 행동> | | | |

### 애니메이션 느낌 목표
이 메커닉의 애니메이션마다 프레임 목표. 시작 = 효과가 나기 전의 준비. 활성 = 행동이 「일어나는」 프레임(판정이 살아 있음 · 능력이 나감). 회복 = 행동이 끝난 뒤 되돌릴 수 없거나 빈틈인 프레임.

| 애니메이션 | 시작 프레임 | 활성 프레임 | 회복 프레임 | 느낌 목표 | 메모 |
|---|---|---|---|---|---|
| <예: 약한 공격> | | | | <예: 빠르고 부담 적음> | |
| <예: 강한 공격> | | | | <예: 무겁고 부담 큼> | |

### 맞는 순간
메커닉의 마침표 — 행동이 무게 있게 느껴지는 반응의 정점. 걸린 것이 큰 사건마다 적어도 하나를 둔다.

| 종류 | 길이(ms) | 설명 | 설정으로 바꿀 수 있나 |
|---|---|---|---|
| 멈춤(맞을 때 잠깐 정지) | <예: 80ms> | <예: 맞닿은 둘을 멈춤> | 예 |
| 화면 흔들림 | <예: 150ms> | <예: 방향 있고 줄어듦> | 예 |
| 카메라 충격 | | | |
| 컨트롤러 진동 | | | |
| 시간 느려짐 | | | |

### 무게와 반응 결
전체 느낌 목표를 짧은 글로. 아래에 답한다.
- **무게**: 무겁고 신중한가, 가볍고 재빠른가?
- **조종감**: 매 순간 얼마나 내가 조종한다고 느끼나? (높음 = 행동 중에도 고칠 수 있음 · 낮음 = 한번 하면 밀고 나감)
- **딱 떨어짐**: 또렷하게 끊기나, 부드럽게 이어지나?
- **가속**: 움직임 · 행동이 바로 시작하나(오락실 느낌), 0에서 차오르나(시뮬레이션 느낌)? 멈출 때도 같이 묻는다.
- **실패의 결**: 실수했을 때 공정하게 느껴지나, 벌처럼 느껴지나? 왜 실패했는지 읽히나?

### 느낌 수용 기준
플레이 시험하는 사람이 측정 도구 없이 확인할 수 있는 구체적인 기준. 주관적인 목표지만 판정이 한결같을 만큼 정확하게 적는다. 사람이 해 보지 않았으면 판정은 「못 봄」이다.
- [ ] <예: 전투가 묵직하다 — 시험한 사람이 묻지 않아도 무게를 말한다>
- [ ] <예: 아무도 「둥둥 뜬다」 · 「미끄럽다」 · 「반응이 없다」고 말하지 않는다>
- [ ] <예: 목표 프레임률 <프로젝트 값>에서 입력 지연이 느껴지지 않는다>
- [ ] <예: 멈춤이 끊김이나 렉이 아니라 시원함으로 읽힌다>

## 교차 참조
다른 기획서의 특정 메커닉 · 값 · 규칙에 기대는 것을 모두 밝힌다. 검토하는 역할이 이 표로 문서 사이의 어긋남을 찾는다 — 글 속에 숨은 참조를 확인할 수 있는 선언으로 바꾼다. 문서 어디서든 다른 시스템의 동작을 말했으면 여기에 있어야 한다.

| 이 문서가 참조하는 것 | 대상 기획서 | 참조하는 요소 | 성격 |
|---|---|---|---|
| <예: 연속 배율이 점수에 들어감> | <프로젝트의 기획서 위치> | `연속_배율` 출력 값 | 자료 의존 |
| <예: 죽으면 부활이 시작됨> | <…> | 죽음 상태 바뀜 | 상태 계기 |
| <예: 기력이 회피를 막음> | <…> | 기력 소진 규칙 | 규칙 의존 |

> **「성격」**: 다음 가운데 하나 — `자료 의존`(그쪽 출력을 쓴다) · `상태 계기`(그쪽 상태가 바뀌면 우리가 움직인다) · `규칙 의존`(우리 규칙이 그쪽 규칙이 참이라고 가정한다) · `소유 넘김`(값의 주인을 그쪽으로 넘긴다).

## 수용 기준
메커닉이 설계대로 되는지 확인하는 시험할 수 있는 기준. 기준마다 무엇으로 확인하는지(자동 시험 · 플레이 시험 · 눈으로 봄)와 그 증거를 둘 곳을 붙인다. 확인하지 못한 기준은 통과가 아니라 「못 봄」이다.
- [ ] <기준 1: 구체적이고 잴 수 있고 시험할 수 있다>
- [ ] <기준 2>
- [ ] <기준 3>
- [ ] 성능: 시스템 갱신이 <프로젝트 값>ms 안에 끝난다
- [ ] 구현에 박아 넣은 값이 없다(조절값은 데이터로)

| 질문 | 맡은 이 | 기한 | 결론 |
|---|---|---|---|
